01

What gets built

Two independent OpenAI-compatible model servers, each its own Docker container, each on its own port, both reading from the same Hugging Face cache. The worker does the agent loop; the critic runs the refutation pass on the verification ladder. They are deliberately different model families, so the critic's blind spots are not the worker's.

RoleModelPortAliasQuantUtil
Worker RedHatAI/Qwen3-Coder-Next-NVFP4 8002worker NVFP4 (pre-quantised)0.65
Critic microsoft/phi-4 8003critic FP8 (at load)0.18
Why phi-4 as the critic here

The worker is a Qwen. The one rule that overrides every other critic choice is do not judge a Qwen worker with a Qwen critic — that is precisely the correlation the second model exists to avoid. microsoft/phi-4 is MIT-licensed, ungated (no Hugging Face licence click, no token needed), dense 14B, and unusually strong at judgement per parameter. The alternative for a non-Qwen critic, google/gemma-3-12b-it, costs a licence acceptance and an HF_TOKEN; phi-4 costs neither.

Everything downstream — the ports, the two containers, the alias names — is what GlassCoder's configuration already expects, so wiring the harness to this is a matter of pointing it at the right hosts, not reshaping it.

02

Where vLLM comes from

The server is the stock upstream vLLM OpenAI image, pulled from Docker Hub. Both containers use the same tag, which means one image download covers both roles: 

vllm/vllm-openai:v0.20.0   # Docker Hub, the reference build

There is a second, NVIDIA-published build — nvcr.io/nvidia/vllm:26.02-py3 from the NGC catalog — tuned for Blackwell. Either serves these models. We stayed on the Docker Hub image because the worker was already running on it, so reusing it avoids a second multi-gigabyte pull and guarantees both roles behave identically.

The entrypoint has serve baked in

This image's entrypoint is already vllm serve. So the model is passed as the first positional argument — do not prepend serve yourself, or the container crash-loops with error: unrecognized arguments: serve. Every docker run below therefore reads … vllm/vllm-openai:v0.20.0 <model-id> --flag …, never … serve <model-id> ….

03

The memory budget

On the Spark the GPU and CPU share one ~119 GB usable pool. Every --gpu-memory-utilization value is a fraction of that whole pool, and the two containers' fractions add up. The knob is not just about fitting the models — it is what decides whether the desktop survives.

The lesson that set these numbers

At worker util 0.85 the worker claimed ~108 GB, leaving ~10 GB for the OS, the desktop and Firefox — and Firefox was OOM-killed. On unified memory an over-committed model server takes the browser down with it. The fix is not more RAM; it is a lower worker utilisation that reserves desktop headroom.

The settled split — worker 0.65, critic 0.18 — leaves roughly a fifth of the box for everything else:

Worker · util 0.65 ~77 GB
worker ~77 GB critic ~19 GB desktop ~23 GB
worker (weights + KV) critic (phi-4 fp8 + KV) OS + desktop + Firefox

Two properties of this arithmetic are worth keeping in mind. First, the reservations are persistent — a loaded container holds its slice whether or not it is decoding, so free RAM for the desktop is fixed by these two numbers, not by whether the models are busy. Second, co-residency is affordable precisely because the critic is cold most of the time: critique is a rung the agent loop awaits, so the worker is not decoding while the panel votes, and the two models are almost never hot at once.

If the desktop is…Worker utilTrade
Idle / headless0.70–0.75More worker KV and context; least desktop headroom.
Light browsing0.70~19 GB free — the guide's default.
Heavy browsing0.65~23 GB free; costs some worker KV / max context. chosen
04

Installing the worker

If a worker is already running and you are only changing its memory footprint, recover its exact launch arguments first, so you change one number and nothing else: 

docker inspect vllm-qwen --format 'IMAGE={{.Config.Image}}{{"\n"}}ARGS:{{range .Args}} {{.}}{{end}}'

Then remove the old container and start the new one. The model is the first positional argument (no serve): 

docker rm -f vllm-qwen

docker run -d --name vllm-qwen --restart unless-stopped \
  --gpus all --ipc=host -p 8002:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:v0.20.0 \
  RedHatAI/Qwen3-Coder-Next-NVFP4 \
  --served-model-name worker \
  --max-model-len 131072 \
  --gpu-memory-utilization 0.65 \
  --max-num-seqs 4 \
  --moe-backend marlin \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder
-p 8002:8000
Container serves on 8000; host exposes it on 8002. The critic takes 8003.
-v ~/.cache/huggingface
The shared weight cache. Both containers mount it, so weights download once.
--served-model-name worker
The alias clients call. It masks the checkpoint path — this is the seam that lets GlassCoder stay agnostic about which model is behind it.
--max-model-len 131072
128 K context. If the smaller pool can't hold its KV, lower this (see errors below).
--moe-backend marlin
The MoE kernel for this NVFP4 mixture-of-experts model.
--enable-auto-tool-choice
--tool-call-parser qwen3_coder
The worker is sent tools, so it needs tool-call parsing — with the Qwen3-Coder parser. The critic gets neither.
Dropping util re-reads all the weights

Restarting the worker re-loads every gigabyte of weights — budget 10–15 minutes before it is ready, and do not start the critic against the old, full pool or you meet the OOM killer instead of a clean error.

05

Fetching the critic weights

Pre-fetch the critic checkpoint into the same cache the container mounts. Doing it here rather than inside docker run means a failed download looks like a failed download, not a container that never becomes ready. First confirm the repo is ungated — cheaper than discovering it 15 GB in: 

M=microsoft/phi-4
curl -s "https://huggingface.co/api/models/$M" \
  | jq -r '"\(.id) gated=\(.gated) downloads=\(.downloads)"'   # expect gated=false

The Hugging Face CLI may not be installed, and its command was recently renamed from huggingface-cli to hf. Install it in an isolated environment with pipx, then put its bin directory on PATH: 

sudo apt-get install -y pipx || python3 -m pip install --user pipx
pipx install "huggingface_hub[cli]"
export PATH="$HOME/.local/bin:$PATH"   # this shell now
pipx ensurepath                        # persist for new shells
The cache is probably owned by root

If the worker container created the cache, every file in it is owned by root, and a user-space hf download fails with PermissionError: [Errno 13]. Hand the cache back to yourself first — the container reads it just fine afterwards: 

sudo chown -R "$USER:$USER" ~/.cache/huggingface
hf download microsoft/phi-4
du -sh ~/.cache/huggingface/hub/models--microsoft--phi-4   # ~28 GB BF16 when complete

The ~28 GB is the BF16 checkpoint; it is quantised to FP8 as it loads in the next step, so there is no pre-quantised checkpoint to hunt down.

06

Installing the critic

Only start the critic once the worker has been restarted at the lower utilisation and free -g shows the headroom is really there. Same image, model as the first positional argument, and note what is absent: 

docker run -d --name vllm-critic --restart unless-stopped \
  --gpus all --ipc=host -p 8003:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:v0.20.0 \
  microsoft/phi-4 \
  --served-model-name critic \
  --quantization fp8 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.18 \
  --max-num-seqs 3
--quantization fp8
Quantises the BF16 weights as they load. Blackwell has native FP8; this is the path with the fewest moving parts. It is also required here — BF16 phi-4 (~28 GB) will not fit the util slice.
--max-model-len 8192
The critic only ever sees a diff, capped by GlassCoder at 20 000 characters (~5 K tokens). An 8 K window is ample and keeps the KV cache small.
--gpu-memory-utilization 0.18
fp8 phi-4 weights plus runtime overhead consume ~18.6 GB; 0.18 (~21 GB) leaves ~2.8 GB for KV — comfortably above the 1.56 GB an 8 K window needs. 0.16 was too tight and failed to start.
--max-num-seqs 3
The critic panel fans out three votes in parallel (Critique:CriticCount), so three concurrent sequences.
no tool flags
No --enable-auto-tool-choice, no --tool-call-parser, no --moe-backend: the critic is never sent a tool, and phi-4 is dense, not MoE.
A harmless warning on start

Warning: You are sending unauthenticated requests to the HF Hub is cosmetic — the weights are already cached, so vLLM only hit the Hub for a metadata check. It does not block loading. Add -e HF_TOKEN=… to silence it if you like; nothing needs redoing.

07

Verifying health

A container that exists is not a server that answers. Check, in order: the container is Up (not Restarting), the log reached startup, the model alias is served, and the box still has headroom.

  1. Is it up, or crash-looping?

    docker ps --filter name=vllm --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'

    Up … is healthy; Restarting (…) means it is failing on boot — read the log.

  2. Did it finish starting?

    docker logs -f vllm-qwen     # and vllm-critic
# wait for: "Application startup complete." — Ctrl-C to detach

  3. Is each alias actually served?

    curl -s localhost:8002/v1/models | jq -r '.data[].id'   # → worker
curl -s localhost:8003/v1/models | jq -r '.data[].id'   # → critic

  4. Is there still headroom?

    free -g   # 'available' should sit ~20 GB with both models up
08

Calibrating the critic

A critic that serves is not yet a critic that judges. Give it a change whose evidence is visibly inadequate — a divisor guard that returns a value where the goal asked for a throw — and confirm it refutes, in parseable JSON: 

curl -s localhost:8003/v1/chat/completions \
  -H 'content-type: application/json' -d '{
  "model": "critic", "temperature": 0,
  "messages": [
    {"role":"system","content":"You are a reviewer whose job is to REFUTE a proposed code change. Judge it through this lens - correctness: does the change actually do what the goal asked, in every case the goal implies. Default to refuted:true when the evidence does not establish that the change is correct. Reply with JSON only: {\"refuted\": bool, \"confidence\": number between 0 and 1, \"reason\": string}."},
    {"role":"user","content":"Goal:\nMake Divide throw on a zero divisor.\n\nProposed change:\nreturn b == 0 ? 0 : a / b;\n\nEvidence offered:\nThe project compiles.\n\nCan you refute this change?"}
  ]}' | jq -r '.choices[0].message.content'

Two things must hold, and both are checked with jq, not by eye:

  • The reply contains a brace-delimited object that parses. The harness's fallback path will happily turn a prose refusal into an approving vote, so a reply that only reads like a refusal is a failure.
  • refuted is true. A critic that accepts this change — a value where a throw was asked for, justified by "it compiles" — will accept anything, and its contribution is worthless.
09

Wiring GlassCoder

Because --served-model-name keeps the aliases stable, the harness needs almost nothing changed. In config/appsettings.json the roles point at the endpoints: 

"Roles": {
  "worker": { "Endpoint": "http://localhost:8002/v1", "ModelAlias": "worker" },
  "critic": { "Endpoint": "http://localhost:8003/v1", "ModelAlias": "critic" }
}
Confirm the worker port matches

The stock config ships the worker role at :8001, but this worker serves on :8002. A critique pass is useless if the worker role cannot be reached, so the worker endpoint must say 8002 to match what is actually running.

The critique pass itself is off by default. Turn it on with either the config key or an environment variable: 

"Critique": { "Enabled": true, "Role": "critic", "CriticCount": 3, "Quorum": 2, "Gates": false }

# or, without editing the file:
GlassCoder__Critique__Enabled=true

Gates: false is deliberate: a small critic refuting a compiler-verified change is a claim worth reading, not a veto worth obeying. Compilation, tests and analyzers gate; the critic advises.

If GlassCoder runs on a different machine than the Spark, swap localhost for the box's hostname — e.g. http://spark.local:8003/v1. The alias is unchanged.

11

Errors we actually hit

error: unrecognized arguments: serve

The image entrypoint is already vllm serve, so a leading serve in the command produces vllm serve serve …. Fix: pass the model as the first positional argument, no serve.

huggingface-cli: command not found

The CLI is not installed, or is installed as hf and its bin dir is off PATH. Fix: pipx install "huggingface_hub[cli]", then export PATH="$HOME/.local/bin:$PATH" and use hf download.

PermissionError: [Errno 13] during download

The cache directory is owned by root (the container created it). Fix: sudo chown -R "$USER:$USER" ~/.cache/huggingface.

max seq len larger than KV cache

The utilisation slice held the weights but left too little for the KV cache — the critic hit this at 0.16 (0.39 GiB KV, needed 1.56 GiB). Fix: raise --gpu-memory-utilization (0.16 → 0.18) or lower --max-model-len. The same error can appear on the worker after dropping its util — there, lower --max-model-len (e.g. 65536) instead.

Firefox / the desktop crashes

Unified-memory over-commit: the model servers left too little for the desktop. Fix: lower the worker utilisation so the sum of both fractions leaves ≥15% free. This is why the worker sits at 0.65 rather than 0.85.

12

If one Spark isn't enough

The binding constraint on one box is memory, not speed — so a second Spark helps most by removing the co-residency squeeze, in one of two ways:

Isolation
Worker on one box, critic on the other — two independent servers over the ordinary network, no special link. The worker reclaims the whole pool (util back to 0.85, full context), the critic gets a dedicated box, and the desktop stops contending with both. In GlassCoder, only the critic role's Endpoint changes to the second host. This is the setup that solves the memory squeeze.
Sharding
Link the two Sparks over their ConnectX fabric and run one much larger worker tensor/pipeline-parallel across both. More setup, and only worth it to grow the worker — not for the critic.
Not a prerequisite

One Spark is a legitimate steady-state configuration: the critic is cold most of the time, and both models already co-reside here. A second box is a comfort-and-scale upgrade — buy it to reclaim worker context or to run a stronger, isolated critic, not to make this work.
