Design review & proposal · monitoring

A health & metrics monitor for the Spark's vLLM services

A small Python service that watches the worker and critic containers, keeps 24 hours of samples in SQLite, and serves one dashboard to every device on your tailnet. Most of the data already exists — the work is collecting it honestly and drawing it clearly.

Source vLLM /metrics + /health · nvidia-smi
Stack Python · SQLite · FastAPI
Reach tailscale serve (tailnet only)

01

The verdict

The proposal is sound and correctly scoped. Watching the two services, surfacing GPU and token usage, and showing daily totals plus a 24-hour graph is exactly the right amount of observability for a single box with two models on it — enough to answer "is it up, is it busy, what did it cost me today," without standing up a monitoring platform you then have to monitor. Four refinements shape the design:

ProposedVerdictRefinement
Observe health of the 2 services keep Use each container's /health for liveness — cheap, and it does not count as an inference request.
Display GPU + token usage free vLLM already serves a Prometheus /metrics endpoint per port. Tokens, throughput, queue depth and KV-cache % come from there — nothing to instrument.
Daily totals / max values care Token counts are monotonic counters that reset when a container restarts. Sum deltas with reset detection, or a restart silently erases the day.
Graph of the last 24 h keep Trivial in storage terms — at 15 s cadence that is ~5 760 points per series. SQLite handles it without noticing.
Reachable on all Tailscale devices keep Expose with tailscale serve (tailnet-only HTTPS), never funnel (public internet).
The one idea that changes everything

You are not building a metrics pipeline; you are building a thin reader over one that already runs. vLLM is a Prometheus exporter out of the box. The service's real job is to poll two /metrics endpoints on a timer, add the GPU/host numbers vLLM cannot see, keep a day of history, and draw it. That is a few hundred lines of Python, not a platform.

02

What's already exposed

Per service — straight from vLLM

Each container answers on its own port. Liveness and the metric feed are both HTTP GETs, so the collector needs no client library beyond an HTTP call: 

curl -s localhost:8002/health              # 200 = alive (worker)
curl -s localhost:8003/health              # 200 = alive (critic)
curl -s localhost:8002/metrics | grep '^vllm:'   # Prometheus text exposition

The series worth reading, and what each one is for:

MetricTypeFeeds
vllm:generation_tokens_totalcounterDaily output-token total; decode tok/s (as a rate).
vllm:prompt_tokens_totalcounterDaily input-token total; prefill volume.
vllm:request_success_totalcounterRequests served today; with failures, an error rate.
vllm:num_requests_runninggaugeLive concurrency; peak concurrency for the day.
vllm:num_requests_waitinggaugeQueue depth — the number that says "the box is saturated."
vllm:gpu_cache_usage_percgaugeKV-cache fullness; peak KV% is your context-pressure gauge.
vllm:time_to_first_token_secondshistogramTTFT p50/p95 — prefill responsiveness.
vllm:e2e_request_latency_secondshistogramEnd-to-end latency percentiles.
Metric names drift between vLLM versions

The vllm: series above are stable on v0.20.0, but names and label sets do move across releases. The collector should treat every series as optional — read what is present, skip what is not, and never crash because a counter was renamed. Pin the parser to "if the line starts with a known key, use it" rather than a fixed schema.

Host + GPU — what vLLM can't see

vLLM reports its own cache, not the machine. GPU utilisation, temperature, power and the unified-memory picture come from the host: 

nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total,temperature.gpu,power.draw \
  --format=csv,noheader,nounits
free -b                                   # unified pool: used / available
Unified memory reads differently here

On the GB10 the CPU and GPU share one pool, so "GPU memory" and "system memory" are the same 128 GB. Report the unified figure from free as the source of truth, and verify which nvidia-smi fields actually populate on this silicon before you trust them — some are blank on Grace-Blackwell. If a field is empty, fall back to tegrastats. Per-container GPU memory is not directly available; do not promise a per-model memory split the hardware won't give you.

03

Architecture

Three concerns, one small Python process: a collector that samples on a timer, a store that keeps a rolling day plus durable daily rollups, and a web layer that serves the dashboard and a tiny JSON API it reads from.

Collector
An asyncio task on a fixed cadence (10–15 s). Each tick: GET both /health, GET both /metrics, run nvidia-smi + read free, parse, write one row per service. Runs inside the web app as a background task, or as its own systemd unit — either way it must keep sampling when nobody has the page open.
Store
SQLite. One samples table (timestamp, service, the gauges, the counter readings) pruned to 24 h for the graph; one daily table (date, service, token totals, peak concurrency, peak KV%, uptime %) that survives restarts and lets "daily totals" outlive the 24 h window.
Web layer
FastAPI (or Flask). Two routes: / serves the dashboard HTML; /api/summary returns the tiles + the 24 h series as JSON. The page fetches that JSON and redraws on an interval.

Why counters become totals in the collector, not the query

Because a counter can reset under you, the honest daily total is accumulated at sample time, where a decrease is visible as a reset: 

def add_delta(prev, cur):
    # cur < prev means the container restarted and zeroed the counter;
    # the tokens since the last sample are then just 'cur', not cur - prev.
    return cur if cur < prev else cur - prev

today_out += add_delta(prev_out, cur_out)   # write to the 'daily' table
prev_out = cur_out

Storing the accumulated total (not the raw counter) means a restart costs you nothing, and the dashboard reads a number it can trust without re-deriving it.

Footprint discipline

The monitor must be invisible on the memory budget it is reporting on. A Python poller is ~40–60 MB of RAM and zero GPU — run it as a normal systemd unit or a tiny container, and never let it hold model memory. Polling /metrics every 10–15 s is negligible load; do not scrape per-second.

04

What to display

Two registers, as you proposed: at-a-glance state (tiles — current value, today's total, today's peak) and the last 24 hours (a few small time-series). Split by service, because the worker and critic have very different rhythms.

Status & daily tiles

  • Up / down per service, with uptime % for the day and time-since-last-seen.
  • Tokens today — input and output totals, per service and combined.
  • Requests today — served, and failed (error rate).
  • Peak decode — the day's max generation tok/s (your ~23 tok/s ceiling, observed).
  • Peak concurrency and max queue depth — did anything ever wait?
  • Peak KV-cache % and max GPU temp / power.
  • Unified memory — used / available right now, the number that predicts a desktop OOM.

24-hour graphs

  • Generation tok/s (decode throughput) — worker and critic on one axis.
  • GPU utilisation % and unified memory used.
  • KV-cache % and queue depth.
The critic will look idle — that's correct

Critique is a rung the agent loop awaits, so the critic is cold except in short bursts while a panel votes. Its throughput graph being flat most of the day is the co-residency design working, not a broken feed. Label it expected-idle so a quiet line does not read as a fault.

Drawing the graph, self-contained

Vendor a small plotting library (uPlot is ~40 KB and built for exactly this — many points, live redraw) into the app's static files rather than pulling a CDN at runtime. It keeps the dashboard working on a tailnet with no outbound internet, and keeps the page fast.

05

Reaching it over Tailscale

Bind the app to localhost, then let Tailscale publish it to the tailnet with automatic HTTPS and a MagicDNS name. No firewall ports open to the LAN, no public exposure: 

# app listens on 127.0.0.1:8090; Tailscale terminates TLS and proxies to it
tailscale serve --bg 8090

# now reachable from every device on the tailnet at:
#   https://spark.<your-tailnet>.ts.net/
tailscale serve status
serve, not funnel

tailscale serve keeps the dashboard inside your tailnet — visible to your devices, invisible to the internet. tailscale funnel publishes to the public internet; that is not what you want for a page that reveals your usage patterns and service health. Use serve. Because it is tailnet-only, the app itself needs no login — Tailscale ACLs are the access control.

06

Gotchas that bite

Counter resets
Handled at sample time (§3). The alternative — diffing counters at query time — reports a huge negative spike every restart.
Self-metering
Probe liveness with /health, not a completion. A monitor that sends inference to check "is it up" inflates the very token totals it reports.
Sampling must outlive the tab
If the poller lives only while a browser is connected, closing the page creates gaps and wrong daily totals. Keep it a background task/daemon independent of any request.
Unified memory semantics
Report free's pool as truth; verify nvidia-smi fields on GB10; don't invent a per-container GPU split.
Day boundary & timezone
Decide what "daily" means — local midnight, in one fixed timezone — and roll over on it consistently, or totals smear across two days.
Restart durability
The daily rollup lives in SQLite on disk, so a monitor restart (or a Spark reboot) doesn't lose the day. The 24 h sample buffer can be ephemeral; the daily totals can't.
07

Build it in phases

  1. Liveness only

    Poll both /health, render a two-row up/down page, serve it over tailscale serve. This alone answers the most common question — "are the models up?" — from your phone.

  2. Metrics ingest

    Parse /metrics, add nvidia-smi + free, write samples to SQLite, accumulate daily totals with reset handling. No graph yet — just the tiles.

  3. The 24 h graph

    Add the /api/summary JSON route and the vendored plot. Now the page has both registers.

  4. Polish

    Per-service split, expected-idle labelling for the critic, day rollover, and a small "packaged as a systemd unit / container" step so it starts on boot.

08

The off-the-shelf alternative

Everything above can be bought instead of built: Prometheus scrapes the two /metrics endpoints (plus node-exporter / a GPU exporter for the host), and Grafana draws the dashboard — 24 h graphs, daily aggregations via PromQL, and alerting, with almost no code.

ChooseWhen
Python service recommendedOne box, two services, you want a single small dependency-light thing that matches the rest of this project and you fully control. The 24 h / daily scope is modest enough that Prometheus is more machinery than the job needs.
Prometheus + GrafanaYou want alerting, retention beyond a day, or you expect to add more services and hosts. Then the platform earns its keep — and it can also receive GlassCoder's own OpenTelemetry (its OtlpEndpoint is currently null) to put run-level cost and pass@1 next to the server metrics.

Recommendation: build the Python service. It is the right size for the problem, it stays self-contained on a tailnet with no outbound internet, and it keeps you owning the one thing that matters here — an honest daily number. Reach for Grafana only when the scope grows past one box.

09

Open decisions

Four choices to make before the first line, none of them blocking:

  • Retention beyond 24 h? The graph is 24 h by design; do you want the daily rollups kept for 30/90 days to see week-over-week, or is today-plus-yesterday enough?
  • One dashboard or per-service pages? Combined is simpler; per-service reads cleaner given how differently the two behave.
  • Packaging. systemd unit on the host (lightest) vs a third small container next to the models (consistent with how the models run). Either is fine; pick the one you'd rather operate.
  • GlassCoder tie-in, later. Whether to eventually surface run-level numbers (tokens-to-solve, cost, pass@1) from GlassCoder's metrics next to the server metrics — natural, but out of scope for v1.
Scope for v1

Two services' health, host GPU + unified memory, per-service token totals and peaks for the day, and a 24 h graph of throughput / memory / KV — served over tailscale serve. That is a genuinely small, genuinely useful service, and every number in it is one the hardware or vLLM already emits.
