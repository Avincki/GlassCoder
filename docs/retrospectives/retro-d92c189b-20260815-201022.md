## What these two reviews say about the harness

Three of the run's expensive stretches are instances of properties this repository has already
named. One is new, and it is the one that matters most, because it undermines the reviews
themselves.

### 1. The repeated-failing-test nudge went blind, and the harness is what blinded it

`RunProgressSentry.ObserveTestOutcomes` (`RunProgressSentry.cs:289`) counts a repeated failing
result only when `invocation.ToolName == "run_tests"`. Its nudge is well-written and is exactly the
advice this run needed: *"Your changes are not reaching the failure… delete the failing approach and
solve it another way."*

Steps 22, 23 and 26 produced byte-identical failing results — three tests dead on WPF's STA
requirement — and every one of them arrived through the ladder's inline verification after a
`create_file`/`edit_file`, not through a `run_tests` call. The counter never advanced. The agent
guessed `[STAThread]` (inert under xUnit), guessed a package, and reached the nudge's own conclusion
unaided at step 26. Firing at step 24 would have saved roughly three steps and two blind guesses.

This is not an accident, and it is not the model's fault. Since 2026-08-09 the system prompt tells
the model **not** to call `build`/`run_tests` itself; since tonight `update_todos` tells it not even
to *plan* one. The harness deliberately moved test results off the tool and onto the ladder — and
the counter that watches for a stuck red tree still watches the tool. The doc comment at
`RunProgressSentry.cs:104` cites `ea9a1f66` and `216360bf`, both of which called `run_tests`
explicitly. This is precisely the generalisation last night's HISTORY entry wrote down: *a mechanism
keyed to the shape of the run that revealed it goes blind the moment the same fact arrives by a
different door* — and here the harness itself opened the other door.

### 2. Every green says what moved; no red does

`VerificationLadder.Unmoved` (`:214`) is appended on the passing branch only (`:422`). The failing
branch (`:429-433`) carries the count, the names and the first assertion message — and nothing about
whether any of it is the same as last time. The stated generalisation, **"every green should say what
moved since the last one"** (`TestCountMemo.cs:20`), has an unimplemented mirror. Step 26 is the
cost: the moment the agent finally got the diagnosis right, its feedback was byte-identical to the
two moments it had it wrong, because the abandoned STA tests were still in the file. "The same three,
failing the same way" versus "two carried over, one new" is the difference between a gradient and a
flat surface.

### 3. A signal cheaper to satisfy than the thing it stands for — third recorded instance

`TestSuiteNotices.OrphanTypeNotice`'s doc comment already carries the scar from run `46231701`: the
clause was silenced by one line in a click handler. The 2026-08-11 fix removed the *prescription*
from the sentence. Step 34 of this run made the product call `Calculator` anyway, and that is why the
deliverable has three types and a two-hop chain for `a * b`. **The cheap route is a property of the
detector, not of the sentence** — removing the advice did not remove the move. The harness still
cannot see this happen: both times it was established by hand-tracing two transcripts.

Worth saying plainly: the notice also *worked*. It reversed a premature finish at step 18 and drove
the step-33/34 investigation. That is more than run `4c7de12b`'s retrospective could say for it.

### 4. New: the code reviewer was handed a change set that disagrees with the working tree

The code review's finding 5 — `MultiplyAppTests.csproj`'s `ProjectReference` absent from the diff it
was given, and a package version that disagrees with disk — is a defect in the review pipeline, not
in the run. `RetrospectiveReviewer.DescribeChanges` (`:667`) renders per-change diffs from
`IChangeLog` and never compares any of it against the file that is actually there. Two mechanisms in
that method can produce the symptom, and both are worth fixing regardless of which one did:

- the cap `break`s on the first oversized diff (`:699`), dropping every later change and naming none
  of the paths it dropped;
- the filter admits `ChangeStatus.Proposed` (`:673`), so a change that never landed is shown to the
  reviewer as part of the deliverable. `RunReviewer.cs:251` — which feeds the *critics* — has the
  same filter.

Nothing else in the harness has this shape. `dotnet_project` re-reads from disk for its after-text
(`DotnetProjectTool.cs:996`), the workspace pane was moved off the change log onto a
`FileSystemWatcher` for exactly this reason on 2026-08-04, and `TestSuiteNotices` sweeps real
sources. The reviewers are the last organ still taking the change log's word for what exists. A
reviewer reasoning from a file state that never existed is the one failure that discredits every
other finding it makes.

### 5. Locale: the runtime argument does not cover the static one

Last night's entry left the culture-sensitive parse open, *"invisible to a single-machine loop by
construction"*. That is true of the runtime oracle — and this run proves it twice over, since the
probe typed `5.0` and `3.0`, which are the two values that cannot distinguish the bug. It is not true
of a static one. `double.TryParse(text, out value)` with no `IFormatProvider` is a syntax fact,
visible at write time, on the same seam `XamlNotices` already uses. Nothing in the harness loads a
`DiagnosticAnalyzer`, so CA1305 can never fire from the Analyzers rung. This is occurrence two on the
operator's own machine culture; by the rule task 70 applied to the zero-match refusal, that makes it
a fix rather than a watch.

### What I would not build

The code review's "five of eleven tests test the `*` operator" and the exact-float-equality trap sit
on the far side of task 66's boundary — *"not in scope: judging test quality"* — and the reason for
that boundary still holds. Coverage adequacy is a slope with no defensible stopping point; "do the
tests touch the product at all" is a question with an answer.

`launch_app` being elective is already Open in HISTORY twice and has an unticked recommendation
against it, so I have not re-proposed it. This run is more evidence for it: steps 37-40 are the best
work in the run, the runtime proof is real, and it exists only because a critic demanded it. The
2026-08-15 investment — the absence line in the completion panel, the probe, the window sweep — is
what made those four steps possible, and it paid.
