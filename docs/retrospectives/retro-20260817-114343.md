## The pattern, stated once

This run is a clean instrument: no failures, no retries, no thrash, every edit landing first try. Nothing here is noise from a struggling run. What it shows is a harness whose *facts* are all correct and whose *consequences* are all optional.

Six times in twenty-one steps the harness told the agent something true and load-bearing, attached to a successful result, and nothing happened:

| Step | What the harness said | What followed |
|---|---|---|
| 0, 3, 6, 10, 14 | "'Build and run tests' restates the automatic verification" | item carried all five times, then discharged at 15–16 |
| 7 | fixed 300px may clip; `launch_app` can see it | no resize, no launch — until step 18, under refutation |
| 12 | the csproj edit is in the change log | log never opened; stale `net10.0` output survived |
| 14 | plan-complete is not evidence the goal is met | next two steps gathered more of the evidence it already had |
| 18 | "nothing was typed into it, so this is what it shows at rest" | read back at 19 as "the application is working correctly" |
| 3, 9 | warnings 2 → 4, one pointing at the line just written | never diagnosed; cleared by accident |

Every one of these is a *notice riding on an `[ok]`*. HISTORY has already fixed this shape at least four times on the failure side — the suite notice reaching `RunProgressSentry`, `AbandonedIntents` for refused calls, the identical-failure counter, the test-outcome counter that moved doors on 2026-08-17. The success side has no equivalent. A notice attached to a green result is, structurally, decoration: nothing counts it, nothing carries it, nothing at completion says it went unanswered.

That is the pattern. It is not an accident of this run — the same six-times-in-a-row shape is what HISTORY's own 2026-08-15 entry called *"a mechanism keyed to the shape of the run that revealed it goes blind the moment the same fact arrives by a different door."* Here the door is simply **success**.

## The one finding that changes an already-planned item

`launch_app` being elective is open and unticked, and HISTORY correctly calls the loop-launches-what-it-built version "the mechanism version of everything above." I am not re-proposing it.

But this run is the case that says **auto-launch alone would not have fixed it.** A launch *did* happen at step 18. It swept the window. Its own result said in plain text that nothing had been typed. Step 19 read that as working, step 20 escalated it to a verified feature list, and all three critics accepted — one of them reasoning explicitly from "displays the required UI elements." The gate the critique rung enforced was *whether a launch happened*, and once one existed it opened.

The goal's verb was "press Multiply." The button was never pressed, in the app or in a test, by anyone — and the previous run's report records the same un-pressed-button refusal being outvoted 2–1 one run earlier. That is occurrence three. Auto-launching would have produced the same at-rest snapshot eleven steps sooner and the same acceptance.

The missing mechanism is one the harness already built once: on 2026-08-15 the completion panel learned to *state the absence* of a launch, because "the panel had to infer an absence from a line that was not there." The exactly-parallel absence — a launch happened, no input was ever sent — is still only inferable from a caveat buried in an evidence blob that three critics and the worker all read past.

## Where the run's real defect was decided, and whether the harness could have been there

The code review's headline defect (bad or empty input silently produces a stale result) traces to step 5: `double`-typed operand properties put the string→number boundary inside WPF's default converter, where nothing the agent could write is testable. No harness signal exists for that and I am not proposing one — it is a design call, and inventing a notice for it would be exactly the speculative detector `CLAUDE.md §18a` forbids.

Two smaller findings *were* within the harness's reach and it stayed quiet in a way it has already decided not to elsewhere: there is no solution file anywhere in the workspace (`ProjectLocator` already volunteers the sibling fact that an empty solution builds nothing, whether or not anyone asks), and the harness's own retarget left a stale `net10.0` output directory beside the new one.

## What was genuinely right

Test ordering was correct and the tests are real — the `ProjectReference` landed at step 12 before tests were written at step 13, so "8 tests passed" honestly meant production code ran. The step-12 framework retarget handled the one real environmental trap in a WPF+xunit layout without the agent fighting it. The refutation at step 17 was well-formed, unanimous, actionable, and recovered from in one step. The step-7 clipping warning was, per the code review's own measurement, a false positive — the layout had roughly twice the room it needed.

- [x] **High** `panel-states-no-input-was-sent` - Completion panel states the absence of input, not just the absence of a launch
      Where the panel already emits its one-sentence absence line when the workspace holds something runnable and no launch was recorded (shipped 2026-08-15, `CritiqueCompletionAsync`), add the sibling case: a launch exists but no probe ever typed or clicked. Today that fact lives only inside the launch summary's hedge ("nothing was typed into it"), which the worker read back at step 19 as "the application is working correctly" and which all three critics accepted past at step 20. The critique rung's gate is effectively 'did a launch happen', so once step 18 produced one, the gate opened on a rest-state snapshot. This is NOT the already-open auto-launch item — a launch did happen here, and auto-launching would have produced the same snapshot eleven steps earlier with the same acceptance. It is also distinct from the previous retrospective's still-outstanding 'sweep the buttons too' item, though the two compose well: this run's sweep printed txtOperand1/txtOperand2/txtResult and no button, so no name for the button existed to press. Verified by: a WPF run whose launch is a bare sweep shows the absence line in the completion panel's evidence, and the line disappears on a run whose probe sent at least one type or click.
- [x] **High** `update-todos-strikes-the-ladder-item` - update_todos strikes the ladder-restating item instead of only naming it
      In the `update_todos` handling shipped 2026-08-15 (night): today an item whose whole title restates the automatic verification is named once per call and left in the plan, deliberately, because 'a refusal spends a step on a rewrite, which is the waste being prevented'. This run is the first live test of that trade and it lost. The same sentence came back verbatim at steps 0, 3, 6, 10 and 14; the item was never edited; and at steps 15 and 16 the agent discharged it literally by re-running verification that had passed automatically since step 2. That is five bookkeeping steps plus two redundant verification steps — a third of a 21-step run — against the one rewrite step the current design was protecting. Third option neither taken nor considered: accept the plan, drop the item, and say in the result which item was struck and why. No refusal, no extra step, and the item cannot be discharged later because it no longer exists. Verified by: replay a plan containing 'Build and run tests'; the accepted plan comes back one item shorter with the strike named, and a follow-up call that re-adds it is struck again.
- [x] **Medium** `unanswered-advisory-notices-are-counted` - Count advisory notices that ride on a successful result
      Every consequence mechanism in the harness is keyed to failure — the suite notice into `RunProgressSentry`, `AbandonedIntents` on refused calls, the identical-failure counter, the test-outcome counter re-doored on 2026-08-17. A notice attached to an `[ok]` result has no counter at all. Six fired in this run (update_todos ×5, XamlNotices clipping, the change-log pointer at step 12, the plan-complete nudge at step 14, the at-rest caveat at step 18) and not one changed behaviour or reached the run record. Add the smallest version: a notice keyed by (source, subject) that is re-emitted on N consecutive calls without the subject changing becomes an unanswered notice, surfaced to the completion panel and the run record in the shape the test-suite notice already uses ('Completed over an unanswered ...'). Do not gate on it — this repository has paid twice for gates that would not concede. Note the overlap with the still-unticked 'update_todos echoing an outstanding notice' item from run 4c7de12b; this is the register that item would read from. Verified by: run 31983adb replayed produces at least one 'completed over an unanswered notice' entry in its run record; a run whose notice is acted on produces none.
- [ ] **Medium** `clipping-notice-settled-by-the-sweep` - Let the launch sweep clear or confirm the static clipping notice
      `XamlNotices` warned at step 7 that a fixed 300px height might clip and pointed at `launch_app`. The code review measured the layout — roughly 115px of content in ~220px of client height — and calls the warning a false positive. Meanwhile the geometry half of the sweep shipped on 2026-08-15 (night) reads `IsOffscreen` and compares each rectangle with the window's, so eleven steps later the harness had the definitive answer and never connected it to its own earlier guess. Wire the two: a clipping notice raised statically is cleared by a launch whose sweep reports nothing outside the window, and stands as outstanding at completion if no launch ever happened. This costs no new sentence — both texts exist — and stops a heuristic guess from being indistinguishable from a measured fact. Verified by: the deliberately-too-short window fixture keeps the notice through its launch; a comfortably-sized window that raised the static notice has it cleared, and the transcript shows the clear.
- [ ] **Medium** `harness-edits-report-what-they-changed` - A harness-performed project edit reports the change inline, not a pointer to the change log
      At step 12 the harness widened the test project's target framework and told the model 'the csproj edit is in the change log'. The agent never opened the log — not then, and not at step 19 when it finally called `list_changes`, which by then came after 'the application is working correctly' had already been written, making it a closing formality rather than a review input. CLAUDE.md §18a's own rule ('no capability the model must elect') applies to reading as much as to acting. Where the harness rewrites a project file on the model's behalf (the retarget path in the test-project/reference tooling), render the substance in the step result — old TFM → new TFM, and any other property it moved — rather than a pointer. Verified by: the retarget step's transcript entry names both framework values; grep a fresh run's JSONL for the new TFM and find it in the step result, not only in the change log.
- [ ] **Medium** `no-solution-stated-like-an-empty-one` - State 'projects but no solution' the way an empty solution is already stated
      `ProjectLocator` has owned the sentence 'an empty solution builds nothing' since 2026-08-15, delivered to the completion panel and the run record whether or not anyone asks, precisely because the fact was previously behind a call the run had no reason to make. A workspace with two projects and no solution at all is the same class of fact with the same consequence — `dotnet build`/`dotnet test` from the root has no target (this is dd11ef7c's MSB1003, recorded 2026-08-15). It escaped `AbandonedIntents` here because nothing was ever refused: the run simply never asked. Add the sibling sentence on the same author, same two surfaces. Deliberately a statement, not a refusal or a scaffold — whether a two-project layout wants a solution is the operator's call. Verified by: a workspace with ≥2 projects and no `.sln`/`.slnx` produces the line at completion; adding a solution removes it.
- [ ] **Medium** `warnings-say-what-moved` - Apply 'every green says what moved' to build warnings
      HISTORY wrote the generalisation down on 2026-08-15 (night) after `TestCountMemo`: every green should say what moved since the last one. Warnings are the next axis and are currently unreported. This run went 2 → 2 → 2 → 4 → 0: at step 9 one of the two new warnings pointed at `MainWindow.xaml.cs(19,22)`, the field the agent had written that same step, and by step 16 the count was 0. The agent noticed a warning at step 3, said so in prose, and never returned; the condition cleared without anyone understanding it. Have the compile rung's summary carry the delta and the first newly-appeared warning with its file and line, in the same run-keyed memo shape as `TestCountMemo`, landing after the count and never inside it so the sentry's first-line keying is untouched. Distinct from the declined 'annotate-benign-template-warnings' item, which was about classifying warnings rather than reporting movement. Verified by: a fixture edit that introduces one warning shows '+1 warning since the last climb' naming it; an unchanged rebuild says the count did not move.
- [ ] **Low** `retarget-sweeps-stale-output` - A harness-performed TFM change names or sweeps the orphaned output directory
      The retarget at step 12 left `tests/MultiplyApp.Tests/bin/Debug/net10.0` beside the new `net10.0-windows`. Harmless to the SDK, and the code review is right that a runner pointed at the old path would execute the stale assembly. The precedent is Clean's boundary argument from 2026-08-15: sweep only what decides what the next command resolves to, name it before it goes, and leave the operator's files alone. This is narrower than Clean — one directory, created by the harness's own edit, under a folder that is already in the writable set. If sweeping is judged too aggressive, naming it in the step result is most of the value. Verified by: a retarget run leaves exactly one framework directory under the test project's `bin/Debug`, or a transcript line naming the orphan.
- [ ] **Optional** `notified-but-unbound-property-notice` - Notice a ViewModel property that raises PropertyChanged and that nothing consumes
      `XamlNotices` already reads a window and its code-behind as a pair and asks 'this sets a DataContext and binds to nothing'. The code review's finding #3 is the next question in that family: `CanMultiply` raised `PropertyChanged` on every operand change, the button had no `IsEnabled` binding, and the code-behind bound only three properties — plumbing implying an affordance that never existed. The process review traces it to the producing and consuming sides never being in view at the same time (the agent never re-opened `ViewModel.cs` after writing it at step 5). Caveat that makes this Optional rather than Medium: this run built its bindings in code-behind, so a XAML-only scan would not have seen them, and it is one occurrence — HISTORY's own rule is no new detector without a live run that spun on that shape, and this run did not spin. Worth building only if a second occurrence lands. Verified by: a fixture ViewModel notifying a property absent from both the XAML bindings and the code-behind binding calls raises the notice; adding the binding clears it.
