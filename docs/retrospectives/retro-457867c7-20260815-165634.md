## What this run says about the harness

Run `457867c7` is the live test the 2026-08-15 (later still) entry asked for — *"the next WPF run on `GlassCoderTest` is the real question"* — and it half-answers it. The unasked-for sweep fired at step 25 and reported two empty boxes with the narrowed hedge (*"nothing was typed into it"*), and that reading is what two of three critics refused on at step 26. **That is the only gate in the run that saw the true state, and it saw it because of a mechanism shipped hours earlier.** The rest of the run is a study in where that mechanism stops.

### The thesis: every rung judges an artifact; nothing judges the composition

From step 16 to step 27 the harness held two implementations of one feature — a `ViewModel` with `INotifyPropertyChanged` that the tests drove, and code-behind `TextChanged` handlers that the window actually ran, with no `{Binding}` in the markup. Twelve verification passes reported success in that window. Every one was honest: both files compiled, the suite really passed, the app really launched. The ladder answers *does this artifact hold up*; it has never been asked *is this artifact the one that runs*.

This is a pattern, not an accident. It is the same family task 66 was written for, seen from the other side:

- `122e11c6` — tests that touch no product type.
- `d5edbc59` — tests that touch a product type nothing ships.
- `46231701` — the product made to touch the type, one line, to silence the notice.
- `457867c7` — the product touches the tested type (`DataContext = new ViewModel()`) and **displays nothing from it**. All three existing clauses stay correctly silent, and the suite is exactly as hollow as `122e11c6`'s.

Every previous instance was caught inside the C# graph. This one lives across the C#/XAML seam, which is where WPF puts the wiring, and it is the seam no sweep crosses. Recommendation 1 is that clause.

The second half of the same story: the run's two load-bearing lines are `OnPropertyChanged(nameof(Fahrenheit))` and its mirror. Delete both and all eight tests still pass. The run *changed the notification mechanism at step 20 to make a test go green* and added no test for it — with two test names (`CelsiusChangeTriggersFahrenheitUpdate`) claiming otherwise. Nothing in the harness asks whether a suite ever subscribes to the events the product raises (recommendation 5).

### Electing a capability turned off the one that did not need electing

`IUiProbe`'s own doc comment states the rule this repository paid for twice: *an optional capability the model must remember to ask for is advice, not a mechanism.* This run shows the rule biting from the inside. `LaunchAppTool.cs:185` reads `asked ? RunAsync(script) : ReadAllAsync()` — **asking a question suppresses the sweep**. The three launches at steps 35–37 typed a value and read one box; the rest of the window went unread on precisely the launches where the window had been changed most recently. Recommendation 2.

And the panel only ever sees one of them: `RuntimeEvidence._latest` is a single string per run, overwritten by each `Record`, and `AgentLoop.cs:777` reads `.Latest`. The run demonstrated three input/output pairs; the panel that accepted 3/3 at step 39 was handed the last one. This is the fourth instance of the shape the `[ModelFacing]` invariant was invented for on 2026-08-15 — the harness collecting a fact and dropping it one organ short of the reader (`tests.Output` at task 69, `tests.Notices` at task 66, `ToolError.Hint` yesterday, launches today). Recommendation 4, with recommendation 8 as the invariant that stops the fifth.

### The interface made the run edit shipped code

`UiAutomationProbe.Find` resolves `AutomationId` then accessible `Name` — nothing else. `launch_app`'s parameter description says *"window checks by x:Name"*. So at steps 30–33 the run guessed names, got `no element by that name` three times, read its own file, and **added two `x:Name` attributes to production markup for the sole purpose of being able to answer the harness**. The code reviewer read those dead attributes (finding #6) as the agent restoring lost context; the process reviewer correctly read them as instrumentation residue. Both are downstream of the tool's address space. Meanwhile the sweep already prints an identity for unnamed controls — `the box after "Celsius:"` — that the prober cannot accept back. Recommendation 3 closes that loop: the harness should be able to drive anything it can name.

### What is accident, and should not be generalised

- The agent's stated diagnosis at steps 19–20 was muddled and its fix was subtly right. Task 69's assertion messages already address the class.
- Step 27's recovery came from over-reading a partly-overstated critique ("no evidence" heard as "the binding is broken"). It landed on the true defect by luck. The right response is more evidence reaching the panel (2 and 4), not a stricter gate.
- The exact-float assertions passed because every chosen value happened to be representable. `exact-float-equality-notice` was already proposed and left unticked on 2026-08-11; I have not re-proposed it.
- Findings #3 and #4 (silent desync on bad input, `37.77777777777778` in the box) are the **second** recorded occurrence — `IUiProbe`'s own doc comment names run `ae72c5ad` for the identical pair. By this repository's stated rule, occurrence two is a fix (recommendation 6).

### The cheap waste, briefly

Steps 3–8 each spawned `dotnet test` against a tree with no test project and reported `0 tests — nothing was verified` six times. The verdict wording is already honest; what is missing is that the ladder pays a process launch for an answer it can read off the project files (recommendation 7). This is the smallest item here and the only one that is purely about cost.

### Net

Nothing in either review argues for a new gate, and I have proposed none. The harness's reliability layer did its job; four of the six items below are about **sight** — making the harness look at the whole window instead of the field it was asked about, address what it can already name, forward everything it collected to the panel that asked for it, and notice when the thing under test is not the thing that runs.

- [x] **High** `window-uses-what-you-test` - Notice when the window binds nothing to the view model it sets
      `XamlNotices.Describe` (src/GlassCoder.Tools/FileSystem/XamlNotices.cs:42) returns empty for any non-`.xaml` path, so it never sees a code-behind. Extend it to accept `*.xaml.cs` as well and evaluate the pair (markup + sibling `.xaml.cs`, whichever was just written), adding a third clause that fires when: the code-behind assigns `DataContext` to a workspace type, AND the markup contains no `{Binding`/`{x:Bind`, AND the code-behind contains no `SetBinding(`/`new Binding(`. Word it as a question in the existing house style — the window sets its DataContext to `X` and displays nothing from it, so tests of `X` cover a path the window does not use. Both write tools already call this (CreateFileTool.cs:205, EditFileTool.cs:248), so it rides existing summaries; keep it a notice, never a gate — programmatic binding and DI-composed views are known false positives. Verified by reconstructing run 457867c7's step-16 tree (markup with `x:Name` TextBoxes and `TextChanged` handlers, code-behind assigning `DataContext`): the notice fires. The shipped final markup — the same file with `Text="{Binding Celsius…}"` — is silent, as is a window that sets no DataContext at all.
- [x] **High** `asked-for-probe-still-sweeps` - An asked-for probe should not switch the window sweep off
      LaunchAppTool.cs:180-196 runs `RunAsync(script.Steps)` when a probe was asked for and `ReadAllAsync()` only when one was not, so the model gets the unasked-for sweep exactly until it starts asking questions. Run the script first, then the sweep, and report both — `ProbeReport` (LaunchAppTool.cs:319) already splits on `asked`, so emit `Probe: …` for the readback and `Window: …` for the sweep; the ten-reading cap and the launch's own clock already bound the cost. The hedge table at LaunchAppTool.cs:241 needs a third case: a sweep taken *after* typing is stronger evidence than one at rest and should say so without silencing the pixels/layout boundary. Verified by a test that launches with `probe: "CelsiusTextBox=100; FahrenheitTextBox?"` and asserts the summary contains a reading for a control nothing asked about; and by replaying steps 35–37 of run 457867c7, where each launch typed one value and left the rest of the window unread.
- [x] **High** `probe-addresses-unnamed-elements` - Let the probe drive the elements the sweep already names
      `UiAutomationProbe.Find` (src/GlassCoder.Tools.Windows/UiAutomationProbe.cs:305) resolves by `AutomationId` then accessible `Name` and nothing else, and `launch_app`'s parameter description (LaunchAppTool.cs:98) says 'window checks by x:Name'. That is why run 457867c7 got `no element by that name` three times and then added two dead `x:Name` attributes to shipped markup purely to be addressable — the harness's interface edited the product. `ReadAll` (UiAutomationProbe.cs:110-151) already computes a placeable identity for unnamed controls (`the box after "Celsius:"`, `Edit#2`); extract that label map and use it as the third lookup in `Find`, and when a step still finds nothing, put the labels the window does offer into the `Problem` string instead of `no element by that name` (UiAutomationProbe.cs:197). Update the parameter description so it no longer teaches naming. Verified by driving the run's final XAML with both `x:Name` attributes deleted: `probe: "the box after \"Celsius:\"=100; the box after \"Fahrenheit:\"?"` reads back 212, and a nonsense element name reports the identifiers that exist.
- [x] **High** `panel-sees-every-launch` - The completion panel sees every launch, not the last one
      `RuntimeEvidence` keeps one string per run (`_latest[RunId] = …`, LaunchAppTool.cs:434) and `AgentLoop.cs:777` hands `.Latest` to the completion critique. Run 457867c7 demonstrated three input/output pairs at steps 35–37 and the panel that accepted 3/3 at step 39 was shown one of them. Keep an ordered, de-duplicated list per run (cap it — four is a window's worth) and render it as one block: what was launched, what was typed, what came back, each time. Reuse-flagged launches (`TryReuse`, LaunchAppTool.cs:453) must not be appended twice. The evidence fingerprint at AgentLoop.cs:790 keeps working unchanged. Verified by replaying steps 35–37 and asserting the string passed to `CritiqueAsync` contains all three readbacks; and by asserting that two identical launches with nothing applied between them still contribute one entry.
- [ ] **Medium** `tests-never-subscribe-notice` - Notice a product event the suite never subscribes to
      Fourth clause on `TestSuiteNotices` (src/GlassCoder.Tools/Verification/TestSuiteNotices.cs:79), same sweep, same syntax-only contract, same notice-never-gate wording. `ReadProductFile` collects event declarations from non-test sources; `TestIdentifiers` is already the set of identifiers used inside test method bodies, so the clause fires when a product type declares an event no test body mentions. In run 457867c7 the two load-bearing lines are `OnPropertyChanged(nameof(Fahrenheit))` and its mirror — delete both and all eight tests still pass, including two named `…TriggersFahrenheitUpdate`. The step-20 repair *was* the notification mechanism and no test followed it. Verified against that run's tree (notice names `PropertyChanged` on `ViewModel`); adding one test that does `viewModel.PropertyChanged += …` silences it; a workspace whose product declares no events is silent.
- [ ] **Medium** `numeric-textbox-binding-notice` - Notice a numeric TextBox binding with no StringFormat
      Second recorded occurrence, which is this repository's own threshold for acting: `IUiProbe`'s doc comment names run `ae72c5ad` for 'a raw 37.77777777777778 in the box', and run 457867c7 shipped the identical pair — `Text="{Binding Celsius, UpdateSourceTrigger=PropertyChanged}"` with no `StringFormat` and no validation, so a computed double renders 17 digits and a non-numeric keystroke silently leaves the other box showing a contradicting value. Add a clause to `XamlNotices` firing on a `TextBox` `Text` binding with no `StringFormat` whose source property the workspace declares as `double`/`float`/`decimal`; the write tools already hold an `ICodeAnalyzer` (CreateFileTool.cs:53) to resolve the DataContext type's property from the syntax tree. Name both consequences and prescribe nothing — the run's own reviewer notes that formatting alone re-opens the round-trip question, so the fix is the model's to find. Verified: the run's final `MainWindow.xaml` + `ViewModel.cs` is noticed, `StringFormat=F2` silences it, and a TextBox bound to a string property is silent.
- [ ] **Medium** `no-test-project-skips-the-test-process` - The test rung stops paying dotnet test for an answer it can read
      Steps 3–8 of run 457867c7 each applied a `dotnet_project` scaffold change, which climbed the ladder, which spawned `dotnet test` against a workspace with no test project and reported `The test run exited cleanly but ran 0 tests - nothing was verified` six times. Before running the rung (VerificationLadder.cs ~355-385), ask whether any project references a test framework — the same predicate `TestSuiteNotices.IsTestFile` already uses via `ProjectLocator.ReadReferences` — and when none does, return the rung with `Unverified = true` and a summary naming that fact, without spawning anything. Keep `Unverified` set so `UnverifiedVerifications` still counts it and nothing reads as a pass. Verified: a scaffolding step on a testless tree climbs in milliseconds with the rung saying there is no test project yet; adding a test project makes the rung execute again on the next applied change.
- [ ] **Low** `critic-evidence-invariant` - An invariant test for evidence reaching the critics
      Generalise recommendation 4 the way `[ModelFacing]`/`RetrospectiveDigestTests` generalised the dropped hint on 2026-08-15. The panel's evidence string is assembled from three sources in AgentLoop.cs:755-815 — the verification rung summaries, `RuntimeEvidence`, and `AbandonedIntents` — and losing one is silent today, which is how the launches were lost. Add `CriticEvidenceTests`: populate each source with a distinct sentinel, run the completion path against a fake `ICriticPanel`, and assert every sentinel appears in the string handed to `CritiqueAsync`. Verified by deleting the `runtime is not null` block at AgentLoop.cs:777 and watching the build fail; the value is that the next source added is covered without anyone remembering to cover it.
- [ ] **Optional** `probed-values-already-asserted` - Say when a probe only re-typed values the suite already asserts
      Offered as taste, and honestly flagged as a sentence rather than a mechanism, which CLAUDE.md §18a discourages. Steps 35–37 spent three launches on 0/32, 100/212 and 212/100 — the same round numbers the unit tests had already proved three times — while one non-representable value would have shown 37.77777777777778 and one non-numeric keystroke would have shown the two boxes contradicting each other. The harness can compute the overlap: the values a probe typed are in `UiProbeStep.Value`, and the literals a suite asserts are already reachable from the `TestSuiteNotices` sweep. When every typed value is one the suite already carries, say so once in the launch summary — the window shows what a test runner cannot, which is formatting and rejected input. Verified against the run's three launches (fires) and against a launch that types any value absent from the test sources (silent). Skip this if the sentence budget is better spent elsewhere; recommendation 2 is the mechanical half of the same point and stands alone.
