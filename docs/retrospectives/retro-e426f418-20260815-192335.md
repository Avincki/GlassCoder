## What these two reviews are actually about

Neither review found a harness that missed something. Both found a harness that **saw the defect, said so correctly, at the right moment, to the right audience — and then let the sentence expire.**

The process review's own one-line diagnosis is the tell: *"Each was individually correct and individually ignorable, and the agent ignored each one individually."* Five signals fired in this run — the step-1 refusal naming the path, ten `verified nothing (0 tests)` suffixes, the step-11 `XamlNotices` line that is verbatim the code review's headline §1, the step-16 launch result saying *"nothing was typed into it"*, and six critic refutations. Every one was right. None of them outlived the step it was printed on.

That is not a new finding for this repository. `HISTORY.md` 2026-08-09 (last) is titled *"The notice layer was finished and the consequence layer was empty"* and closed it **for suite notices**. 2026-08-15 (later still) closed it **for refused calls** (`AbandonedIntents`). 2026-08-15 (end of day) closed it **for empty solutions**, and drew the generalisation that matters: *"a mechanism keyed to the shape of the run that revealed it goes blind the moment the same fact arrives by a different door."*

Run `e426f418` is the same fact arriving by three more doors, and I checked each one in the source:

- **`XamlNotices` has no consequence layer at all.** It is referenced in exactly two places — `CreateFileTool.cs:205` and `EditFileTool.cs:253` — both appending to one tool observation. It never reaches `RungResult.Noticed` (only `TestSuiteNotices` does, `VerificationLadder.cs:430`), never reaches `RunProgressSentry`, never reaches the completion panel's evidence, never reaches the run record. The one sentence in this entire run that named the code review's §1 defect was printed once at step 11 and was gone by step 12. `TestSuiteNotices` got the full three-place treatment a year of runs argued it into; its sibling, shipped four days ago, got none of it.
- **`EmptySolutions()` (`AgentLoop.cs:937`) is keyed on the wrong fact.** It fires when a solution exists and is empty. This run shipped *no solution*, so it was silent — and the consequence is identical: `dotnet test` at the root has no target, which is why the process review counted ten climbs that verified nothing. The 2026-08-15 fix moved the key from the *event* (a refused `new_solution`) to the *fact* (an empty solution). It stopped one notch short of the fact that actually matters: the root has no build target.
- **The harness told the model that a bare launch answers the refutation.** `AgentLoop.cs:870-875`, the `runtime is null` branch: *"Then call launch_app: it starts the application and reports whether it came up and drew a window, **which is the evidence a refutation like that is asking for**."* The agent did precisely that at step 16 and was refuted at step 17 for precisely that. Since 2026-08-15 the critic prompt asks critics to judge values on a `Window:`/`Probe:` line — so two model-facing strings in the same run now contradict each other, and the run obeyed the wrong one. This is the sixth recorded instance of the class `ModelFacingPromptTests` was built to catch, and the first where the false claim is not stale but *self-inflicted by a later change to a different string*.

  Worse, and structural: the branch that **does** name the probe is `runtime is not null`, which by construction cannot be produced by the first panel. It can only ever be produced by a panel that has a launch to look at — i.e. the second — and at `critiquePanels == MaxCritiquePanels` (`AgentLoop.cs:288-298`) that message is converted into a caveat and never sent. **The harness's single most actionable piece of advice on the one axis that matters is generated on every such run and delivered on none of them.**

## Where the pattern breaks the harness's own instrumentation

The second half is not about the worker at all. It is that the reviewers who diagnose this were given a lossy account of it — the same failure class, one layer out, which is exactly what `[ModelFacing]` and `VerificationVerdict.Describe` were built as invariants against.

- **The completion caveats are truncated out of the retrospective.** `AgentLoop.cs:303-334` assembles the whole consequence layer — critique caveat, red-tree caveat, notice caveat, abandoned intents, empty solutions — joins them with a space onto the final step's `error`, and `Retrospective.cs:709` renders that as `OneLine(step.Error, 300)`. The critique caveat alone is capped at 800 characters and is first in the join. So on any run that finishes over a refutation, **every machine-computed caveat behind it is cut**. This run's process reviewer reconstructed "asked for a solution at step 1, never came back" by hand from two step records — while `AbandonedIntents` had computed exactly that string and put it somewhere the reviewer could not see.
- **The stage-1 diff set stops at the first oversized change.** `RetrospectiveReviewer.cs:698` is `break`, not `continue`: one large diff drops every change after it regardless of size, and the footer reports it as *"N further change(s)"*, which reads as a tail. The code reviewer said out loud that its input was incomplete and named the missing `ProjectReference`. It was right, and the harness had no way to tell it which files were withheld.

## What is a pattern and what is an accident

**Pattern, with four prior closures on record:** a fact the harness computes, states correctly to exactly one audience for exactly one step, and never records as outstanding. Four of the five recommendations below are that pattern in a new door. The repository already knows the shape of the fix — recompute at completion from the workspace, hand it to the panel, put it on the record — and has three working instances of it to copy.

**Pattern, with five prior instances:** a model-facing string that asserts something the harness has since made false. `ModelFacingPromptTests` catches retired denials. It does not catch a *promise* — a sentence that tells the model what evidence will satisfy a gate the harness then fails it on. That is worth adding to the same denial list.

**Accident, and I would treat it as one:** the tautological `Multiply_WithZero_ReturnsZero`. It is the first occurrence of that exact shape (expected literal equals the asserted member's initial value), and the repository's own decision rule from task 70 is *watch on one, fix on two*. I have listed a fourth `TestSuiteNotices` clause at Medium rather than High for that reason — but note that this is now the fourth consecutive desktop run to ship a suite weaker than it looks, in a fourth distinct shape, and task 66's own note ("three questions on one sweep, not three tasks") anticipated exactly this.

**Not a harness defect, and I want to say so plainly:** the `MaxCritiquePanels = 2` ceiling and the advisory concession did what they were designed to do. This repository has paid for gates twice, and the right reading of "completed over a second refutation" is not "add a gate" — it is that the harness spent both of its two panels arguing about *whether a launch happened* when its own tooling could have made the answer moot. `CLAUDE.md §18a` already says the probe shipped as advice and advice is not a mechanism. This run is the fourth data point on that open item, and it sharpens it: **an automatic launch would not have saved this run either**, because the launch it did make was at rest. The open item is not "launch it" but "drive it", and I have deliberately not re-proposed either, since both are recorded as open in `HISTORY.md`.

## One thing that went right and should not be lost

The step-11 `XamlNotices` sentence is the best diagnostic this harness has ever produced: it named the defect, named the mechanism (*"Every rung can pass while the running window uses neither"*), and predicted the exact failure mode that steps 13–17 then walked into, one step after the defect existed and two before any test was written. Nothing in the recommendations below improves that sentence. They are all about making it survive past step 12.
