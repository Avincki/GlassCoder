## What these two reviews say about the harness

Run `ae72c5ad` is not a bad run. Seventeen steps, no file thrash, every file read before it was edited and edited once, two real compile failures each recovered in one to two steps, 100% of the authoring done in two edits. The file-tool work of tasks 45/46/70 and the diagnostic work of task 69 visibly held — none of the old failure shapes appear. What is left is narrower and more specific, and three of the four things worth fixing are **strings the harness itself wrote**.

### Pattern 1 — the verdict vocabulary is precise where it is computed and lossy at every re-telling

`RungResult.Unverified` exists, is documented against runs `a408b61b`/`ca727be3`, is persisted on `StepVerificationRecord.Unverified` (`StepRecord.cs:106`), is honoured by the loop's logger (`AgentLoop.cs:632`) and by the model-facing message (`:647`). And `Retrospective.cs:386` — the transcript extract that stage 2 and the human read — renders `verification: {Passed ? "passed" : "FAILED"} at {HighestRungReached}` and consults neither `Unverified` nor `Noticed`. That single line is why both of your reviewers concluded the harness "reported a test stage as passing" with no tests in existence. The rung told the truth; the retelling did not.

This is the third instance of the same shape, all recorded in `HISTORY.md`: 2026-08-09's model-facing header saying "passed" while the logger said `passed (0 tests)`; 2026-08-11's `accepted 1/3` whose word and ratio disagreed. Each was fixed at the one surface that had it. **Every new renderer re-derives the verdict from `Passed` alone, and there is no test that says it must not.** The per-surface fix is right; the missing thing is the invariant.

### Pattern 2 — the harness has learned to stop *saying* satisfiable things and not yet to stop *prescribing* them

2026-08-11 caught the orphan-type notice prescribing its own one-line shortcut and removed the remedy from the sentence. The refutation-recovery message is the same shape one level up. `AgentLoop.cs:791-796` tells a refuted model: *"Then call launch_app: it starts the application and reports whether it came up and drew a window, which is the evidence a refutation like that is asking for."*

At step 15 the model did exactly that — and the launch had already happened at step 12, its result was already in the evidence the critics had just refuted, and the returned string came back byte-identical, hedge included. The harness prescribed a move that was already spent. The process reviewer read this as the agent failing to notice a repeat; it is at least as much the harness naming the repeat as the fix. The `evidence` critic then flipped accept→refute, correctly registering step 15 as a non-event.

### Pattern 3 — the runtime rung tops out at "a window drew", and the critics are right about it

Task 71 shipped `launch_app` knowing this ("deliberately not a screenshot") and it was a genuine advance. Three runs on, the refutation *"runtime evidence only proves a window drew"* is still correct and still unanswerable from inside the loop. Every defect in the code review — the dead `ErrorMessage` block, the stranded value on backspace, `37.77777777777778` — is a thirty-second-of-typing defect that no static rung can reach. The harness now has `IWindowPresence` reading `Process.MainWindowHandle`, so the seam that would take a bounded UI-Automation probe already exists; this is no longer a research question, it is the next rung.

### Pattern 4 — the one thing the harness measures obsessively, it does not measure here

`RunMetrics` carries tool-call validity, edits-to-green, recovery rate, cascade ratio, retrieval counters — and **not one field about the critique**. "Completed over a unanimous refutation" has now happened in `216360bf`, `d5edbc59` and `ae72c5ad`; `StepCritiqueRecord.EvidenceUnchanged` makes it greppable per-transcript, and `AgentLoop.cs:279` writes a caveat onto the run record, but nothing counts it across runs. By this repository's own stated standard — *"greppable across runs rather than reconstructed from two transcripts by hand"* — that is the number missing.

### One accident, and one thing worth not fixing

Step 5's XAML-before-code-behind ordering is a sequencing slip, and `xaml-handler-declared-notice` already sits unticked in the 2026-08-11 work order; I have not re-proposed it. The `XamlNotices` clip warning fired on a layout that demonstrably does not clip (≈105px of content in ≈180px usable) — worth one cheap regression case, not a redesign.

### And the human oracle was asked blind

The operator rated 5/5 minutes after the loop wrote *"Completed despite a second critique refutation"* into the run record. Task 65's argument for the strip is that it asks at the one moment a person can answer honestly. It asks without telling them what the run's own machinery had just concluded — which is the cheapest possible way to lose the harness's only screen oracle.

- [x] **High** `launch-app-probe` - launch_app gains a bounded UI-Automation probe
      The missing rung. `LaunchAppTool` (src/GlassCoder.Tools/Build/LaunchAppTool.cs) already resolves the app's own executable and already has `IWindowPresence` reading `Process.MainWindowHandle` — the seam a probe needs is built. Add an optional `probe` argument: a short, capped list of steps against named automation elements (set text on a named box, invoke a named button, read back named elements' text), executed after `ReadySignalled`, each step reporting what it saw. Feed the readback into `RuntimeEvidence.Record` so it reaches the completion panel, and make the tool's closing hedge conditional — 'whether the window is right still needs eyes on it' should stop being said once the tool has read text out of the window. Keep task 71's contract: failures are observations, the timeout still kills the tree, and a probe that finds no element by that name says so rather than throwing. Deliberately not pixels; this is the text-level half. Verification: re-run the temperature-converter goal and grep the transcript for an observation reporting the Fahrenheit box's content after `100` was typed into Celsius; the 'runtime evidence only proves a window drew' refutation should either disappear or come back naming rendering specifically.
- [x] **High** `refutation-recovery-not-relaunch` - Stop prescribing launch_app when the run has already launched
      `AgentLoop.cs:791-796` — the `screen` string inside `CritiqueCompletionAsync` — tells a refuted model to call `launch_app` as 'the evidence a refutation like that is asking for'. In run `ae72c5ad` the launch had already happened at step 12 and its result was inside the very evidence the panel had just refuted, so step 15 re-issued the identical call and got the identical string back. Condition the sentence on `_runtime?.Latest`: when runtime evidence already exists for this run and the panel refuted anyway, say so and name what is still absent (what the window shows for a given input) instead of prescribing the launch again. This is the same correction 2026-08-11 applied to the orphan-type notice — a remedy the harness can see satisfied is a remedy worth one step and nothing else. Verification: two tests in `GlassCoder.Core.Tests` — with `RuntimeEvidence` empty the refutation message still names `launch_app`; with it populated the message does not, and names the gap instead.
- [x] **High** `advisory-authority-names-what-ran` - The advisory concession must not cite a rung that verified nothing
      `AgentLoop.cs:803-806`, the non-gating branch: *'the compiler and test results above remain the authority, and you may finish as-is if you disagree.'* In this run the test result above was a UnitTests rung that ran zero tests — `report.Unverified` was true and the loop's own message three hundred lines earlier already said so. The sentence pointed the model at the weakest evidence in the run and offered it the exit, and the model took it. Make the clause name only what actually ran: when the last report is `Unverified`, say the compiler is the authority and that no test verified this change; when the tests rung was skipped entirely, do not mention tests at all. Same edit, same reasoning as 2026-08-09's 'the model-facing verdict stops saying passed over a rung that verified nothing' — this is the one remaining place that still does. Verification: a test asserting the concession text for an `Unverified` report contains no claim of test authority, and the gating-mode branch is untouched.
- [x] **High** `retro-transcript-says-unverified` - The retrospective transcript renders Unverified and Noticed
      `src/GlassCoder.Core/Verification/Retrospective.cs:386` writes `- verification: {(verification.Passed ? "passed" : "FAILED")} at {rung}` and reads neither `StepVerificationRecord.Unverified` nor `.Noticed`, both of which are persisted on that same record precisely so a run can be grepped rather than reconstructed (`StepRecord.cs:106-110`). That is why both reviewers of this run read 'verification: passed at UnitTests' and concluded the harness passes a test gate with no tests in existence — the rung was honest, the extract was not, and the extract is what stage 2 and the human read. Render `passed (0 tests) at UnitTests` and append the notice marker, using the same words `AgentLoop.cs:632` already uses so the two cannot drift. Worth adding the invariant while you are there: a test that every surface rendering a verification verdict distinguishes the unverified case — this is the third surface to have had this bug (2026-08-09's model-facing header, 2026-08-11's `accepted 1/3`, this one). Verification: `RetrospectiveTests` over a step record with `Unverified = true` produces a line that does not read as a clean pass.
- [x] **Medium** `repeat-launch-is-marked-reused` - A repeated launch with nothing changed is marked reused
      `RuntimeEvidence` (LaunchAppTool.cs:261-277) overwrites `_latest[runId]` silently, so step 15's launch was indistinguishable from step 12's — same call, same result string, no signal that it was a repeat. `BuildTool.cs:101-110` already has the pattern: an unchanged target returns the previous answer with `reused: true`, and since 2026-08-11 `RunProgressSentry` counts that flag and nudges on the second consecutive one. Give `launch_app` the same treatment — same project, no applied change in the change log since the previous launch, return the previous result marked reused and say a launch of an unchanged tree cannot show anything new. Verification: two launches with nothing applied in between; the second observation carries `reused` and the sentry sees it, while a launch after an applied change runs for real.
- [x] **Medium** `critique-outcomes-in-metrics` - Record critique outcomes in metrics.jsonl
      `RunMetrics` (src/GlassCoder.Core/Metrics/RunMetrics.cs) has fields for tool-call validity, edits-to-green, recovery, cascade and retrieval, and nothing at all about the critique. Runs `216360bf`, `d5edbc59` and `ae72c5ad` each completed over a refutation; the transcript records it per-run (`AgentLoop.cs:279`, `StepCritiqueRecord.EvidenceUnchanged`) and no reader can count it. Add four counters read at run end: `CompletionCritiquePanels`, `CompletionCritiqueRefusals`, `CompletedOverRefutation`, and `UnverifiedVerifications` (rungs that ran and verified nothing). They cost nothing on the wire, they make the pattern these two reviews describe visible as a number rather than as three hand-read transcripts, and they are the metric that would tell you whether the probe above actually changed anything. Verification: a scripted run that finishes over a second refutation writes `completedOverRefutation: true` into `metrics.jsonl`.

The rating is the harness's only screen oracle and it is currently the only judge in the run that is not told what the other judges concluded. Verification: a WPF test where a run ending with a caveat renders it in the strip and a clean run renders no line; the recording path and the Skip button are unchanged.
- [ ] **Medium** `launch-app-directory-names-the-project` - launch_app names the project when a directory resolves to one
      `LaunchAppTool.cs:100-107` refuses a directory with 'Pass the .csproj of the executable project - list_projects names them.' Step 10 hit exactly that and step 11 spent a whole step on `list_projects` to learn a path the build gate had echoed back at steps 1, 5 and 7. `ProjectLocator` (src/GlassCoder.Tools/Verification/ProjectLocator.cs) already resolves owning-project / sole-project for the ladder. Same principle as task 44's MSB1003 work — a refusal that names the single thing it can see costs one step less than one that describes a shape. Verification: a test asserting the refusal over a directory containing one .csproj quotes that path, and that an ambiguous directory still points at `list_projects`.
- [ ] **Medium** `build-warning-count-names-its-oracle` - The build summary says which warnings it is counting
      `BuildTool.cs:190` says 'Build succeeded (N warnings)'. Three steps after a ladder climb that reported 6 warnings, step 9's `build` reported 0 — and both were true of different questions. The 6 came from the Analyzers rung's in-memory Roslyn compile (`VerificationLadder.cs:328`), which reports the full analyzer/IDE set every time; the 0 came from MSBuild, which re-emits nothing for projects it did not recompile. Two organs, two numbers, neither saying which it is, and the model reconciled nothing (its step-8 narration says 'just a warning', singular). Label the source in both sentences — 'N compiler warnings from this build' against the analyzer rung's existing 'Analyzer warnings (informational)' — and add one clause when a build succeeds with zero warnings and the same target has built before: an incremental build does not re-report warnings from files it did not recompile. Verification: a `FakeCommandExecutor` test over two consecutive builds asserting the caveat on the second and the source label on both.
- [ ] **Low** `build-cache-key-is-the-resolved-target` - Key the build cache on the resolved target, not the caller's string
      `BuildCache` keys on `verdict.RelativePath` plus `allowRestore`. The ladder builds what `ProjectLocator` resolved (a .csproj); the model calls `build` with whatever it typed (often the directory). Same MSBuild work, same answer, different key, guaranteed miss — which is most likely why step 9 ran a fresh build seconds after step 7's ladder had built the same project, and it is the shape `HISTORY.md` (2026-08-09, last) recorded as 'a correct miss' without asking whether the two strings named the same target. Normalise both writes and reads through `ProjectLocator` before hashing. Conservative direction is preserved: a normalisation that fails falls back to the raw string, so a missed hit stays possible and a stale hit does not. Verification: the cache already logs its key at Information on miss — grep the next run's log for a miss whose key differs only in shape from a key it holds; then a unit test where the ladder fills the cache with a .csproj target and a `build` call on that project's directory is served.
- [ ] **Low** `clip-notice-regression-case` - Give the clip notice a known false positive to argue against

Add the temperature-converter XAML as an asserted silent case and re-derive the threshold against it and run `ea9a1f66`'s dialog (the case it was built from), so the two are separated by something dimensional rather than by a count.
