## What these two reviews say about the harness

I read `WORKPLAN.md`, `HISTORY.md`, and then the run's own log (`%LocalAppData%\GlassCoder\logs\glasscoder-20260809.jsonl`), because several of the process review's claims are checkable and two of them turn out to be about the harness rather than the agent.

### The pattern: the notice layer is finished and the consequence layer is empty

Task 66 built exactly the check this run needed. It fired, correctly, with the right wording, twice — at step 16 on the ladder's UnitTests rung and at step 20 on `run_tests`. It also reached the critics: the step-23 record contains the notice text, so the completion panel read *"the tests exercise `MultiplyViewModel`, which no non-test source references"* and accepted 2/3 anyway. Task 66's own acceptance criterion ("it has to reach the critics") is met. The defect it was written to catch shipped regardless.

That is the finding. It is not "the notice needs to reach further." Every mechanism this repository has built under the principle *the information has to be in the message the model is already reading* worked in this run. What none of them has is a **state the run carries**. `AgentLoop.cs:618` composes the model-facing verdict as `"Automatic verification of your change passed (reached UnitTests)"` — while `AgentLoop.cs:609` logs the same report as `"passed (0 tests)"` for the operator. Two renderings of one report, and the model gets the flatter one. `VerificationLadder.cs:349` concatenates `tests.Notices` into a summary string; nothing structured survives, so `RunProgressSentry` — which already owns exactly the right shape, `ChallengeCompletion()` once then `CompletionCaveat()` in the record — cannot see a notice at all. `RungResult.Unverified` exists and is likewise invisible to the sentry.

This is the same asymmetry HISTORY records twice from the other side (`5c071f37`, `a408b61b`: gates that would not concede). The correct answer here is not a gate — this repository has paid for those. It is the mechanism already in the file: **one challenge, then let it through with a caveat in the record.** Four consecutive `Unverified` rungs and two unanswered notices should have produced one sentence the model had to answer, and a run record that says "completed over an unanswered notice." Today they produce neither.

### The evidence boundary leaks, and one prompt has drifted

`AgentLoop.cs:730-731` appends the worker's own completion summary to the `evidence` string, and `CriticPanel.cs:383` renders that whole string under the heading `Evidence:` — while the system prompt one line up tells critics to *"Judge only the change and evidence in front of you."* The process review's charge that two votes treated the agent's claim as evidence is not a model failure; the harness put it there and labelled it that way.

Separately, `CriticPanel.cs:374-376` still tells every critic *"It cannot launch the application, interact with a UI, or capture a screen."* Task 71 shipped `launch_app`, the run used it at step 21, and `AgentLoop.cs:705-708` appended the result to the very evidence block those critics were reading. The prompt asserts a limitation the harness removed three tasks ago. HISTORY records this shape twice already (the system prompt still ordering build/run_tests after the ladder began verifying applied changes; `Agent.SystemPrompt` in the operator's settings shadowing the code default, "the second time"). Prompts are the one artifact here with no test tying them to the capability they describe.

### Raw bytes reach the model on the one path task 15 does not cover

Step 9's Compile-rung failure summary, verbatim from the log, is `[?25l[1F\ncsproj\n[?25h[?25l[2F\n[120G[6D(0.1s)…` — 21 escape sequences and no diagnostic. The model was told verification FAILED and given nothing to act on; it recovered from its own knowledge of WPF. The same sequences ride every `dotnet_project` observation (`DotnetProjectTool.cs:240`, `Trim(result.CombinedOutput)`). The .NET CLI's progress reporter writes CSI codes even into a redirected pipe, and `ProcessRunner.Append` (`ProcessRunner.cs:97-102`) is the single place they all pass through. Task 15's rule — never hand raw compiler output to the model — holds everywhere the parser succeeds and is bypassed by the "print the raw tail when the parser types nothing" fallback added on 2026-08-06.

### Two corrections to the process review

**Step 2 was not a misread.** The refusal (task 73) ends: *"The workspace's writable set does not reach the root, so there is nowhere a solution would work here: skip it."* The agent did what it was told. Code-review finding 5 — no `.sln`, no single build/test entry point — is a consequence of `WritablePaths: ["src","tests"]`, not of an agent that stopped one token short. `ProjectLocator`'s "root solution" branch can never fire under the shipped configuration.

**Step 22 was not blind by accident.** `list_changes` is a ledger of writes the agent recorded; the run read it as a survey of the tree. The leaked `MultiplyApp_2e3zldbb_wpftmp.csproj` is why step 18 got `MSB1011: this folder contains more than one project or solution file` — which `BuildTool` passes through raw, having a special case for MSB1003 (`BuildTool.cs:198`) and none for MSB1011.

### What the run says the harness got right

Every message this run needed existed and was well written. The task-73 refusal named its consequence rather than its rule. The task-70 memo told the model at step 12 that the file had not changed. Task 66's notice was precise enough to be actionable. `launch_app` was scrupulous about the difference between "it drew a window" and "the window is right." The gap is uniformly one layer down from the prose: nothing the harness said had a place to be *recorded as outstanding*.
