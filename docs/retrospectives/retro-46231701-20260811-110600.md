## What these two reviews are really about

Strip the WPF specifics and both reviews describe the same run: the harness told the agent something true four separate times, and each time the agent did the cheapest thing that made the sentence stop being true. That is not a model failure and it is not four unrelated incidents — it is one property of how GlassCoder's signals are built.

### 1. The pattern: a signal whose satisfaction condition is cheaper than the property it stands for

**The orphan-type notice is the clearest case, and the harness wrote the escape hatch itself.** Task 66's clause two fired at step 16 and again at step 19: *"the tests exercise `MultiplicationService`, which no non-test source references."* Read `src/GlassCoder.Tools/Verification/TestSuiteNotices.cs:126-128` — the notice ends **"If the product duplicates that logic rather than calling it, have it call this instead."** At steps 20–21 the agent re-read `MainWindow.xaml.cs`, found the one line that was `firstNumber * secondNumber`, and replaced it with `MultiplicationService.Multiply(...)`. It did exactly what the harness instructed. And that single line moved `MultiplicationService` into `Survey.ProductIdentifiers`, which silences clause two; clause one was already silent (the tests name a product type); clause three needs a *computed* expected value and these are literals. **After step 21 the whole sweep goes quiet on a suite that tests `a * b` while every line the agent authored — parse, format, the invalid-input branch — remains unreachable by any test.** The notice's remedy is detectable by the notice's own detector, so satisfying it costs one line and buys nothing.

`RunProgressSentry.ObserveVerification` then does its job perfectly: `_noticeOutstanding = noticed` (`RunProgressSentry.cs:185`), the next climb had nothing to say, the notice cleared, no caveat reached the run record. The 2026-08-09 decision — *"a notice is cleared by the next climb that has nothing to say"* — is right against the failure it was written for (a notice outvoted by later rungs) and wrong against this one (a notice discharged by a change to the thing it was measuring).

**The same shape appears at step 0.** Task 73's `RefuseSolutionBelowTheRoot` refused `src/MultiplyApp/solution.slnx`. It worked exactly as designed. But the live shape is `WritablePaths: ["src","tests"]` (`config/phase1.json:23`), so the root is not writable, so task 73's own hint correctly says *skip the solution* — and the agent concluded it needed none. The refusal can never fire again, so nothing downstream noticed. **Under the shipped writable set, "no solution at all" is the only reachable state**, and `ProjectLocator`'s root-solution branch is dead code — which HISTORY already recorded on 2026-08-09 as a curiosity. This run is the same fact arriving as a deliverable gap: `dotnet test` from the root has no target.

**And the third: the notice that talks the agent out of the tool.** `XamlNotices.cs:109-110` fired on step 9's XAML write and ended *"Compile and tests cannot see clipping; **only the operator's Run app can**."* Task 71 shipped `launch_app` in the loop. The app was never launched in 26 steps; the evidence critic dissented at step 25 for want of exactly that; the code review found the misaligned margin and the fixed `Width="150"` that a launch would have surfaced.

### 2. Stale prompt text is now the harness's most reproducible defect class

HISTORY 2026-08-09 fixed the critic prompt and called it *"third recorded instance of a prompt asserting a limitation a later task removed."* There are three more live, all denying `launch_app`:

- `src/GlassCoder.Tools/FileSystem/XamlNotices.cs:110` — *"only the operator's Run app can"* (this fired in this run)
- `src/GlassCoder.Core/Agent/AgentLoop.cs:786-789` — the refutation recovery instruction, same sentence
- `src/GlassCoder.Tools/Registry/ToolRegistry.cs:185` — *"The application is launched by the operator's Run app button, **never by you**"* — flatly false since task 71

Six instances is not carelessness, it is a missing mechanism. Every one of these was written as a scar from a specific run and none of them is anchored to the capability it asserts.

### 3. The instrument the harness learns through is itself lossy

The process reviewer flagged the run digest as *"internally inconsistent about that vote: the header says 2/3 accepted, the line below says 1/3."* They were reading `src/GlassCoder.Core/Verification/Retrospective.cs:391-393`, which renders `- critique: accepted {RefutingVotes}/{RespondingVotes}` → **`accepted 1/3`**. The word and the ratio disagree. Worse, the vote list two lines down (`:395-399`) prints each critic's lens and reason and **drops `vote.Refuted`**, so a reader cannot tell which lens dissented. `TranscriptViewModel.cs:50` gets this right (`critic.refute 1/3`); the retrospective, whose only purpose is to be read by a reviewer, does not — and it misled one.

### 4. Task 74 made the redundant step cheap; it did not make it stop

`BuildTool.cs:107` tells the model *"Build succeeded (unchanged since the last build, so this result was reused)."* Steps 18, 22 and 23 spent themselves anyway. Four of 26 steps re-confirming the one axis never in doubt, in a run where the axis that *was* doubted got nothing — which is verbatim task 74's own opening paragraph, unfixed by task 74. The harness's own repeated lesson (2026-08-09: *"Every message this harness has built worked. None of them had anywhere to be recorded as outstanding"*) applies here and has not been applied.

### What is accident, and what earned its keep

Steps 10–12 (invented edit anchor) look like the fourth recurrence of the XAML-before-handler class — HISTORY records it at steps 9-12 in `122e11c6` and `d5edbc59`, and it is steps 9-13 here. But task 70 clearly converted: the recovery was three steps instead of four, it ended in a targeted edit rather than the whole-file rewrite that gave `d5edbc59` its nine stray usings, and step 12's `FileReadMemo` clause — *"has not changed since you last read it in this run"* — is what ended the search. The remaining cost is the ordering itself, which the harness has never addressed because it twice, correctly, refused to build a *refusing* handler pre-check. `XamlNotices` is the shape that is allowed.

Genuinely working and worth not disturbing: the TFM widen at step 3, the zero-test honesty (*"exited cleanly but ran 0 tests — nothing was verified"*), 100% tool-call validity, no manufactured passes, and the below-root refusal doing precisely what it says. The code review's culture-handling and threading findings are the model getting the hard part right in one pass with no signal to help it — nothing for the harness to do there.

### The one-line version

Every mechanism in this harness is a sentence. The run's failure mode is that a sentence can be made to stop being true more cheaply than the thing it describes can be made true — and in the orphan-notice case, the harness supplied the cheap route in the sentence itself. The fix is not more sentences; it is (a) not naming a remedy your own detector can see, (b) recording *how* a signal was cleared rather than only *that* it was, and (c) a build-time guard so a model-facing string cannot go on denying a capability that shipped.
