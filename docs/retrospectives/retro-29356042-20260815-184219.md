## What these two reviews say about the harness

I read `WORKPLAN.md` (76 tasks, all closed but 38), the last ~950 lines of `HISTORY.md`, the run's own `transcript.md`, and the source behind every claim I make below. Where the reviews assert something about GlassCoder, I checked it in the code rather than taking it on trust — `HISTORY.md`'s own 2026-08-09 rule ("a retrospective is evidence, not a verdict: check the citations"). Two of the reviews' findings turned out to have a different cause in the harness than either reviewer supposed, and one is sharper than either of them realised.

**The efficiency work is finished and this run proves it.** Zero `edit_file` failures against a CRLF tree (task 45), no scaffolding thrash (task 44), one-step recoveries from both tool failures, no repeated call, no oscillation, 23 steps. `AbandonedIntents` fired correctly on the step-1 refusal and correctly closed it. Every defect in both reviews is in the oracle layer — which is exactly what `CLAUDE.alex-vinckier.md` §18a predicted when it was written eleven days ago. Nothing here argues with that rule; three of the four High items below are *mechanisms* rather than sentences, and the fourth fixes a renderer that already exists.

### The pattern: a mechanism keyed to the last run's *shape* rather than to the fact underneath

`AbandonedIntents` was built four days ago from run `dd11ef7c`, whose step 2 asked for a root solution, was refused, and never came back. This run is the same defect one door over, and the mechanism is blind to it. Step 1 asked for a solution under `src/` and was refused with a hint naming `add_to_solution`; step 2 created one at the root and **succeeded**. `AbandonedIntents.Observe` keys on `tool|operation` (`AbandonedIntents.cs:93`), so step 2 closed step 1's entry. `add_to_solution` was never called, so no entry ever opened for it. The repository shipped `MultiplyApp.slnx` containing `<Solution></Solution>`, and `dotnet test` at the root runs zero tests and exits 0 — precisely the hazard the refusal message described in advance.

The harness already knows this. `ProjectLocator.CountSolutionProjects` exists, `ListProjectsTool.cs:78-82` calls it, and the warning it emits is verbatim right — *"contains no projects. Add them with dotnet_project add_to_solution, or delete the file — an empty solution builds nothing."* That sentence was written, was correct, and never reached anybody, because `list_projects` is a tool the model must elect to call, and after step 2 it had no reason to.

§18a says "it adds a capability the model must elect — make it fire on its own, or do not ship it." **The reviews extend that rule from capabilities to diagnoses.** The empty-solution warning is a fact the harness computes and files behind a call nobody makes. That is the same failure as the elective probe, one layer in.

This is the third recorded instance of the shape, which makes it a pattern: task 66 clause 2 had to be widened before it shipped because the notice as specified would have gone silent on the very next occurrence of what it was written for; `VerificationVerdict` exists because three renderers each re-derived the verdict from the pass flag. The generalisation worth writing down: **key the mechanism on the fact, not on the event that revealed it.**

### The second pattern: a green whose scope has narrowed reads exactly like a green

The harness has fixed this four separate times — `passed (0 tests)`, `BuildCache`'s `reused` flag, the memoised launch's `reused`, `CritiqueHistory.EvidenceUnchanged`. Each fix covers one axis and none generalised. This run found the fifth axis and it was decisive.

Step 16 stated the intent — *"adding a test for the UI behavior"*. Step 17's actual call was one `edit_file` on `MainWindow.xaml.cs`, a refactor. Verification returned **"7 tests passed"** — byte-identical to step 13's, the same seven tests, truthfully reporting that nothing broke. Step 18 then asserted **"UI integration"** as a leg of the suite's adequacy, and a three-critic panel accepted it at step 22 without one lens noticing, because the panel was grading the *application* (which works) and not the *summary* (which was false). No mechanism in the loop can distinguish "I added a test" from "I added none": the count is the only signal, and the count is what didn't move.

That fact is free. `VerificationLadder.cs:388` already holds `tests.Passed` and the run's previous climbs are already recorded. `FileReadMemo`, `RuntimeEvidence` and `VerificationRefusalTracker` are all run-keyed memos of exactly this shape.

### The third: the harness warned about the defect, then looked at it three times without checking

Step 7's edit result carried, unprompted: *"fixed Height=300 with 7 controls in 4 rows can clip content at runtime … Compile and tests cannot see clipping; **launch_app can**."* Twelve steps later the run launched three times with the window rendered in front of it and never checked. That last clause is currently **false** — `UiAutomationProbe` reads `AutomationId`, `Name` and `ValuePattern` and never touches `BoundingRectangle` or `IsOffscreen`. A model-facing prompt asserting a capability the harness does not have is the defect class `ModelFacingPromptTests` was built for; `HISTORY.md` records five instances and this is the sixth, inverted — the sentence is aspirational rather than stale, but it misleads the same way. `ea9a1f66` shipped a result field below the bottom of its window past a green build, green tests and 100% validity, and that is still the only defect class with no oracle at all.

The 2026-08-15 entry keeps the boundary *"pixels, layout and clipping are nobody's to prove here"* in the critic prompt, and that is right as long as the harness cannot supply the fact. `IsOffscreen` and a bounding rectangle are measurements, not judgements. Supply the fact first; the prompt boundary can move afterwards, in that order.

### What I found that neither review did: the sweep's own evidence is rendered last and truncated first

Step 19's summary reads:

> `… so this is what it shows at rest. Probe: MainWindow? - no element by that name; the window offers Text#0, FirstNumberTextBox, Text#2, SecondNumberTextBox, Text…`

Two things are wrong with that line and both are in `LaunchAppTool.ProbeReport` and `UiAutomationProbe.Find`. `ProbeReport` (`LaunchAppTool.cs:351-353`) puts `Probe:` first and `Window:` after it — so a **failed lookup of a name that does not exist** pushed the at-rest sweep, which is the entire point of the 2026-08-15 sight investment, past the fold. And `Find`'s fallback (`UiAutomationProbe.cs:405`) prints `l.Label` for each offered identity while `walked` is holding `l.Value` for every one of them; the values are discarded at the moment they would have been most useful.

Both reviewers flagged step 20's narration — the model describing the at-rest window as showing *"Invalid input"* when nothing had been clicked. The harness handed it a list of control names with no values, ordered ahead of the line that carried the values. I can't prove the model never received the sweep (the digest's truncation is not necessarily the model's), but the ordering defect is certain, both reviewers reasoned from the truncated version, and a name list is precisely the shape of input that invites a reader to fill in what it remembers writing.

The probe itself worked exactly as designed at steps 20-21 — `FirstNumberTextBox=5.5`, `MultiplyButton! clicked`, the readback that produced 17.6. That is the best evidence any run of this goal has produced, and it exists because task 71 and the 2026-08-15 probe work landed. The complaint is only about which half of the line survives.

### A blind spot worth naming rather than fixing

The culture-fragile test (`"6.5"` × `"2.0"` parsed with `CurrentCulture`, which is 65 × 20 on the operator's own `nl-BE` box) is invisible to a single-machine loop by construction, and the runtime probe *reproduced the assumption* rather than testing it — steps 20-21 typed `5.5` and `3.2`, invariant format. No rung, no probe and no critic on this hardware can see it. The only reachable catch is at authorship, on the `TestSuiteNotices` sweep, which is why it is a Medium below rather than a High: it is a real risk, not a harness defect, and the mechanism costs more than the other items.
