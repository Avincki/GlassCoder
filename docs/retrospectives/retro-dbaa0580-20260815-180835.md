## What the two reviews actually establish

I checked both against run `dbaa0580`'s own transcript and metrics before accepting anything. Three of the process review's findings changed shape under checking, and one new defect fell out that neither reviewer could see.

### The harness broke its own build and then blamed the code

Step 3 scaffolded the WPF project. Its markup pass failed (`error MSB4018:` — with an **empty message**), and the SDK left `TemperatureConverterApp_4lgcpo3h_wpftmp.csproj` behind in `src/TemperatureConverterApp/`. Step 4 then called `build(path: "src/TemperatureConverterApp")` and got, verbatim from the transcript:

> `error MSB1011: Specify which project or solution file to use because this folder contains more than one project or solution file.`

There was never a second project. The harness's own failed build put it there, and nothing swept it. Steps 5–7 then read App.xaml, MainWindow.xaml and MainWindow.xaml.cs — 44 lines across three steps — hunting for a compile error that did not exist in any file. The 31 KB residue, stuffed with absolute paths from this machine, shipped in the deliverable.

This is the sharpest thing in the run and it is not a message problem. `CLAUDE.md §18a` opens with "the reliability work is done; what is left is sight." This says otherwise: the harness damaged its workspace, reported the damage to the model as a compile error with no remedy, and cost three of twenty steps. `build` already gives MSB1003 a named remedy at `BuildTool.cs:200-218` — bought with run `e8f9186a`'s wasted steps — and gives MSB1011, the identical class of problem, nothing.

### The harness held the correct refutation and delivered it eleven seconds too late

The decisive finding. Same critic role, same three lenses, same finished work:

- **19:22:27 — completion panel: 3/3 accept.** All three cite build and tests. None mentions a launch.
- **19:22:38 — post-run review: 3/3 refute.** All three refute on *exactly* the missing launch: *"there is no evidence of the application being launched to verify the automatic update functionality"*; *"lacks a launch verification showing the application's runtime behavior."*

The critic prompt is not the problem — `CriticPanel.cs:417` already says the absence of a launch, for a goal about a running application, is grounds to refute. The prompt works. It works in `RunReviewer` and not in the completion panel, and the one provable difference is that `AgentLoop.CritiqueCompletionAsync` (`:777-781`) appends runtime evidence when there is some and says **nothing at all** when there is none. The completion panel has to infer an absence from a missing line; the post-run reviewer is handed a whole-run framing that makes the absence visible. So the harness ran the better-informed panel at the only moment its verdict could change nothing.

That is the pattern, not the accident. The oracle layer is now good enough to be right. It is wired to the wrong moment.

### Elective capabilities do not fire — now three occurrences

`§18a` already states this rule, and cites `launch_app`'s **probe** as the example: *"an optional parameter on the one axis nothing else can see is advice, and advice is not a mechanism."* Run `dbaa0580` is the same rule one level up: `launch_app` **itself** is elective, and across 20 steps of a desktop goal it was never called. Run `dd11ef7c` did not launch either. Run `457867c7` launched only because a refutation forced it. The sweep, the probe, the positional addressing, the `Window:` line, the critic clause — the whole 2026-08-15 investment is gated behind a call the model does not make unless something makes it.

### "A signal cheaper to satisfy than the thing it stands for" — recurring, and this time the model said so out loud

The 2026-08-11 finding repeats. `ChallengeNotice()` worked exactly as designed and deserves the credit the process review gives the agent: step 15 was a bare completion attempt, the challenge fired, and step 16 opens with the model agreeing. Its own words:

> "The verification notice correctly observed that the tests compute the conversion formulas directly rather than calling the actual application code… **they don't exercise the WPF UI code or the text change event handlers.**"

It then extracted the formulas, tested those, cleared the notice at step 18, and stopped — leaving the handlers, which is where 100% of the code review's defects live. The model named the untested surface in the same breath as it declined to test it. The notice asked one narrow question and got exactly that question answered. Nothing in the run re-asked *what should be tested* after step 16 created the first testable seam.

### The process review was reading a lossy instrument

Its claim that step 4 "returned strictly less information than step 3" is wrong at the model-facing layer and right at the digest layer. The model received the full observation including `data.diagnostics` naming MSB1011. `Retrospective.RenderStep` (`:386-410`) renders only `Summary`, `Error` and `Hint` — never `ToolCallRecord.Result`, which is the serialized observation the model actually read (`AgentLoop.cs:1110`). `Result` is model-facing and carries no `[ModelFacing]` marker, so the invariant written on 2026-08-15 to stop exactly this does not cover it. This is the fifth surface to drop a model-facing fact, and it is the one every future process reviewer reads.

### One defect neither reviewer could see

`BuildTool` never sets `outcomeOk: false`. `RunTestsTool` does (`:253`), `LaunchAppTool` does (`:308`), `DotnetProjectTool` does in three places — `BuildTool` does not, in any branch. `IToolObservation.OutcomeOk`'s own doc comment names this case: *"a failed `dotnet` operation is `Ok`… but the outcome is a failure, and the progress machinery must see it as one."* Run `dbaa0580` recorded three build failures; `RunProgressSentry` and `AbandonedIntents` saw three successes.

### The recurring structural shape

Four separate instances in one run of *two organs holding two views of one fact*: `build` versus the Compile rung on diagnostic detail (task 69's shape, still open in a different branch); `AgentLoop.DescribeChanges` (per-edit journey) versus `RunReviewer.DescribeChanges` (net diff per file, carrying run `ff74b2d4`'s lesson — only one of them does); `outcomeOk` set by three tools and not the fourth; the digest versus what the model read. `VerificationVerdict.Describe` and `[ModelFacing]` are the right answer to this shape and are under-applied.

### What was an accident

The MSB4018 markup failure itself is environmental, not a harness defect — though what the harness *said* about it (`error MSB4018:` with no message) is. The TFM widening at step 12 was announced correctly and worked as designed; the process review calls it silent and it is not (`DotnetProjectTool.cs:705-710`). And run `dbaa0580` was genuinely economical: 20 steps, 6 edits, no thrash, no refusal loop, 100% tool-call validity. The reliability layer held. The sight layer had one capability, and nothing made it fire.

- [x] **High** `build-reports-a-failed-build-as-a-failed-outcome` - build must set outcomeOk false when the build fails
      `BuildTool.BuildAsync` never passes `outcomeOk: false` — not in the MSB1003 branch (`BuildTool.cs:214`), the unparseable-output branch (`:227`), or the ordinary failure branch (`:236`). `RunTestsTool.cs:253`, `LaunchAppTool.cs:308` and `DotnetProjectTool.cs:259,672,698` all set it correctly, and `IToolObservation.OutcomeOk`'s own doc comment names a failed dotnet command as the case it exists for. Consequence: run `dbaa0580` recorded `buildFailures: 3` while `RunProgressSentry.FailureKey` and `AbandonedIntents.Observe` saw three successes — a run that fails the same build ten times is invisible to both, and a build that failed and was never made to pass never opens an abandoned intent. Fix: pass `outcomeOk: payload.Succeeded` on every non-success return. Verification: a unit test asserting a failed build's observation carries `outcomeOk: false` on the wire, and an invariant test over `GlassCoder.Tools` asserting that every tool relaying a process exit code derives `outcomeOk` from it — the same source-scan shape as `ModelFacingPromptTests`.
- [x] **High** `sweep-wpftmp-residue-after-a-build` - Delete the SDK's *_wpftmp.csproj residue a failed build leaves behind
      Step 3's failed WPF markup pass left `src/TemperatureConverterApp/TemperatureConverterApp_4lgcpo3h_wpftmp.csproj` (31 KB, absolute paths from this machine) in the workspace. The SDK deletes it on success; only a failed or interrupted markup pass leaks it. Step 4's `build` on that directory then failed MSB1011 purely because of it, and the file shipped in the deliverable. The harness already does exactly this class of workspace housekeeping around a build — see `DropboxIgnoreMarker`, which logged "Marked 2 build-output folder(s) … as ignored by Dropbox" in this same run. Put the sweep in `BuildTool.BuildAsync` after the executor returns, scoped to the built directory, matching `*_wpftmp.csproj` and `*_wpftmp.sln` and only when the file is not the target that was asked for. Verification: scaffold a wpf project, force the markup pass to fail, assert no `*_wpftmp.csproj` survives and that the next `build` on that directory reaches the compiler instead of MSB1011.
- [x] **High** `msb1011-names-the-projects-like-msb1003-does` - build tells the model which project to build when a folder holds several
      `BuildTool.cs:200-218` gives MSB1003 a named remedy — it lists the projects inline rather than pointing at `list_projects`, bought with run `e8f9186a`'s wasted steps. MSB1011 ("this folder contains more than one project or solution file") is the same class of problem — the target is not a single project — and gets nothing but `Build failed with 1 error(s).` and a raw diagnostic. It cost run `dbaa0580` steps 5, 6 and 7, spent reading three scaffold files for a compile error that was not in any of them. Add an MSB1011 branch beside the MSB1003 one, reusing the same `ProjectLocator.FindAllProjects(directory)` call already in that block, and name which of the found projects to build. Verification: a test over a directory containing two `.csproj` files asserts the observation summary names both and says to build one; ideally pair with the wpftmp sweep so the same fixture proves the residue is gone too.
- [x] **High** `no-launch-is-stated-to-the-completion-panel` - Tell the completion panel when the run never launched what it built
      `AgentLoop.CritiqueCompletionAsync` (`:777-781`) appends `_runtime?.Latest` when a launch happened and appends nothing when none did. The critic prompt already handles the case — `CriticPanel.cs:417` says the absence of a launch, for a goal about a running application, is grounds to refute — but the panel must infer an absence from a missing line, and it did not. Proof it is the evidence and not the prompt: at 19:22:27 the completion panel accepted this run 3/3 citing build and tests; at 19:22:38 the post-run reviewer, same critic role, refuted 3/3 with all three lenses naming the missing launch explicitly. Append one line when `runtime is null` and the run applied changes to a project that produces an executable — this is the only renderer of a fact that already exists, so it clears `§18a`'s bar on new sentences. Verification: replay `dbaa0580`'s completion panel with the line present; it should refute, matching the post-run panel that already did on the same work.
- [x] **High** `a-diagnostic-with-no-message-carries-the-raw-tail` - When the parsed diagnostics carry no message, fall back to the raw output
      Step 3's Compile rung told the model, in full: `error MSB4018:` — the code with an empty message and no cause. MSB4018 puts the exception that actually failed on the lines that follow, which are not MSBuild diagnostic format, so `MsBuildOutputParser` drops them. `BuildTool` already has the right escape hatch — `Tail()` at `:240` — but it fires only when `summary.TotalErrors == 0` (`:224`), and here TotalErrors was 1, so the empty message won and the fallback was skipped. Widen the condition to "no parsed diagnostic carries a non-empty message". This is task 69's lesson (`a delta the model cannot see is a repair it cannot make correctly`) in the build channel rather than the test channel, and it fixes both organs at once because `VerificationLadder.cs:308` returns the same `build.Diagnostics` to the rung. Verification: a fixture of real MSB4018 output asserts the message names the inner exception type rather than ending at the colon; the existing 0-error fallback tests must stay green.
- [x] **High** `digest-carries-what-the-model-actually-read` - The retrospective digest drops the observation payload the model was given
      `Retrospective.RenderStep` (`:386-410`) renders `Summary`, `Error` and `Hint` per tool call and never `ToolCallRecord.Result`, which holds the serialized observation the model read (`AgentLoop.cs:1110`). `Result` is model-facing and carries no `[ModelFacing]` marker (`StepRecord.cs:61-71`), so the invariant added on 2026-08-15 to stop precisely this does not cover it. That is the fifth surface to drop a model-facing fact, and it is the one every future stage-2 reviewer reads. Mark `Result` `[ModelFacing]` and render a capped excerpt (300 chars, same budget as the others) on its own line for calls whose `outcomeOk` is false — which requires the `build` outcomeOk fix to be useful for builds, but stands on its own for every other tool. Verification: extend `RetrospectiveDigestTests` to populate `Result` with its own sentinel and fail the build if the digest loses it.
- [ ] **Medium** `the-loop-launches-what-it-built` - One automatic launch before the completion panel, when nothing launched the app
      `CLAUDE.md §18a` already forbids shipping a capability the model must elect, and names `launch_app`'s probe as the example. `launch_app` itself is that same thing one level up: run `dbaa0580` spent 20 steps on a desktop goal and never called it; `dd11ef7c` did not launch either; `457867c7` launched only after a refutation forced it. Everything built on 2026-08-15 — the sweep, positional addressing, the `Window:` line, the critic clause — is gated behind a call the model does not make. Scope it narrowly: in `AgentLoop`, immediately before `CritiqueCompletionAsync`, when the run applied changes, `_runtime?.Latest` is null, and exactly one executable project exists in the workspace, invoke the launch path once with the existing 120 s clamp. `LaunchAppTool` already treats still-running-at-timeout as success and already sweeps the window for free, so this reads and never types. Verification: re-run the desktop goal and assert the transcript contains a `Window:` line and `RuntimeEvidence` is non-null at the completion panel without the model having asked; a console-host run must skip it and say so rather than reporting a window with nothing in it.
- [ ] **Medium** `one-renderer-for-the-change-under-review` - The two critic panels render the same change two different ways
      `RunReviewer.DescribeChanges` (`:261-294`) renders one net diff per file, and its doc comment records why: run `ff74b2d4` refuted a finished run for having once been wrong, because the panel was shown every intermediate edit. `AgentLoop.DescribeChanges` (`:988-1008`) still renders exactly that — every applied change in sequence, each with its own diff — so the completion panel judges the journey while the post-run panel judges the net state. Only one of them carries the lesson. This is the same two-organs-one-fact shape `VerificationVerdict.Describe` and `[ModelFacing]` were built to end. Extract one renderer both call, on the `RunReviewer` semantics, and give it the net-nothing case too. Verification: a test asserting both callers produce byte-identical text for the same change set, plus a replay of `dbaa0580`'s completion panel to see whether the rendering alone moves the vote.
- [ ] **Medium** `record-when-the-two-panels-disagree` - Count runs the completion panel accepted and the post-run review refuted
      Run `dbaa0580` was accepted 3/3 at 19:22:27 and refuted 3/3 at 19:22:38 by the same critic role on the same work. `RunMetrics` carries `completionCritiquePanels`, `completionCritiqueRefusals` and `completedOverRefutation` — the inverse case, where the later and unactionable panel was the correct one, is recorded nowhere and is reconstructable only by reading a log beside a `ReviewRecord` by hand. Add a boolean to `RunMetrics` set when the completion critique accepted and the post-run review refuted. This is the measurement that tells you whether the launch-absence line, the shared renderer, or the automatic launch actually closed the gap — without it, all three are changes you cannot grade. Verification: the flag is true for a replay of `dbaa0580` and false for `457867c7`, which was refuted and repaired inside the run.
- [ ] **Medium** `notice-what-this-run-wrote-that-nothing-exercised` - A fourth clause: types this run changed that no test references and no launch drove
      Task 66's three clauses ask whether the tests touch the product, and run `dbaa0580` answered exactly that question and no more: the model wrote at step 16 that its tests "don't exercise the WPF UI code or the text change event handlers", extracted the two-line formula, tested that, cleared the notice at step 18 and stopped — leaving 100% of the code review's defects untested. State it as a fact, not a prescription, and name the launch as the answer for code-behind — which is honest, since a code-behind handler is genuinely not unit-testable and that is why it needs the other oracle. A notice, never a gate, on task 66's stated contract. Verification: run `dbaa0580`'s tree produces a notice naming `MainWindow`; a tree whose changed types are all referenced by tests or covered by a launch readback is silent.
