## 1. The newest rung shipped with no route in, and this run was its scheduled test

`HISTORY.md`, 2026-08-15 (later), open threads: *"Not re-run end to end through the loop: the probe was driven against the real application directly. **The next live run on a WPF goal is the actual test of whether the model reaches for it.**"*

This is that run. The answer is no.

The transcript's own verdict lines read `verification: passed (0 tests)` — the post-`VerificationVerdict.Describe` rendering, so this was a build carrying `probe` — and step 20's summary ends with the unconditional hedge, which `LaunchAppTool` now emits only when `readings` came back empty. (Worth confirming from `RunRecord.Provenance` in the run's JSONL before acting; if the build predated the probe, this section is void and the rest is not.)

So: the probe was there, the model had written `x:Name`s an hour earlier, the goal was literally about two values agreeing, and it called `launch_app` with two arguments. The tool then reported *"It runs and renders; whether the window is right still needs eyes on it"* — while `CelsiusTextBox` said `0` and `FahrenheitTextBox` said `0`.

The capability is right. The **delivery mechanism** is the part that failed: an optional parameter costing 268 characters of schema, which the model must elect, on the one axis nothing else in the harness can see. This repository already wrote down the rule that governs this, in task 55: *"Do not rely on the system prompt to hold this. 'Only call when needed' is advice; `IRetrievalPolicy` is a mechanism, and the difference is the lesson of every alias and stall counter in this file."* The probe is currently advice.

The cheapest correction needs no prompt at all. A launch that already has a window handle and a UI Automation client can read back every named text-bearing control without being asked — no typing, no clicking, no side effects, no schema cost. On this run it prints `0` and `0` into the transcript, into `RuntimeEvidence`, and into the evidence three critics read.

## 2. Four perfect sentences, four shipped defects — a message is spent the moment the next step begins

Step 2's refusal is the sharpest case, and it is *stronger* than the process review could see. The full observation carried a hint the digest does not render:

> Create it at the root instead - path 'TemperatureConverter.slnx' - and then add each project with `add_to_solution`. If you do not need a solution, skip it…

A filename, a tool name, and an ordering. The model read it, wrote nothing down, and the repository shipped without a root solution. Same shape at step 9 (the clip-risk note naming `launch_app`, reached eleven steps later as a checkmark), step 14 (a project-layout problem delivered as an already-applied repair, read as a status line), and step 20 (the open question, read as a green light).

`HISTORY.md` for 2026-08-09 named this exactly — *"Every message this harness has built worked. None of them had anywhere to be recorded as outstanding"* — and fixed it **for suite notices**, via `RungResult.Noticed` → `RunProgressSentry` → a line in the run record. The general case is still open, and refusals are the instance where fixing it is cheapest: the harness knows what was wanted (the tool and its operation), knows it did not happen, and can check whether it ever happened afterwards. `dotnet_project new_solution` was refused at step 2 and never succeeded in 20 more steps. That fact is computable and currently uncomputed.

Note what this is *not*: a case for better wording. The wording is already excellent. The gap is persistence.

## 3. The harness misled its own reviewers again, one field over

2026-08-15 fixed `Retrospective.cs` because both reviewers of `ae72c5ad` read `verification: passed` over a rung that had verified nothing, and `VerificationVerdict.Describe` became the single renderer with a source scan guarding it. That fix was about the *verdict* field. The same class survives in the same method: `RenderStep` writes `call.Summary ?? call.Error` and drops `ToolError.Hint` entirely.

The consequence is visible in the review you commissioned. The process reviewer built a careful mechanism argument on step 2 — *"the corrective is right there in the sentence"*, *"form errors get repaired in the next call because the correction lives in the same working thought"* — reasoning about a message it was shown half of. The conclusion survives; the recommendation it implies changes. Half-text points at wording. Full text points at persistence.

This is the fourth surface in this repository to map a rich model-facing fact onto a lossy retelling (model-facing header 2026-08-09, critique tally 2026-08-11, verdict renderer 2026-08-15, hint field now). The 2026-08-15 fix found its fourth instance with a source scan; there is no equivalent guard for "the digest drops a field the model was given."

## 4. The completion panel's own prompt licensed the overclaim

Three critics accepted 3/3. The `evidence` lens wrote *"runtime confirmation that the application starts and draws a window"* — an accurate restatement of a sentence whose second clause disclaimed exactly the question being voted on. None of the three cited a line of source, and defect #1 is visible from reading `ViewModel.cs` alone.

`CriticPanel`'s system prompt is why. It reads: *"the absence of a **launch**, for a goal about a running application, now is [grounds to refute]"* — written for task 71, when a launch was the best runtime evidence obtainable. Since 2026-08-15 it is not. A launch that only watched is now the *weak* form, and the prompt still treats its presence as the answer. That is the same defect HISTORY records three times under a different name: a prompt asserting a limitation a later task removed. The condition task 71 set for tightening a critic — *"refute over evidence the worker could have produced and did not"* — is now satisfied for readbacks, and a refutation on those grounds is answerable in one step rather than unanswerable, which is what distinguishes this from the gate deadlocks of `5c071f37` and `a408b61b`.

## 5. Two smaller things the run establishes

**The redundancy nudge cannot fire in the shape the model produces.** Steps 17 and 18 re-established step 15's green and were not cache hits: `RunTestsTool` keys `BuildCache` on `verdict.RelativePath` from its `path` argument, whose default is `"."`, while `VerificationLadder` passes `request.ProjectPath` — the ProjectLocator-resolved `.csproj`. The ladder's entry and a bare `run_tests` can never share a key, so the `reused` flag never sets, so 2026-08-11's *"at the second consecutive one with nothing applied in between, one nudge"* is unreachable. Normalising the key is not the fix (`"."` over two projects and no solution genuinely resolves to nothing, and a hit there would be unsound); decoupling the nudge from the cache is.

**The plan was authored before the first observation and never moved.** Step 0's `update_todos` preceded `list_projects`, kept the same five items for 22 steps, went 0→1→2→3→5 of 5, and never absorbed step 2's failure. Five of twenty-two steps, zero influence on control flow. The 2026-08-08 decision moved todos to phase boundaries; the boundary before any information is not one of them.

## The pattern, stated once

Every fix in `HISTORY.md` since 2026-08-08 has been a **message** — better wording, a named consequence, a truer verdict, a hint that says where the text diverged. That work is close to finished and it worked: this run had 100% validity and zero thrash. What this run shows is the ceiling of the approach. A message reaches one step. The four that mattered here were all read, all understood, and all outlived by nothing.

The next tranche is not more messages. It is (a) capabilities that do not require the model to elect them, (b) a place for a still-wanted intent to sit, and (c) an oracle that looks at what the product does when it opens rather than only at what the change did to it. The defect a user sees first — `0 °C` beside `0 °F` — was reachable by the harness at step 20 and by a three-line constructor test at step 15, and the run had a green light on both.

Items already declined on the `ae72c5ad` and `46231701` work orders (the rating-strip caveat, the build-warning oracle label, the exact-float-equality notice, `update_todos` echoing an outstanding notice, skipping the UnitTests rung when no test is declared) are left alone, even where this run touches them. One exception is flagged as such below: `launch_app` refusing a directory cost a step in `ae72c5ad` and again at step 19 here, which by this repository's own occurrence-two rule reclassifies it.
