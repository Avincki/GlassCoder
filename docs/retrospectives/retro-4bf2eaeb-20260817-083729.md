### The pattern: three mechanisms were defeated by ordinary, honest work happening beside them

This is not three accidents. It is one property, and `RunProgressSentry.cs:103-107` already names it for a different field: *"each edit honestly reset every other counter while fixing nothing."* The same property bit three more organs in this run.

**1. The identical-failure counter never armed, across nine identical failures.** `dotnet_project` returned the byte-identical first line `dotnet add_package failed with exit 1.` at steps 30, 32, 38, 39, 41, 44, 49 — plus 46's restore. `FailureKey` is stable across all of them, so this is precisely the shape `NudgeAfterIdenticalFailures = 3` and `MaxIdenticalToolFailures` exist for. It never fired, because `ObserveStep` clears `_failureCounts` on any applied change, and the run applied real changes at 29 (csproj edit), 36 (delete), 40 (create), 48 (csproj edit) — legitimate work, interleaved with the guessing. The counter peaked at 2, four times. Twenty-six steps and roughly two-thirds of a 1.12M-token run passed with every stop-verdict structurally unable to fire. The fix already exists one field over: `ObserveTestOutcomes` is deliberately tracked *before* the reset and exempted from it.

**2. The test-suite notice was silenced by the one edit its own text warns against — for the second time.** The notice fires at steps 17, 19 and 24. At step 26 the agent edits `MainWindow.xaml.cs` to construct `MultiplicationService`, and step 26's rung reads `passed at UnitTests … 5 tests passed. The same number as the previous climb` — clean. The notice never returns, including at step 53 where the copy-pasted suite lands. `TestSuiteNotices.cs:99-113` records that run `46231701` did exactly this, and the 2026-08-11 fix was to change the *wording* so it names the trap instead of prescribing it. The wording is good and it did not work: the detector's mechanical condition (`type ∈ ProductIdentifiers`) is still satisfiable by one line. From step 26 on, the run had no instrument pointed at its largest defect.

**3. The retrieval signal was cleared by a green compile while its question was still open.** Step 37's pre-write refusal carries `CS0246` on `StaFactAttribute` — a type no workspace source declares — so `DiagnosticRetrievalSignals.Set` fired. Step 40's verification ran a complete compile with no CS0246 (the file had been rewritten), so `Observe(..., complete: true)` called `Clear()`. Fourteen steps later the model asked the exactly-right question and `learn_search` refused: *"Nothing in this run says the answer is outside the workspace."* The class's own doc comment already worries about the inverse case (narrow batches erasing an admission) and fixed it; this direction is untouched. A green compile is not an answer to "does any package provide `StaFact`" — it is the absence of the question, which is what deleting the file produced.

The generalisation `TestCountMemo` already carries — *every green should say what moved since the last one* — has a sibling this run establishes: **every counter that resets on progress needs to say which progress it is entitled to reset on.** An applied change is honest evidence about `edit_file`'s text-match failures. It is no evidence at all about whether a package exists, whether the tests reach the product, or whether a documentation question was answered.
