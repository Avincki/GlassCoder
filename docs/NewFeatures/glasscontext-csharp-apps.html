Analysis · revisit · small-medium C#

Intent and plan, not a catalog

The earlier preprocessor note treated C++ headers, legacy Lisp and monolith scale as the hard limits. The actual target is small-to-medium C# applications. That retires those limits, and it also retires most of what a file-by-file documentation mirror was going to buy. The pairing is still the right exercise — because this is the only target both applications can already finish, and the only place the context term can be measured.

00

The target

GlassContext was built for multi-repo C++ / C# libraries with sibling DLLs and archived Lisp. The preprocessor analysis inherited that flagship and spent a section on the C++ verification gap, regeneration cost on a 1.6M-LOC tree, and a path-resolution rule aimed at .h files. Those are the wrong constraints.

The consumer is GlassCoder. The work GlassCoder is for is small-to-medium C# applications: a handful of projects, tens to a few hundred source files, a solution that dotnet build and dotnet test --filter already understand. GlassCoder itself is one of those applications. The overlap is no longer a sliver. It is the whole product surface.

In scopeOut of scope
C# / .NET solutions, typically WPF + class libraries + tests C++ headers, AutoLISP, hybrid survey libraries
One repo, or a solution whose projects already live inside it Sibling DLL checkouts and CLAUDEDOCS_* fallbacks
30–300 .cs files; regeneration is a coffee break Monoliths where a documentation mirror goes stale as you walk it
Oracles that are test class names Prose acceptance against a legacy Lisp system
01

What this retires

Previous limitStatus now
GlassCoder cannot verify C++ / Lisp Irrelevant. Roslyn and dotnet test are the ladder.
docs/llms regeneration dies on a huge tree Irrelevant. A hundred files regenerate in a session.
Sibling DLL repos, legacy/*.lsp, CLAUDEDOCS_* Optional leftovers. They must not shape the emitter or the plan.
The worker cannot see the tree without a map in FILE 1 False here. The workspace map lists up to 200 files and inlines the small ones. A small C# app is often fully oriented at step 0.
Path 2 intent is too expensive to run on everything Inverted. On this size you can enrich every file, and freshness is cheap.

The pairing is a better fit than the first note said. That does not mean GlassContext as it stands is the right preprocessor. It means the harness term is already strong, so context only pays if it adds what the harness cannot see.

02

The equation on this target

capability ≈ model × harness × context

A product, not a sum: a zero on any term zeroes the result. GlassContext does not train a model and does not replace the loop. For a 40–200 file C# solution the three terms sit like this:

TermWhat it is hereWhat the pairing does
Model The served worker, the local critic, the optional remote second opinion Nothing. Same aliases, same endpoints. Extraction goes up; weights do not.
Harness list_projects, find_symbol, in-memory compile, diagnostic summarizer, dotnet test --filter, workspace map A small upgrade: consume a plan, gate the checkbox on an oracle, keep the todo list visible after compaction.
Context What the worker believes before step 1, and what it can retrieve later The term that moves — and only if it is purpose, conventions, gotchas and a sliced next unit of work, not a file catalog.

Discovery of where code is is a harness job now. The worker can already open Foo.cs. The product goes up when it does not have to infer why Foo exists, which layer it belongs in, and what “done” means.

More content is not more context

Dumping FILE 1 plus the whole docs/llms tree into every step would lower the product. Dilution costs wall-clock on every step; the useful tail is truncated; the worker follows Claude Code rituals it cannot keep. Wrong context is not a small context. It is a smaller product. The agent-profile plus retrieval-on-demand split raises useful context without raising resident context.

Three qualities, if GlassContext emits them for this reader:

  1. Identity at step 0 — what the app does, how it builds and tests, which rules constrain an edit. That is CLAUDE.agent.md in the 6 000-token root.
  2. Intent on demand — why a member exists, what it mutates, the gotcha a caller must know, an example mined from tests. That is Path 2, pulled only when the worker touches the file.
  3. A framed next unit of work — not “here is the repo,” but “task retry-transport: change these files; done means this test is green.”
03

What GlassContext still brings

Still high value

  • Path 2 intent — purpose, gotchas, test-mined examples. find_symbol answers “where is it declared.” Intent answers what a syntax tree will not. On this size the content-hash cache makes a full pass affordable.
  • Module C’s human-gated narrative — a two-page product brief (what the app does, layering, “no logic in code-behind,” where a feature lives) is exactly the lean root a local worker needs, if you stop asking Module C for a Claude Code ritual document.
  • A workplan with dotnet test --filter oracles — the missing-oracle gap is easy to close. Every task can name a test class. GlassCoder already has TestFilter. A workplan row becomes a suite row.
  • Tutorial / from-scratch rebuilds — a small C# app can be rebuilt from empty. Every ablation arm starts byte-identical. That is a project-scale benchmark, not a demo.

Value collapses, or becomes optional

  • FILE 1 as emitted today — personal-context rituals, “tick the checkbox yourself,” legacy Lisp, sibling header paths. On a single-repo C# app the workspace map plus list_projects already give orientation. Loading stock FILE 1 into the root is dilution.
  • docs/llms from HeaderParser — the C# regex requires an access modifier and name(…). It misses records, interfaces, properties, primary constructors, expression-bodied members and most types. Without Path 2 the pages restated what read_file already returns.
  • Sibling / legacy / Python / C++ walkers — cheap to leave in the tree. They must not drive defaults, prompts or FILE 1 section order.
  • YouTrack-sized 1h–2d tasks — a medium C# feature is often two to four GlassCoder runs. Human-day estimates are the wrong unit.

Missing because the target is C#

GlassContext does not yet understand a .NET solution. That is now the real gap, not C++.

  • No .sln / .csproj graph in the root (who references whom, which project is the test project, which is WPF).
  • No NuGet / central-package story.
  • No View / ViewModel / XAML pairing — both applications in this pairing are WPF, and GlassContext treats .xaml as invisible (FileExtensions defaults to .h and .cs).
  • Module briefs (FILE 5) stay empty placeholders. On a six-project solution those briefs are the map.
  • Parsing is regex. GlassCoder already has Roslyn in-process. GlassContext is the weaker C# reader and the stronger intent writer. That split should be explicit.
04

What the harness already covers

At step 0 on a small C# repo the worker typically gets the system prompt, a workspace map that is often a full listing, and the goal string. Then list_projects names every .csproj, find_symbol finds the declaration, the ladder compiles the edit in memory, and tests run with a filter. Discovery and verification are solved.

What is not solved, and what still zeros the context term:

  • RootContextFiles defaults to []. The worker has no product identity unless the goal text carries it.
  • update_todos is invented mid-run and falls out of the window when the conversation is compacted.
  • There is no next-task queue. One goal box, one paste.
  • Completing a plan is not “the feature works” unless an oracle says so — and run e426f418 showed a finished todo list impersonating a finished goal.
Do not rebuild inventory

GlassContext features that re-implement list_projects or a file listing do not multiply the product. Build the things the loop cannot see: purpose, conventions, gotchas, and a sliced next unit of work with a test name on it.

05

What to change and add

On GlassContext — become a C# intent-and-plan preprocessor

  • An agent profile that is a product brief, not a shrunk FILE 1. Emit CLAUDE.agent.md, about 1.5–3k tokens: what the app does, the solution map (projects, references, the one build command and the one test command), layering and conventions that constrain edits, and a pointer that per-file intent lives at docs/llms/<mirrored path>. No personal-context ritual, no checkbox instruction, no sibling or legacy sections unless they exist. Keep FILE 1 for Claude Code. Reuse the reviewer rubric — conciseness and actionability are already two of its six criteria.
  • Replace regex C# parsing, or stop pretending the catalog is documentation. Drive member lists from Roslyn, or skip the HeaderParser pages and only emit Path 2. Signature-only markdown is not context on this target.
  • Fill per-project briefs, not per-folder indexes. src/Foo.Core/CLAUDE.md: purpose, public surface, what may depend on it, “when changing X also change Y.” Six short files beat one generated tree of 150 signature pages.
  • See .csproj and .xaml. Default extensions should be .cs, with .xaml as paired context (this view binds that view-model). The solution graph belongs in the agent profile.
  • Workplan format v2, sized for a 30-step run. Stable task ids so pass@1 survives a reorder; target projects and files named; an **Oracle:** line that is a dotnet test --filter expression; size in steps, not days; no “add tests / run the build” tasks — the ladder already does that. Generate from the accepted brief plus the solution graph, not only from a Module C draft.
  • Run Path 2 on the files that carry rules, or on everything. On this size, “the 10–20% that carry intent” is a preference, not a cost limit. Prefer domain, orchestration and guardrail types over generated code and trivial DTOs. The content-hash cache stays.
  • Leave the C++ / Lisp surface parked. Do not delete it. Do not let it drive defaults.

On GlassCoder — consume, do not rediscover

  • Load CLAUDE.agent.md and measure it against the existing no-context arm. A reviewer score of 7.2 is an opinion about a document. A pass@1 and tokens-to-solve delta is a fact about it. Do this before building anything else. Do not raise MaxRootContextTokens to fit FILE 1.
  • Put the selected workplan task in the opening user message — id, text, target files, oracle. Do not ask the worker to open WORKPLAN.md. The harness already injects the goal; it just does not parse the file.
  • A workplan runner that ticks the checkbox only when the named tests passed, stops at the first failure, and resumes on the next unchecked row. Attempt already exists for retries. The console host is the first surface; the WPF goal box grows a “next unchecked task” picker, not a second planner.
  • Hint the intent sidecar on first touch of a source file — one line on the observation, not a dump of the tree. Even though a small tree might fit in the root, it is still the wrong resident set. Measure whether the hint moves tokens-to-solve.
  • Seed update_todos from the task’s slices and re-inject the current list after compaction. The failure mode on a small app is not “lost in a huge tree.” It is “claimed done because 5/5 todos ticked.”
  • Close the loop through retrospectives, not another planner. Session retrospectives already read WORKPLAN.md. Stage 3 may propose a split or a “this task was too big” flag; a human accepts; GlassContext’s workplan view shows it. Both applications were designed with a human gate on generate-plan-execute.

Deprioritize

  • In-process reference to GlassContext Core for regeneration — regen is fast; a button or a CLI is enough until stale-detected-then-act is the bottleneck.
  • A C++ syntax rung as a prerequisite.
  • Monolith freshness as a design constraint.
  • Teaching the worker the src/foo/Bar.h → docs/llms/… rule as a central feature. Keep the mapping. Discovery is not the bottleneck.
06

Why the exercise is worthwhile

The catalog is not what multiplies capability. Running the pairing is. You get a measured context term on the only target both applications can already finish: a C# solution, Roslyn on the write, dotnet test as the oracle, a tree small enough that “with context / without context” is a fair fight.

That is the thing neither application has alone. GlassContext can score a draft. GlassCoder can score a run. Until the same tasks go through both, you do not know whether a page of intent, a 2k-token brief, or a sliced workplan moved pass@1 or only read well. The founding guide called that the teacher. The exercise is that measurement. 

// the loop neither application closes by itself
GlassContext writes context  →  GlassCoder runs the same tasks with / without it
                    →  pass@1 and tokens-to-solve say whether context paid
                    →  GlassContext keeps the sections that moved the number
                    →  capability goes up because the context term went up
                       and you can prove it

It is also cheap enough to be honest. Path 2 on a hundred files is a session, not a pipeline. A workplan row with --filter is a suite row. StandardArms.NoContext already exists and currently compares an empty list to an empty list. You can learn in a week whether context paid, instead of arguing from reviewer scores.

If you do thisWhat you learn
A lean CLAUDE.agent.md, actually loaded Whether identity at step 0 earns its tokens, or the workspace map was already enough.
Intent on the types that carry rules Whether gotchas and test-mined examples move edits-to-green, or only read well.
A few oracle-backed slices Whether a framed unit of work beats a pasted paragraph — and whether the harness, not the model, can be trusted to tick the box.
The same suite with the root on and off The context term as a number. Either it paid, or a plausible story is retired. Both results are progress.

Sitting on GlassContext output that never enters a GlassCoder run is not an exercise. Loading stock FILE 1 as-is will likely hurt tokens-to-solve. The worthwhile version is the short identity, the retrievable intent, the oracle-backed slice, and the A/B. If the delta is real, you have the preprocessor the equation was missing. If it is not, you have a measurement. Either way the lab did its job.

Shape of the work

Continues the numbering from the preprocessor note (77–81, C1–C4), but drops the items that only existed for C++ or for in-process regeneration. The profile and the oracle still come first: they are what make the measurement worth running.

#TaskEst.Depends on
C1′ GlassContext: agent-profile emitter — CLAUDE.agent.md as a 1.5–3k product brief (solution graph, build/test commands, layering), no session rituals. Reviewer loop reused to score it. 1d —
C2′ GlassContext: workplan format v2 — stable task ids, target files, an **Oracle:** line that is a dotnet test --filter expression, size in steps, no build/test tasks. Module D and Module F prompts updated. 0.5d —
C5 GlassContext: fill per-project FILE 5 briefs from the solution graph; default extensions .cs (and .xaml as paired context). Park the C++ / Lisp defaults. 1d C1′

77′ GlassCoder: point RootContextFiles at CLAUDE.agent.md on a small C# repo; run the suite baseline vs no-context; record the first real pass@1 delta for generated context. 0.5d C1′
78 GlassCoder: workplan runner — parse, run unchecked tasks in order, tick only on the oracle, stop at first failure, resume on re-invocation. Seed update_todos from the task and keep the list visible after compaction. 1.5d 77′
80′ GlassCoder: honour the per-task **Oracle:** line as TestFilter; hint the intent sidecar on first touch of a source file; measure tokens-to-solve with and without the hint. 0.5d 78, C2′
81 Run one Module F tutorial workplan from an empty directory as a project-scale benchmark arm; compare against the same plan under no-context. 1d 78, 80′
C3 GlassContext: metrics importer — join metrics.jsonl per-task outcomes onto the workplan view; flag repeat failures for decomposition. Human-gated. 1d 78

Acceptance

  • Running the suite with a GlassContext-generated CLAUDE.agent.md as root context produces a measured pass@1 and tokens-to-solve delta against no-context — a number, not an opinion.
  • A workplan checkbox is ticked by the harness only after the named tests passed; a run the model merely believed finished leaves the box unticked.
  • Re-invoking the runner after an interruption resumes at the first unchecked task, with attempt numbers intact in the metrics.
  • The agent profile contains a solution graph and no personal-context ritual; FILE 1 remains the Claude Code document.
  • A tutorial workplan executed from an empty directory yields per-arm comparable metrics and counts as a project-scale suite entry.
