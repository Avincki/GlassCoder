00

The gap this closes

GlassCoder can read, grep, glob, create, edit, build and test. What it cannot do is change the shape of the solution it is working in. A .sln is where projects are wired together, and the agent has no verb for it: it can write a new Widget.csproj with create_file and then have no way to tell the solution the project exists.

The suite already names this gap. Task 6 in the task suite is “wire a new module into the build”, and its oracle is a build that only goes green once the new project is part of the solution. Today the only routes to that are the two this proposal exists to replace:

Route todayWhy it is wrong
Hand-edit the .sln with edit_file A .sln is a fragile format — a per-project GUID, a matching entry in ProjectConfigurationPlatforms, and folder nesting maps in NestedProjects. Replacing one exact string cannot keep those three in sync, so the agent corrupts the solution as often as it configures it.
Shell out to dotnet sln with bash Right engine, wrong seam. bash is opt-in and sandbox-gated, and — the reason CreateFileTool refuses to be a bash call — it writes around the change log. The change would never appear in the diff view or reach the approval gate, so the UI would stop being an honest record of what the agent did.
The distinction that matters

Editing a project's contents is already edit_file's job, and building or restoring is build's. This proposal is only the one thing neither does: editing the membership and structure of a solution, safely enough that it can be a standard tool rather than a privileged one.

01

Four verbs, one tool set

A single SolutionTool : IToolSet under src/GlassCoder.Tools/Solution/ — the folder mirrors Git/, and the tool mirrors GitTool: a set of related verbs that wrap a well-behaved CLI through IProcessRunner. Each verb is a method carrying [GlassCoderTool], with a [Description] on the method and on every parameter, so the JSON schema is generated from the signature and cannot drift from the executor.

Wire nameOrderdotnetDoes
solution_list_projects read-only 90 sln <sln> list Returns the projects in a solution, with a truthful count even when the list is capped. Built first: it proves the argv, the parse and the path guard with zero write risk.
create_solution 91 new sln Creates a new solution. Refuses to overwrite an existing file — creation and modification stay separate verbs, exactly as create_file does.
solution_add_project 92 sln <sln> add Adds a project, optionally nested under a named solution folder. dotnet assigns the GUID and writes the configuration map.
solution_remove_project 93 sln <sln> remove Removes a project and its configuration entries, leaving the project files on disk.

Each verb returns one typed ToolObservation<T> — a small record with [Description] on every property, like GitCommitResult — carrying the solution path, the action, the new project total and a ChangeId the desktop change view can deep-link to. The Order values start at 90 so these sit after the git verbs and never precede build or run_tests in the advertised list.

02

Keeping the write visible and gated

This is the whole design problem. dotnet sln add writes the file the instant it runs, which would sail straight past the approval gate. The fix is to let dotnet do the edit against a preview copy, review the result, and only then write it for real: 

// 1. Guard both paths. The .sln must be writable; the project must be readable
//    and inside the workspace. A rejection short-circuits to path_not_allowed.
// 2. before = the current .sln text  (empty for create_solution)
// 3. Copy  GlassCoder.sln → GlassCoder.glasscoder-preview.sln  in the SAME dir,
//    so the project's relative paths still resolve, then run dotnet against it:
dotnet sln GlassCoder.glasscoder-preview.sln add src/Widget/Widget.csproj
// 4. after = the preview's text; delete the preview file
// 5. change = _changes.Propose(relPath, "solution_add_project", before, after)
//    → renders as a diff in the change view BEFORE anything real moves
// 6. _approval.RequestAsync(change) — refused ⇒ mark Rejected, write nothing
// 7. approved ⇒ File.WriteAllTextAsync(realSln, after); mark Applied

The real solution is never touched until a human — or the auto-gate, when approval is not required — has seen the diff. Steps 5 through 7 are the same propose → gate → write pipeline create_file and edit_file already run, so a solution change lands in the per-task change log and the diff view for free, with no new UI:

The simpler variant, and why the preview copy wins

The alternative is to let dotnet edit the real file and restore the captured before text on a refusal. The net effect is identical, but it dirties the real solution between the command and the decision. The preview copy — a sibling file so relative project paths still resolve — never does, which is the same reversibility instinct that makes git_sync abort a conflicted rebase to leave the tree exactly as it found it.

03

Guardrails and validation

  • Path guard on both ends. The .sln is resolved for write and the project for read through IPathGuard. A project outside the workspace, or a solution outside the writable set, is refused with path_not_allowed before dotnet is ever launched.
  • No flag smuggling. A solutionFolder or path beginning with - is rejected, reusing the reasoning behind GitTool.IsSafeRefName: a leading dash is the one way a configured or model-supplied value could turn into a dotnet option. User paths are always passed as their own argv elements after the subcommand.
  • Errors are observations. A missing dotnet, a duplicate add, a remove of a project that is not there — each becomes a typed ToolObservation failure with a hint (already_exists, not_found), sniffed from dotnet's own message the way GitTool reads git's output. Nothing throws out of the loop.
  • Timeouts are bounded. Like every command tool, a run that overruns CommandTimeoutSeconds comes back as timeout, not a hung step.
04

Why the host, not the sandbox

build and bash run inside the container because a build is arbitrary code execution — restore targets, MSBuild tasks, analyzers, all of it repository code. dotnet sln is not that. It parses a solution, rewrites some text, and exits; it compiles nothing and runs no project code. It belongs on the same seam as git: the host, through IProcessRunner, with a fixed argument list and no shell.

The privilege argument

The tool is no more privileged than edit_file, which can already rewrite a .sln by hand. It touches one file inside the writable set, executes no repository code, and gates every write. That is what lets it be a standard write tool rather than an opt-in, sandbox-only one.

The process is launched with prompts disabled and output capped, exactly as GitTool.RunProcessAsync does, so a misconfigured environment fails fast instead of hanging a loop step.

05

build is the oracle

There is no Roslyn pre-write rung for a solution, and there should not be. A .sln is not a C# document, so RoslynCodeAnalyzer.Handles returns false for it and the in-memory compile check that guards create_file would no-op anyway. Inventing a .sln linter would be a second oracle to keep correct for no gain.

The authoritative check a solution edit already has is build .. A project added to the wrong folder, a broken relative path, a solution left inconsistent — all of it surfaces as a build failure through the verification ladder that already exists. So the tool descriptions tell the model to build after changing the solution, and the loop's existing cheapest-oracle-first ladder does the rest. Nothing new to verify; the change is proved by whether the solution still builds.

06

Configuration and registration

A SolutionOptions record binding GlassCoder:Solution, shaped like GitOptions:

{
  "GlassCoder": {
    "Solution": {
      "Enabled": true,              // present so it can be switched off
      "DotnetExecutable": "dotnet",  // bare name resolves through PATH
      "CommandTimeoutSeconds": 120,
      "MaxListedProjects": 200        // cap; the count stays truthful
    }
  }
}

Where it registers

Two defensible placements, and the recommendation is the first:

OptionArgument
Standard write tool recommended Register in AddPhase1Tools alongside create/edit/build/run_tests, guarded by path-guard and approval only. It is no more privileged than edit_file, so solution management becomes part of the normal close-the-loop capability. The Enabled flag still lets an operator freeze build structure.
Opt-in like git and bash An AddSolutionTools extension gated on Enabled, off by default. Correct if you consider solution structure something the agent should not touch unless explicitly allowed. More conservative, less consistent with the fact that edit_file can already do it.

Either way the registration follows the house pattern: bound with AddOptions<SolutionOptions>().Bind(...).ValidateOnStart(), and the tool registered both concretely and behind IToolSet so the registry generates its schema.

07

slnx, and the edges

  • The XML format, .slnx. dotnet sln handles both classic .sln and the newer XML .slnx, so the tool picks the format from the target path's extension and the whole preview-copy flow is unchanged. WorkspaceRootLocator already treats both as root markers, so a freshly created solution correctly anchors the workspace with no change there.
  • Duplicate add, missing remove. Surface dotnet's own message as a typed already_exists or not_found observation rather than a raw dump, so the model gets a clean signal it can act on.
  • What it must not do. No editing of .csproj internals — package references, target frameworks, properties — that is edit_file's territory and stays there. This tool's subject is membership and structure, nothing else.
Solution folders are not disk folders

A solution folder is a grouping inside the .sln, not a directory. The solutionFolder parameter maps only to dotnet's --solution-folder; it never creates or moves anything on disk, and the path guard would refuse it if it tried.

Acceptance

  • A project written with create_file can be added to the solution, the solution still builds, and the addition appears in the change log as an Applied diff.
  • A refused approval leaves the real .sln byte-for-byte unchanged.
  • A path outside the workspace, or a folder name beginning with -, is refused before dotnet runs.
  • With Enabled false, none of the four verbs appear in the registry.
  • Suite task 6 passes by editing the solution, not by cramming the module into an existing project.
