Analysis · two applications, one pipeline

The context generator as a preprocessor

ClaudeContextGenerator3 writes CLAUDE.md and WORKPLAN.md for a repository; GlassCoder drives a local model against one. This analysis maps the outputs of the first onto the intakes of the second, judges how much that is worth as things stand, and lists the changes — on both sides — that would make it worth more.

This pipeline has already run once

The strongest evidence that the integration works is sitting in GlassCoder's own repository root. GlassCoder.ccgproj is a ClaudeContextGenerator3 project file; WORKPLAN.md holds the 35 tasks that built the harness; CLAUDE.alex-vinckier.md and HISTORY.md follow CCG's personal-context and history-entry conventions. GlassCoder was itself constructed through this exact pipeline — CCG generated the context and the workplan, and Claude Code executed the tasks.

The last row deserves emphasis. The learning guide — “an evaluation of ClaudeContextGenerator, the case for pairing it with a local LLM” — is the document GlassCoder was built from, and it was written as a CCG companion before a line of GlassCoder existed. This analysis is not proposing a new pairing; it is checking, against both codebases as they now stand, how much of the founding pairing survives contact with a 7B worker.

So the question this analysis answers is not “could CCG's output drive an agent?” — it demonstrably has. The question is what changes when the agent stops being Claude Code and becomes GlassCoder's local worker: a smaller model, a tighter context budget, a harness that measures everything, and a verification ladder that demands a testable outcome per change.

01

Producer and consumer

The fit is unusually good, because both applications were designed against the same equation — capability ≈ model × harness × context — with CCG building the third factor and GlassCoder building the second. Almost every CCG output has a named GlassCoder intake waiting for it:

CCG producesGlassCoder consumes withState
CLAUDE.md (FILE 1, always regenerated) Context:RootContextFiles — “the lean always-loaded root”, injected by ContextAssembler.CreateInitialMessages as a second system message, budgeted at MaxRootContextTokens (6,000) config only
WORKPLAN.md (FILE 7: numbered, self-contained, dependency-ordered tasks) AgentRunRequest — TaskId + Goal per task; today only by pasting one task into the goal box manual
docs/llms/** (per-file markdown, path-mirrored: src/foo/Bar.h → docs/llms/foo/Bar.md) grep / glob / read_file — retrieval on demand, exactly as CLAUDE.md §12 prescribes works today
Regeneration on demand (Module B, or headless P4) ProvenanceStamper.JudgeFreshness — compares the newest RootContextFiles mtime against the newest source file, and stamps ContextFresh on every run detects, cannot yet act
Reviewer scores (o3/Grok rubric, composite 0–10) Nothing — but see §5: GlassCoder's pass@1 is the ground truth this proxy is standing in for no link
The intent is already written down, on both sides

GlassCoder's CLAUDE.md §12: “If integrating a context generator, reference its UI-free core library in-process rather than shelling out.” Phase 3 of its roadmap: “Plug in the context provider in-process; A/B against no-context. Watch: pass@1, tokens-to-solve.” And CCG has grown the mirror-image seam — its .ccgproj now carries agentEnabled, agentCliPath, agentMaxTurns and agentMaxBudgetUsd fields, and IIntentAgentRunner already launches a headless agent as a subprocess, restricted to read-only tools, with CCG keeping every write. Each application has half-built the bridge toward the other.

They even share a doctrine, in the same words

CCG's value proposition names the “Self-Review Blind Spot” as a problem it exists to solve — “when the same AI drafts and evaluates its own output, it reinforces its own blind spots” — and answers it with an independent reviewer from a different provider. GlassCoder's CritiqueOptions.Role is documented as “ideally a different model family from the worker, so the critic's blind spots are not the worker's blind spots.” Two codebases, written apart, converged on the same rule in nearly the same sentence: never let a model grade itself. An integration that respected everything else but broke this — say, by letting the drafting model verify workplan completion — would be violating both designs at once.

02

What works today, with zero code

Two configuration edits connect the applications this afternoon: 

// config/appsettings.json — GlassCoder, running against a CCG-managed repo
"Context": {
  "RootContextFiles": [ "CLAUDE.md" ],
  "MaxRootContextTokens": 6000
}

…and a workplan task pasted into the goal box. Both function. The root context loads under its token budget, the provenance stamp starts judging freshness against the file's mtime (with no root files it returns fresh-by-default and measures nothing), and the ablation harness can immediately answer whether the context helps: StandardArms.NoContext — “does the always-loaded root earn its tokens? Watch pass@1 and tokens-to-solve” — is already in the default comparison. The A/B instrument for exactly this question shipped before the question was asked.

Three frictions appear immediately, and they are the subject of the rest of this document:

  • The CLAUDE.md is written for the wrong reader (§3). Its conventions assume a frontier model with session rituals; a 7B worker under a 6,000-token root budget gets dilution, and instructions it cannot follow.
  • The workplan has no runner (§4). Tasks are executed by a human pasting them one at a time, and nothing ticks the checkbox when a run's verification passes.
  • Neither side learns from the other's result (§5). CCG scores its context with a reviewer; GlassCoder measures its runs with an oracle; the two numbers never meet.
03

The profile mismatch

CCG's FILE 1 is calibrated for Claude Code, and it shows. The standing instruction it emits into every generated CLAUDE.md reads: 

// FILE 1 §4 — the personal-context standing instruction (abridged)
"At session start, read CLAUDE.<username>.md from this repo root …
 Also read CLAUDE.<username>.history.md from the repo root and from the
 current working folder … At session end, append a dated entry to the
 history file … Also read WORKPLAN.md from this repo root if it exists."

That is a set of meta-instructions: read further files, maintain a journal, track your own progress. A frontier model follows them; they are cheap relative to its context and its instruction-following. For GlassCoder's worker they are exactly wrong, three times over:

  • They spend steps. Every “at session start, read X” costs a read_file round-trip inside a MaxSteps: 30 budget before any real work happens. What a strong model does by convention, GlassCoder's harness should do by construction — resolve the files statically and put the right content in the root context to begin with.
  • They spend tokens on the wrong audience. Team conventions, YouTrack ticket formats, personal-file naming rules: none of it changes what a local worker should do with the next edit. At ~4 characters per token, the 6,000-token budget is roughly 24KB — GlassCoder's own CLAUDE.md alone overruns it, and everything past the budget is silently left out.
  • They assume capabilities the worker lacks. “Append a dated history entry at session end” presumes the model reliably remembers an obligation across a whole session. GlassCoder's design principle is the opposite: put intelligence in the tools and the verifier, not in prompt rituals (CLAUDE.md §18).

What survives the translation untouched

One part of FILE 1 is a perfect fit for a weak model precisely because it is mechanical: the path-resolution rule — src/foo/Bar.h → docs/llms/foo/Bar.md. It is a single deterministic mapping that turns CCG's entire generated documentation tree into retrievable content for read_file, without loading any of it eagerly. This is the CCG output whose value is highest for a local worker: intent-enriched per-file docs (Path 2 enrichment: purpose, gotchas, test-mined examples) that the agent pulls only when it touches the file in question. Lean root plus retrieval on demand is GlassCoder's §12 in one rule.

The root cause is a missing reader profile, not a bad generator

Nothing above is a defect in CCG. It generates for its one consumer, and generates well — the reviewer loop even scores drafts for conciseness. The gap is that “context for Claude Code” and “context for a 7B worker in a measuring harness” are different documents drawn from the same facts: same repos table, same build commands, same path rule, different ceremony and different budget. That is an emitter profile, not a rewrite — see §7.

04

The workplan as a run queue

CCG's workplan format is closer to an agent-run queue than it looks. Its generation rules demand imperative titles, self-contained 2–5 sentence descriptions a developer can start from, dependency ordering, and a checkbox per task. Map that onto GlassCoder's run request and the correspondence is almost one-to-one:

WORKPLAN.md elementAgentRunRequest fieldFit
Task number (## 7. …)TaskId clean — stable across runs, so metrics.jsonl can compare attempts per task
Title + descriptionGoal clean — “self-contained for a developer to start working” is precisely the property a goal needs
Dependency orderrun order clean — execute top to bottom, stop at the first failure
Checkbox - [ ] → - [x]completion signal semantics change — see below
Time estimate (“1d”)— meaningless to an agent — but usable as a proxy for task size when deciding what to decompose
Acceptance criteria (prose, inside the description) VerificationRequest the real gap — prose is not an oracle

Who ticks the checkbox

In CCG's convention, the agent updates - [ ] to - [x] when it considers a task done — a self-assessment. GlassCoder exists because self-assessment is not evidence: its ladder runs syntax → compile → tests before believing anything, and its second-opinion note spent a whole section keeping a model from granting itself a second attempt. The correct integration is that the harness ticks the checkbox, and only when verification passed — the checkbox becomes a record of oracle outcomes, not of the model's opinion. That single change makes the workplan trustworthy as a progress ledger across sessions.

Granularity, and the missing oracle

Two real mismatches remain. First, CCG sizes tasks for humans — one hour to two days. GlassCoder budgets runs at MaxSteps: 30; a two-day human task is several runs at least. Second, and more fundamentally: a GlassCoder task suite entry is defined by its oracle — “each with a passing test as ground truth; no human grading” (CLAUDE.md §16) — while a workplan task carries only prose acceptance criteria. The 17-task hsbGeoLibExt workplan says “validate outputs against legacy LISP system results”; nothing executable says whether that happened. Until a task carries a machine-checkable oracle (a test filter, a command, an expected exit code), a workplan run can only end in “the model believes it is done and the ladder found nothing broken” — which is weaker than what GlassCoder's own suite demands of itself. §7 proposes carrying the oracle in the workplan; it is the single highest-value CCG-side change.

The tutorial workplan — the reproducible special case

CCG has a second workplan producer besides Module D: the Tutorial Generator (Module F) mines a finished project's history files into a phased, from-scratch rebuild plan — pitched, in CCG's value proposition, at “a junior developer [who] can follow the generated CLAUDE workplan to recreate a similar project from scratch.” Read that with GlassCoder's eyes and the phrase lands differently: a local 7B worker is the ultimate junior developer. And because a tutorial workplan starts from an empty repository, it escapes the reproducibility problem that ordinary workplans have (§8): every arm starts byte-identical, exactly like a suite fixture. A tutorial workplan with per-task oracles is a project-scale benchmark — the natural successor to suite-01 through suite-08, generated from a real project's history instead of hand-written. That is a use CCG's own documentation never anticipates, and it may be the most valuable artifact in the whole exchange.

05

How useful is this?

Judged in tiers, honestly:

TierWhat it takesWhat it is worth
As-is Two config lines and manual pasting Modest but real. The docs/llms tree plus the path rule genuinely helps a retrieval-on-demand agent; the root CLAUDE.md helps despite its profile, and the no-context arm can prove by how much. The workplan saves typing, nothing more.
With the §6/§7 changes An agent-profile emitter, a workplan runner, per-task oracles — roughly a week across both applications High. GlassCoder stops being a one-goal-at-a-time tool and becomes a workplan executor with verified, resumable progress; CCG stops emitting prose plans and starts emitting task suites. This is the tier where “preprocessor” is the accurate word.
The closed loop Feeding GlassCoder's per-task metrics back into CCG The strategic value, and it runs in both directions. Below.

The measurement loop neither application has alone

Read CCG's own value-proposition document closely and notice what kind of evidence it offers. Its core claim is right — “output quality is directly proportional to the quality of context” — but its support is a plausibility argument (“spending 20 minutes iterating on context … is orders of magnitude cheaper than hitting a critical misunderstanding 3 hours into a coding session; if the reviewer catches even one such issue, the loop has paid for itself”) and a proxy metric (“measurable improvement — composite scores track quality across iterations”). Its comparison table against manual approaches is a column of checkmarks, every one of them unmeasured. None of this is wrong; all of it is unproven, because CCG has no way to run the counterfactual.

GlassCoder is the counterfactual machine. Run the same task suite with and without the artifact and read pass@1 and tokens-to-solve. A reviewer score of 7.2 is an opinion about context; a pass@1 delta is a fact about it. GlassCoder can tell CCG which sections of a generated CLAUDE.md earn their tokens, whether Path 2 intent enrichment moves outcomes or only reads well, and whether a workplan's decomposition was executable — converting the value proposition's claims, one by one, from asserted to measured. And where CCG's own working paper concedes a gap — “the reviewer scores draft quality; skipExisting compares timestamps; neither detects semantic drift of docs vs. source” — GlassCoder's fresh-versus-stale comparison is the outcome-level answer: drift matters exactly when it moves pass@1, and now that is checkable.

The reverse direction is just as clean. GlassCoder's Phase 3 needs a context provider to plug in and A/B; CCG is that provider, already built, with a UI-free Core library exactly as §12 requests. GlassCoder's Phase 6 measures “pass@1 fresh vs stale context” and its provenance stamper already detects staleness — CCG is the only thing that can act on the detection, by regenerating. Each application supplies precisely the half the other left open. That symmetry, more than any single feature, is the argument for doing this.

06

Changes on the GlassCoder side

  • Point the root context at the artifact config only — RootContextFiles: ["CLAUDE.md"] in the target repo's arm config. No code. Do it first, because it arms both the freshness judge and the no-context comparison.
  • A workplan runner in the console host the core feature — parse WORKPLAN.md into tasks (the format is regular: ## N. Title, checkbox line, description); for each unchecked task, issue an AgentRunRequest with TaskId = "workplan-N" and the task text as Goal; run the ladder; tick the checkbox only on a passing verification, writing the file the same way any other change lands. Stop at the first failure — the tasks are dependency-ordered, so running past a failed prerequisite measures nothing. The retry machinery from the second-opinion work carries over unchanged: Attempt already rides the request, result, run record and metrics.
  • Stamp the context version, not just its mtime small — JudgeFreshness compares timestamps; a content hash of each root context file in the provenance stamp would let two runs be compared by the context they actually saw, which is what the fresh-vs-stale ablation needs to be trustworthy.
  • Reference ClaudeContextGenerator3.Core in-process for regeneration later — a net8.0 library loads in a net10 host, and CCG's Core is UI-free by design. A --regenerate-context flag on the console host could call DocGenService / the deterministic RootClaudeEmitter before a suite run, closing the Phase 6 loop (stale detected → regenerate → measure). Two frictions to respect: CCG's PathGuard is static global state and must be configured before any write, and — pleasingly — both Core libraries define an AgentRunRequest, so one side gets an alias. Do this only after the runner exists; shelling out to a future CCG CLI is an acceptable interim, though it is exactly what §12 says to avoid long-term.
  • Nothing at all for docs/llms — grep, glob and read_file already reach it. The only requirement is that the path-resolution rule survives into whatever root context profile CCG emits (§7).
07

Changes on the CCG side

  • An agent-profile emitter for FILE 1 the biggest value-per-effort — a second output target alongside the Claude Code profile: budgeted to ~6,000 tokens, front-loading what a worker acts on every step (build and test commands, the path-resolution rule, the repos table, the eight universal rules) and dropping what it cannot act on (personal-context rituals, history obligations, ticket formats). Same facts, different reader. CCG's reviewer rubric even has the right criteria to score it — conciseness and actionability are two of its six. Emit it as a separate file (say CLAUDE.agent.md) so the two profiles never fight over FILE 1's always-regenerate rule.
  • Per-task oracles in the workplan turns prose into a suite — one added line per task, machine-readable: **Oracle:** dotnet test --filter RoofRingTests. GlassCoder's VerificationRequest already takes a TestFilter; with an oracle line the runner can gate the checkbox on ground truth, and the workplan becomes exactly the task-suite format GlassCoder's §16 defines. Claude generates the workplan from context anyway — asking it to also name the test that proves each task is a prompt change, not an architecture change.
  • Stable task IDs trivial — renumbering on edit breaks cross-run metrics; a slug or GUID per task (<!-- task:valley-hip-lines -->) keeps pass@1-per-task comparable after the plan is reordered.
  • GlassCoder as a second runner behind the agent seam later — CCG already probes and launches a headless CLI (claude -p via IIntentAgentRunner; agentCliPath is configurable). GlassCoder's console host is the same shape: a process that takes a config and a goal and returns meaningful exit codes. A second IIntentAgentRunner implementation pointed at GlassCoder would let CCG's own agentic features (P4 drafting, intent enrichment) run against the local box instead of metered API — with GlassCoder's transcript as a free byproduct. Worth doing only once the local worker demonstrably handles the enrichment prompt; the seam makes trying it cheap.
  • Read the metrics back the loop-closer — a small importer that joins metrics.jsonl per-task outcomes onto workplan tasks: tasks that repeatedly fail or exhaust budgets are flagged for decomposition in the Workplan editor; a no-context-vs-baseline delta per suite becomes the number CCG's value proposition has been missing. This is deliberately CCG-side — CCG owns the plan, so CCG should own learning from its execution.
08

Limits worth respecting

  • The C++ gap is the big one. CCG's flagship targets are C++/hybrid repositories (hsbGeoLib, headers, legacy LISP); GlassCoder's ladder verifies with Roslyn and dotnet — C# only, today. Its CLAUDE.md §8.3 sketches the C++ path (syntax-only checks via /Zs / -fsyntax-only with flags from compile_commands.json), but until that rung exists, the overlap where this whole analysis applies end-to-end is C# repositories. For the C++ targets, CCG's consumer remains Claude Code.
  • Do not let the root context creep. The temptation once CLAUDE.md is wired in is to raise MaxRootContextTokens until the whole document fits. GlassCoder's own §12 says why not: effective context lags advertised context, and dilution costs wall-clock on every step. The fix for an oversized profile is §7's leaner emitter, not a bigger budget — and the no-context arm exists to referee the disagreement.
  • An ordinary workplan is not a benchmark. Suite fixtures are byte-identical per arm and their oracles are exit codes; a Module D workplan executes against a live, moving repo. Those runs measure progress, not comparable capability — keep them out of ablation comparisons unless the starting commit is pinned per arm. The exception is §4's tutorial workplan: a from-scratch rebuild starts byte-identical by construction, which is what makes it benchmark-grade.
  • Scale-fit is bounded, by CCG's own admission. Its context-strategy working paper judges the generated documentation mirror “defensible for library-sized repos, weak for a 1.6M-LOC monolith” — regeneration cost and freshness both degrade with size. The pairing analysed here inherits that scope: library-sized C# repositories are the sweet spot, and GlassCoder's lean-context discipline makes the monolith case no easier.
  • Two humans-in-the-loop stay in the loop. CCG's iteration loop is deliberately human-gated, and GlassCoder's approval gate and retry button exist for the same reason. Chaining the applications must not quietly produce an unattended generate-plan-execute-plan pipeline; the natural gate is “a human accepts the workplan in CCG before GlassCoder ever sees it.”
  • Versioning across two repos. An in-process reference from GlassCoder to CCG's Core couples release cycles (net8 lib in a net10 host works, but PathGuard's static configuration and the duplicated AgentRunRequest name both need care). The file-based contract — CLAUDE.md, WORKPLAN.md, docs/llms — is the loose coupling; prefer it wherever it suffices.
09

Shape of the work

GlassCoder tasks continue the shared workplan numbering — the sibling proposals hold 36–39 (second opinion, built), 40–45 (MCP retrieval) and 46–51 (harness advisor), and the second-opinion follow-ups hold 52–55 — so this analysis starts at 56. CCG tasks are numbered on its own plan. Order matters: the profile and the oracle (56, C1, C2) are what make everything downstream worth building.

Acceptance, in the style of the existing plans

  • Running the suite with a CCG-generated CLAUDE.agent.md as root context produces a measured pass@1 and tokens-to-solve delta against no-context — a number, not an opinion.
  • A workplan checkbox is ticked by the harness only after the task's verification passed; a run the model merely believed finished leaves the box unticked.
  • Re-invoking the workplan runner after an interruption resumes at the first unchecked task, with attempt numbers intact in the metrics.
  • A task carrying an oracle line fails its run when the named tests fail, whatever the ladder's other rungs said.
  • Regenerating context in CCG and re-running the suite flips ContextFresh from stale to fresh without touching GlassCoder config.
  • A tutorial workplan executed from an empty directory yields per-arm comparable metrics — same starting bytes, oracle-gated checkboxes — and so counts as a project-scale entry in the task suite, not just a demo.
