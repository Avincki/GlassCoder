Design note · built

A second opinion

Putting a different model family in front of the local worker's work: which critic judges is chosen before you press Run, every applied change is judged during it, the finished run is offered to the same critic afterwards, and acting on what it says stays a button a human presses. All of that is now written, transport included. What is left is measuring it.

What is built, and what is not

Built: the critic role is chosen per run and recorded in the transcript; rung 6 runs inside the loop after every applied change; a finished run is offered to the same critic; a refuted run offers a retry that a human presses; the review is persisted verbatim into the JSONL transcript and replays with its run; an unreachable critic no longer counts as an approving vote; a role declares whether it needs a key, so the control that offers it can be greyed out instead of failing on press.

Built since: the transport. A role now picks its wire format, and critic-remote speaks Anthropic's /v1/messages against api.anthropic.com out of the box, through the official SDK's IChatClient adapter. The OpenAI-compatible shape is still one config switch away. §2 describes what shipped.

Still not built: the Ask Claude button on the approval banner (§3 describes what replaced it, and why the banner is still the harder problem), and any measurement at all — nothing on this page has been run against a real critic on a real task suite. That is workplan task 38, and it is now unblocked.

00

What exists now

CriticPanel is rung 6 of the verification ladder: it fans out N critics in parallel, gives each a different lens, parses a JSON verdict, and counts votes. What has been added around it is a way to say which critic, when, and what happens to what it says.

The critic prompt already asks for the right thing. Each critic is told to refute rather than review, which the class documents as deliberate: 

// CriticPanel.cs
// "is this good?" invites agreement from a model that has just been shown a
// plausible-looking diff, while "find what is wrong with this" gives it a job
// it can fail at honestly.

And the three lenses are already split so the critics are not redundant: correctness (does it do what the goal asked, in every case the goal implies), regression (does it break behaviour other code depends on) and evidence (does the evidence prove the change works, or only that it compiles).

The argument is already in your codebase

CritiqueOptions.Role is documented as “ideally a different model family from the worker, so the critic's blind spots are not the worker's blind spots.” That is the case for this feature, written before the feature was proposed. A local worker critiqued by a second instance of itself mostly agrees with itself.

01

Two moments, one critic

“Let a second model check the work” collapses two different things. They share an oracle and share nothing else: they differ in who the advice is for, and that changes almost every decision downstream.

Rung 6 · during the runReview · after the run
AdvisesThe agentYou
WhenEvery change, automaticallyOnce, when the run ends
JudgesOne edit, with its evidenceThe run's diffs and its closing claim
Consumed byThe next model stepA human deciding whether to retry
Latency budgetTight — it is in the loopLoose — the run is already over
Cost profileEvery change × N criticsOne panel, per run
Stateshippedshipped

They are complementary, and the second turned out to be the one worth building first — not because it is a better oracle, but because it was the one with a runtime path at the time: a review of a finished run needs only the run, whereas rung 6 needed the loop to climb the ladder at all. It does now, so both moments are live, and the interesting question moved from "does this work" to "which of the two is worth its cost".

The in-loop half has a cost profile worth respecting

Rung 6 runs on every applied change, times N critics. Against a local critic that is wall-clock; against a hosted one it is a bill, and RunBudget.EstimatedCostUsd now adds the critic's spend at the critic role's own prices, so Agent:MaxCostUsd can actually trip on it. The post-run review is one panel per run. Nobody has yet measured whether the first buys enough recovery to justify the ratio.

One critic, chosen once

Both moments use the same role, and it is fixed before the run starts. A critic that could be swapped while a run was in flight would make that run two arms, and no metric taken from it would be attributable to either. So the choice lives on AgentRunRequest next to the model role and the budget, and lands in the run record with everything else the run was.

02

Choosing the critic before the run

There are now two critic roles rather than one repointed role, and a run says which it wants. Critique:Role is the default; Critique:RemoteRole is what the checkbox asks for. 

// config/appsettings.json — as shipped
"Critique": {
  "Enabled": false,
  "Role": "critic",                     // what a run gets when it does not ask
  "RemoteRole": "critic-remote",        // what the checkbox asks for
  "CriticCount": 3,
  "Quorum": 2,                          // see §6
  "Gates": false
}

Both roles are ordinary entries under Models:Roles, so the settings dialog lists them, checks them and stores their keys with no new UI. The new field on a role is RequiresApiKey — see §7 for why guessing it from the endpoint was not good enough.

The transport, as built

The pipeline the factory assembles — role defaults, then constrained decoding, then OpenTelemetry, then transport — was worth keeping intact, so what landed is a transport swap at the innermost layer rather than a parallel factory. The shipped critic-remote now points at api.anthropic.com and model claude-opus-5.

  • Transport on ModelRoleOptions, defaulting to OpenAI — so every existing role keeps working untouched and no configuration changes behaviour silently.
  • The official SDK, not a hand-rolled client. The Anthropic package ships a first-party IChatClient adapter (AsIChatClient), so this is a second branch in ChatClientFactory rather than a wire format we would own the parsing of — and it brings retries, typed errors and the versioned anthropic-version header with it.
  • Only the innermost client branches. Everything outside it — telemetry, role defaults, cost accounting, the deliberate absence of UseFunctionInvocation() — stays shared.
  • Constrained decoding does not apply. The critic returns JSON by prompt, not by grammar, and CriticPanel.Parse already falls back to a text heuristic when the JSON is malformed. critic-remote switches the stage off.
Two things this transport does that the other does not

Its endpoint is a host root. The SDK appends /v1/messages itself, so https://api.anthropic.com is the whole endpoint — a /v1 suffix produces /v1/v1/… and a 404 that looks like an outage. The settings hint and the config comments state which convention each transport uses for exactly that reason.

It drops sampling parameters rather than forwarding them. Current Anthropic models reject temperature and top_p with a 400 instead of ignoring them, and the critic panel pins temperature at 0 — the right habit for a local critic and a fatal one here. The transport's role defaults null them out, so which oracle a role addresses stays a config choice rather than a crash.

A refusal is an empty answer, not an exception

The API's safety classifiers can decline a request with a successful HTTP 200, a stop_reason of "refusal" and no content at all. Through the critic panel's existing parse that reads as "the critic returned nothing" — a failure to judge, a non-vote, outside the quorum, which is exactly right. The fake server used in tests has a refusal case so this stays true by test rather than by luck.

Correction — cost, and what has since been fixed

An earlier version of this section said a paid critic “slots into both without new plumbing”, so that “a runaway critique loop trips a budget rather than a credit card”. That was wrong at the time: RunBudget priced a whole run from a single role's rates, so a critic on a different role contributed nothing to Agent:MaxCostUsd — a budget that could not trip.

It can now. CritiqueResult carries the panel's own InputTokens, OutputTokens and EstimatedCostUsd computed at the critic role's prices, and RunBudget.EstimatedCostUsd adds that figure — the debt the old comment named, paid when rung 6 was wired into the loop. MaxTotalTokens deliberately still counts only worker tokens, because it guards the worker's context window, which the critic never occupies.

03

The review after the run

The run ends, and the shell asks the critic what it makes of it. The verdict appears above the status bar with two buttons: Retry with this and Dismiss. It decides nothing — it reports, and leaves the next move to you.

Why here and not at the approval gate

The approval banner was the original target, and it is still the more interesting surface — but it is also the one with a trap in it, and the review needed neither the trap nor the gate to be useful. The banner version remains unbuilt; what follows is why it is harder than it looks, and it is all still true.

Three things that version would have to get right

  • The button must not complete the TaskCompletionSource. The loop thread is parked inside WpfApprovalGate.RequestAsync awaiting ChangesViewModel.RequestApprovalAsync. Only ApproveCommand and RejectCommand may call TrySetResult. A third command runs a side query and raises a property.
  • The approval timeout is a trap. WpfApprovalGate starts a CancelAfter(ApprovalTimeoutSeconds) — 300 by default — the moment the banner goes up, and expiry is a rejection. A Claude round-trip plus your reading time can cross that and silently discard the change. The timer needs to be suspended while an advisory query is in flight, or reset when one returns. This is the single most likely thing to be got wrong.
  • Cancellation still has to win. Pressing Cancel during an advisory query must abandon it and reject the change with the existing wording, The run was cancelled while waiting for approval.

What the query gets is the interesting design question. The minimum is what rung 6 already assembles: the goal, the diff, and the verification evidence. That is enough to catch the example above. It is not enough to catch “this duplicates a helper three files away” — which is the argument for the second option in the next section.

What the review sends, as built

RunReviewer assembles the same three things from the finished run rather than from one edit: the goal off AgentRunResult, every change the run made as a unified diff from IChangeLog, and as evidence the per-change verification summaries plus the stop reason, step count and tool-call validity. The agent's closing statement goes in last, which is the part a critic most often catches — a run claiming success is a claim, and rung 6 never sees it because rung 6 finishes before it is made.

Two runs it does not review

A run that stopped on a step, token, time or cost limit is skipped by default (RunReview:OnlyCompletedRuns): the stop reason already says what happened, and a critic re-deriving it is spend for nothing. A run that changed no files is skipped too — there is nothing to refute. Both say so on screen rather than showing an empty pane.

04

API or Claude Code headless

“Headless Claude” could mean two quite different things, and the choice does not have to be the same for the in-run rung and the post-run review.

Messages APIClaude Code headless
SeesOnly what you put in the promptThe repository, by reading it
IntegrationAn IChatClient behind the existing seamA process invocation
LatencyOne round tripIts own agent loop
CostPredictable per callUnbounded until it stops
CatchesErrors visible in the diffErrors visible only in context
Sandbox storyNetwork call from the harnessA second agent with file access

Recommendation, and what was taken: the Messages API, for both moments. Rung 6 runs on every change and needs bounded cost and latency, which decided it there; the post-run review then got the same transport for free rather than earning a second integration. The CLI remains worth considering only for the review, where nothing is waiting on it and depth is worth seconds — and where a single unbounded call is a decision someone just made deliberately.

The CLI option is a second agent, not a second opinion

Claude Code headless has its own tools, its own loop and its own budget. Nothing in GlassCoder's transcript, metrics or change log would see inside it, so a run that used it would have a hole in exactly the place this project exists to make visible. If it is used at all, it should be read-only and its output treated as text — never as a tool call, and never as something that can write.

05

What must not change

This is the part worth being stubborn about. The project's claim is that a local model, driven by a good harness, can do useful work. A remote critic is compatible with that claim, but only under conditions.

  • The worker stays local. The thing being measured is the worker. If Claude ever writes code that lands, the measurement is gone and the project is answering a different question.
  • Critique:Gates stays false. Your own comment gives one reason — “a model refuting a compiler-verified change is a claim worth reading rather than obeying.” There is now a second: the moment a remote critic can veto, “the local model solved suite-03” stops being a clean result.
  • Suite and ablation runs default to critique off. A hosted critic makes runs non-reproducible and costs money per arm. with-critique stays a named arm you opt into, not part of StandardArms.Default.
  • The critic never sees secrets. Whatever is sent goes through the existing SecretRedactor path, not around it.
  • No critic ever starts a run. The one added here. A retry the reviewer triggered would be a second attempt granted by a model, and a store that cannot tell a first attempt from a granted one reports pass@2 under the name pass@1. So RunReviewer composes the retry goal and stops; pressing the button is the human's job.
  • A retry is a new run, and says so. AgentRunRequest.Attempt defaults to 1 and rides through the result, the run record and RunMetrics, so pass@1 stays computable as the rate over Attempt == 1 once retries exist at all.

There is a positive version of this too. Because critique does not gate, turning it on cannot change pass@1 — so the honest way to justify the feature is to show it moves recovery rate: how often the agent gets out of a hole it has dug. That number already exists on the Metrics surface, and with-critique already exists as the arm that measures it.

Which is also why the checkbox is read once

An earlier sketch of this had three states in a dropdown that could be changed during a session. It was dropped for the same reason: a run whose critic changed at change 7 of 20 is two arms, and every number taken from it belongs to neither. Reading the checkbox when Run is pressed makes the run one arm by construction, and costs nothing — there was never a use for changing it mid-run that a second run would not serve better.

06

The unreachable critic

fixed This was a real defect, and it was the one that had to go before a hosted critic could be trusted at all. CriticPanel.AskAsync caught a failed critic and returned a verdict whose comment contradicted its own arithmetic: 

// A critic that cannot be reached must not silently become an approving vote.
_logger.LogWarning(ex, "Critic {Index} failed; counting it as a refusal to judge");
return new CritiqueVerdict(false, 0d, $"Critic unavailable: {ex.Message}");

Refuted = false, and the tally counted refutations against a threshold — so a critic that could not be reached was arithmetically indistinguishable from one that read the change and accepted it, and the summary reported it under “N/M critics accepted the change”. With three critics and a threshold of two, two unreachable critics plus one genuine refutation produced “not refuted”. Against a local endpoint that is nearly unreachable; against a hosted API it is a Tuesday — a rate limit, a timeout, an expired key.

What it does now

Quorum, as recommended. A verdict carries Available; an unreachable critic — or one that answers with nothing at all — is recorded as not having voted, and the tally runs over the critics that did. Below Critique:Quorum the panel reports inconclusive rather than concluding, and CritiqueResult exposes RespondingVotes, UnavailableVotes and Inconclusive so the transcript shows how much of the panel actually spoke.

The third option on the old list came along for free: a panel that lost a member never claims consensus. When any critic is missing, the summary carries “N of M critics could not be reached, so this is not a full panel” — whichever way the remaining votes fell.

Inconclusive is not acceptance

The distinction is load-bearing downstream. RunReview.Reviewed is false for an inconclusive panel, so the shell offers no retry and does not report a verdict that was never reached. “The critics could not be reached” and “the critics had nothing to say” are different facts, and only one of them is about the code.

07

Decisions, and how they went

QuestionDecision
Does the review share the critic role, or get its own? Its own, and so does every run. Two roles are configured — critic and critic-remote — and the run says which. That is strictly more than the question asked for, and it costs nothing: the roles dictionary was already open-ended, so the only change was to stop CritiqueOptions.Role being the single answer.
Does the critic's opinion reach the agent? Only if you press the button. RunReviewer.ComposeRetryGoal appends the refuting reasons to the original goal and hands it back; the shell starts a new run with it. A rejection the agent cannot read is one it will earn again — but a model deciding when to hand it over is a different feature, and a worse one (§5).
Is the output recorded? Yes, verbatim, as its own record. The run record carries CriticRole and Attempt; the critique itself is a ReviewRecord beside it — every vote with its reason and availability, tokens, cost, duration — routed and redacted like any other record and replayed with its run. It is not a field on the run record, because the run record closes before the review runs: an opinion cannot ride the record of the run it judges.
How much context does it send? Every diff the run made, plus its evidence, capped by RunReview:MaxChangeCharacters so one large edit cannot fill the critic's window. Sending the touched files whole is still worth offering later.
What happens with no API key? The checkbox is disabled and says why. This page previously claimed ICriticPanel.Enabled “already models exactly this” — it did not. See the correction below.
Correction — configured is not reachable

Enabled was _options.Enabled && _clients.ContainsRole(role), and ContainsRole is just a dictionary lookup. It answered “is this role in the config file”, not “can this role be addressed” — so a hosted critic whose key never arrived reported Enabled == true, and the button that trusted it would have failed on press. Exactly what this section said must not happen.

The fix is declared rather than guessed: ModelRoleOptions.RequiresApiKey, and IsUsable derived from it. Inferring it from the endpoint string — treating localhost as free and everything else as paid — would be a heuristic wrong about reverse proxies, LAN servers and gateways alike. CanCritique(role) now checks configured and usable, and the checkbox tooltip distinguishes “critique is switched off” from “this role has no key”, because those are different fixes.

Task 38 is now the one that matters

Everything on this page compiles, is tested, and does nothing until Critique:Enabled is set — so the recovery-rate argument in §5 has still never been run. Rung 6 running inside the loop makes cost-per-solved-task with a hosted critic a real number that nobody has measured, which is precisely the thing task 38 exists to do.

Two smaller threads are open beside it:

  • The review strip does not say the critique is on the record, and there is no UI for browsing past reviews. The transcript view reads step records only; ReviewRecorded is on the bus for whoever adds that.
  • The in-loop critique records a verdict, not a vote-by-vote record. Rung 6 puts its conclusion in the step's verification summary; if task 38 makes rung 6 look interesting, it deserves the same ReviewRecord treatment the post-run review got.

Acceptance, in the style of the existing plan

  • holds A panel with fewer real verdicts than its quorum reports inconclusive, and never reports consensus. (CriticPanelTests, 10 cases.)
  • holds Asking for a critic role that is not configured, or that is missing a key it declared it needs, is reported rather than silently answered by a different oracle.
  • holds Nothing but a human press starts a retry, and a retry is a new run with Attempt = 2 against the same task. (RunReviewerTests.)
  • holds Switching a critic role between wire formats is a configuration change with no code change, and a refusal from the hosted API is a non-vote rather than an exception. (AnthropicTransportTests against a socket-level fake server.)
  • holds A review is written to the transcript and reads back as the same record, with its votes, tokens and cost intact.
  • unmeasured pass@1 is unchanged by enabling critique, and recovery rate improves. Still the right criterion; it needs a real critic and a real suite run, which is task 38.
