Surviving a reboot

Coming back up is not one problem but three: the containers have to start, they have to start in an order, and something has to warm them before the harness arrives.

01

What a reboot actually does

As the setup guide leaves things, the two containers behave differently on boot, and only one of them comes back. That asymmetry is not intentional — it is an artefact of the docker run in section 04 omitting a flag that section 03 has.

ContainerAs writtenOn rebootConsequence
vllm-worker --restart unless-stopped comes back Starts with the Docker daemon. Still cold for 10–15 minutes.
vllm-critic (no policy) stays down GlassCoder's worker role looks healthy while critic fails to connect. The Phase 2 refutation pass is the thing that breaks, which is a long way from the symptom.

The timeline you are actually waiting through

The load cost is not a first-run cost. Rough edge 6 in the setup guide — startup takes forever every time — is exactly this: default safetensors loading re-reads the full weight file on every start. Nothing is cached across a reboot that materially helps, because on a unified-memory box the page cache would have to hold a second copy of something already occupying half of RAM.

0:00
Power onFirmware, kernel, userspace. A minute or two.
~0:01
Docker daemon readyRestart policies fire here. Both containers would begin loading at once if both are set to auto-start.
0:01 – 0:16
Worker reads ~66 GB from NVMe10–15 minutes per the setup guide. The port is open long before the model is servable.
~0:16
First request triggers JITAround 25 seconds. Whoever sends the first request pays it — make that a throwaway curl, not a GlassCoder run.
~0:17
Actually usableTool-call validity is the acceptance test, not "the port answers".
The failure this creates

A machine that reboots overnight looks fine in the morning — docker ps shows the worker running — and the first run of the day either times out or silently loses the critic. Both symptoms point at the harness. Neither is the harness.

02

Choosing a path

There are two ways to make this reliable, and the important thing is to pick one. Docker's restart policies and systemd both want to own the container lifecycle; run both and you get a container systemd thinks it started, Docker restarts underneath it, and neither reports honestly.

Path A

Restart policies

One command per container. Docker brings both up when the daemon starts.

  • Two minutes of work
  • No ordering — both load at once
  • No warm-up
  • Right answer if you rarely reboot

Path B

systemd units

Units start the containers in sequence and gate on readiness before warming.

  • Critic waits for the worker
  • Warm-up runs unattended
  • journalctl tells you what happened
  • Right answer if reboots are routine
Prerequisite for both

Neither path does anything if the Docker daemon itself does not start at boot. This is the default on Ubuntu with the official packages, but confirm it once rather than assume it: 

systemctl is-enabled docker      # → enabled
sudo systemctl enable docker     # if it says disabled
03

Path A — restart policies

If the containers already exist, you do not need to recreate them. docker update changes the policy in place, which matters here because recreating means another 15-minute load. 

# the fix
docker update --restart unless-stopped vllm-critic

# confirm both, don't trust that it took
docker inspect -f '{{.Name}} {{.HostConfig.RestartPolicy.Name}}' \
  vllm-worker vllm-critic

Expect two lines reading unless-stopped. If the critic container no longer exists, recreate it with the policy included:

docker run -d --name vllm-critic --restart unless-stopped \
  --gpus all --ipc=host -p 8003:8000 \
  -e HF_TOKEN="$HF_TOKEN" \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  nvcr.io/nvidia/vllm:26.02-py3 \
  vllm serve <a-small-model-from-another-family> \
    --served-model-name critic \
    --max-model-len 32768 \
    --gpu-memory-utilization 0.10 \
    --max-num-seqs 4

Two differences from the setup guide's version: the restart policy, and -e HF_TOKEN, which section 04 omits and which you need if the critic checkpoint is gated.

unless-stopped versus always

unless-stopped
Starts with the daemon unless you had deliberately stopped it beforehand. A manual docker stop survives the reboot as an intentional decision.
always
Starts with the daemon regardless. Convenient until the evening you stop the critic to free memory, reboot, and find it running again.

unless-stopped is the better default on a box you also use interactively.

04

Path B — systemd units

Path A's weakness is that both containers begin reading tens of gigabytes from the same NVMe simultaneously, and they draw their memory from one shared pool with no coordination. systemd gives you ordering, a readiness gate, and a log.

Do this first

Hand the lifecycle to systemd or to Docker, never both. Before installing the units, clear the policies: 

docker update --restart no vllm-worker vllm-critic

  1. The worker unit

    docker start returns as soon as the container is running, so Type=oneshot with RemainAfterExit=yes is the honest shape — the unit represents "the container has been started", not "the model is ready". Readiness is step 3's job.

    /etc/systemd/system/vllm-worker.service 
    [Unit]
Description=vLLM worker for GlassCoder
Requires=docker.service
After=docker.service network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/docker start vllm-worker
ExecStop=/usr/bin/docker stop --time=60 vllm-worker

[Install]
WantedBy=multi-user.target

    If your HuggingFace cache lives anywhere other than the internal NVMe, add RequiresMountsFor=/path/to/cache under [Unit] so the unit does not start before the mount exists. The setup guide already recommends keeping that cache local, which sidesteps the issue entirely.

  2. The readiness gate

    This is the piece that makes ordering meaningful. It polls until the worker answers, then sends the throwaway request that absorbs the JIT cost. Everything downstream orders after it.

    /etc/systemd/system/vllm-worker-ready.service 
    [Unit]
Description=Wait for the vLLM worker, then warm it
Requires=vllm-worker.service
After=vllm-worker.service

[Service]
Type=oneshot
RemainAfterExit=yes
TimeoutStartSec=1800
ExecStart=/usr/local/bin/vllm-warmup.sh 8001 worker

[Install]
WantedBy=multi-user.target

    TimeoutStartSec=1800 gives thirty minutes — comfortably more than the 10–15 minute load, so a slow boot is not misreported as a failure. The script itself is in section 05.

  3. The critic unit, ordered behind it

    After=vllm-worker-ready.service is the whole point: the critic does not begin loading until the worker has finished and answered, so the two never contend for disk or profile memory against each other.

    /etc/systemd/system/vllm-critic.service 
    [Unit]
Description=vLLM critic for GlassCoder
Requires=docker.service
After=docker.service vllm-worker-ready.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/docker start vllm-critic
ExecStop=/usr/bin/docker stop --time=60 vllm-critic

[Install]
WantedBy=multi-user.target
    Not a hard dependency

    After= without Requires= on the ready unit is deliberate. If the worker warm-up fails, you still want the critic to try — a degraded box is more useful than a dark one, and the journal will tell you which half broke.

  4. Optionally, warm the critic too

    Same script, different port and alias. Small models load fast enough that this is optional, but it costs nothing.

    /etc/systemd/system/vllm-critic-ready.service 
    [Unit]
Description=Wait for the vLLM critic, then warm it
Requires=vllm-critic.service
After=vllm-critic.service

[Service]
Type=oneshot
RemainAfterExit=yes
TimeoutStartSec=900
ExecStart=/usr/local/bin/vllm-warmup.sh 8003 critic

[Install]
WantedBy=multi-user.target

  5. Install and enable

    systemd-analyze verify catches typos and bad directives before a reboot does. Worth running — the alternative is discovering the mistake fifteen minutes into a boot. 

    sudo systemd-analyze verify /etc/systemd/system/vllm-*.service
sudo systemctl daemon-reload
sudo systemctl enable vllm-worker vllm-worker-ready \
                      vllm-critic vllm-critic-ready

# exercise it without rebooting first
sudo systemctl start vllm-worker-ready
systemctl list-unit-files 'vllm-*'
05

The warm-up

Two jobs in one script: block until the endpoint serves the alias, then spend one tiny request on the kernel compilation so a real run never does. It takes a port and an alias, so one file covers both roles.

/usr/local/bin/vllm-warmup.sh 
#!/usr/bin/env bash
set -euo pipefail

PORT="${1:?usage: vllm-warmup.sh PORT ALIAS}"
ALIAS="${2:?usage: vllm-warmup.sh PORT ALIAS}"
DEADLINE=$(( SECONDS + 1500 ))

echo "waiting for ${ALIAS} on :${PORT}"
until curl -sf "http://localhost:${PORT}/v1/models" >/dev/null; do
  if (( SECONDS >= DEADLINE )); then
    echo "timed out waiting for ${ALIAS}" >&2
    exit 1
  fi
  sleep 10
done

# the alias must be the one the harness addresses, not a checkpoint path
curl -sf "http://localhost:${PORT}/v1/models" | grep -q "\"${ALIAS}\"" || {
  echo "endpoint is up but does not serve alias ${ALIAS}" >&2
  exit 1
}

echo "warming ${ALIAS} (absorbs the ~25s JIT)"
curl -sf "http://localhost:${PORT}/v1/chat/completions" \
  -H 'content-type: application/json' \
  -d "{\"model\":\"${ALIAS}\",\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}],\"max_tokens\":3}" \
  >/dev/null

echo "${ALIAS} warm after ${SECONDS}s"
sudo install -m 0755 vllm-warmup.sh /usr/local/bin/vllm-warmup.sh
/usr/local/bin/vllm-warmup.sh 8001 worker    # test it by hand first
Why check the alias

The setup guide notes GlassCoder rejects anything resembling a checkpoint path and requires the alias. Checking for it here means a mis-set --served-model-name surfaces at boot with a clear message, rather than as a connection error in the harness hours later.

On Path A, where there are no units, run the same script from a @reboot cron entry instead: 

# crontab -e
@reboot sleep 60 && /usr/local/bin/vllm-warmup.sh 8001 worker \
  >> /var/log/vllm-warmup.log 2>&1
06

Proving it survives

docker restart is not a test of this. The daemon-startup path is precisely the one that behaves differently, so the only honest check is a real reboot.

  1. Reboot, and wait properly

    sudo reboot
# give it 20 minutes before concluding anything

  2. Both containers running

    docker ps --format '{{.Names}}\t{{.Status}}\t{{.RunningFor}}'

    Two rows. RunningFor should be roughly your uptime, not seconds — seconds means something is crash-looping.

  3. Both aliases served

    curl -s localhost:8001/v1/models | jq '.data[].id'   # → "worker"
curl -s localhost:8003/v1/models | jq '.data[].id'   # → "critic"

  4. On Path B, read the journal

    systemctl status 'vllm-*' --no-pager
journalctl -u vllm-worker-ready -b --no-pager

    The warm-up line reports its own elapsed seconds. That number is your real boot-to-usable figure, and it is worth writing down — if it drifts upward over months, the cache has probably moved off the NVMe.

  5. The acceptance test that matters

    A served alias is a weaker claim than a working tool call. Re-run the setup guide's tool-call check, then confirm validity rate is still near 1.0: 

    jq -r '"\(.taskId)  validity=\(.toolCallValidityRate)"' \
  metrics/metrics.jsonl | tail -3
If GlassCoder runs elsewhere

The harness config addresses http://spark.local:8001/v1. If GlassCoder runs on the 5090 rather than on the Spark, that name resolves via mDNS, which is a second thing that has to come back after a reboot and is outside Docker's control entirely. Testing with curl from the client machine — not from the Spark — is the check that covers it. A static IP or hosts entry removes the variable if it proves flaky.

07

Rough edges

SymptomCause and fix
Critic missing after reboot, worker fine The original condition. No restart policy on vllm-critic; see section 03.
Container restarts but exits repeatedly A restart policy will loop a container that fails for an unrelated reason. Read docker logs --tail 50 vllm-worker before adjusting anything — the sm_121 build mismatch from the setup guide presents exactly this way.
Both start, one hits the OOM killer Concurrent startup on a shared pool. The setup guide's advice to drop the worker to 0.75 when running a critic is what protects you. Path B avoids the contention outright by serialising.
systemd says active, endpoint dead Expected with Type=oneshot on the start units — they report that the container was started, not that the model loaded. The ready unit is the one to check.
Container comes up twice, or fights itself Both a restart policy and a systemd unit are managing it. Pick one; see section 04.
First run after boot still times out Warm-up not running or not finished. On Path A the cron entry's fixed sleep is a guess; the script's own polling loop is what makes it correct, so do not shorten it into a bare sleep.
Reboots happening unexpectedly Unattended upgrades can reboot the box overnight. last reboot and /var/log/unattended-upgrades/ will say. Worth knowing about a machine that takes fifteen minutes to become useful.
08

What I have not verified

Three claims in this document are reasoning rather than measurement. They are called out here so nothing above reads as more settled than it is.

compile cache
The docker run commands mount only the HuggingFace cache. Recent vLLM versions appear to cache compiled kernels separately — possibly under ~/.cache/vllm — which would live in the container's writable layer and survive docker start but not recreation. If that is right, a second -v would make recreations cheaper. Confirm the path against the docs for your pinned image tag before adding it; I have not verified it for the NGC 26.02 build.
memory profiling
The claim that two containers profiling concurrently may each over-estimate available memory follows from how vLLM sizes its KV cache, but I have not confirmed the behaviour on GB10 unified memory specifically. It is the main argument for Path B's ordering — treat it as a plausible risk to test, not an established fact.
readiness endpoint
The warm-up polls /v1/models, which the setup guide already uses and is therefore known to work. vLLM likely also exposes a /health endpoint that would be a more idiomatic probe, but since I cannot confirm its semantics for this build, the script uses the endpoint you have already exercised.
Also unresolved

The critic docker run keeps the setup guide's <a-small-model-from-another-family> placeholder, because the actual checkpoint was never specified. Substitute the real one before running it.

Dated material

Written July 2026 against the setup guide of the same date. Restart policies and systemd semantics are stable; container tags and vLLM's startup behaviour are not. The 10–15 minute load figure is inherited from the setup guide rather than measured here — replace it with your own warm-up timing once you have a few boots on record.
