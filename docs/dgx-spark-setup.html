01

The binding constraint

A DGX Spark holds 128 GB of unified LPDDR5x that the CPU and GPU share, at roughly 273 GB/s. For comparison, an RTX PRO 6000 moves memory around five times faster. So the Spark is not a small machine that runs small models — it is a capacious machine that reads memory slowly.

Autoregressive decoding reads the active weights once per generated token. That gives you a ceiling you can work out on the back of an envelope: 

tokens/second  ≈  273 GB/s  ÷  bytes read per token

70B dense, 4-bit  → ~35 GB/token  →  ~7 tok/s   (unusable for an agent)
120B MoE, 12B active, NVFP4 → ~6 GB/token → ~23 tok/s  (workable)
80B MoE, 3B active,  4-bit  → ~2 GB/token → fast, but a smaller brain

The conclusion is unusually clean, and it is the opposite of the advice you would give for a bandwidth-rich GPU: on this box, pick a sparse mixture-of-experts model, not a dense one. An MoE reads only its active experts per token, so it buys you a large parameter count at a small bandwidth cost. vLLM's own guidance for the Spark is to look for 100–130B total parameters with 10–15B active, in NVFP4.

Why this matters for an agent specifically

GlassCoder measures wall-clock per solved task alongside pass@1 for exactly this reason. A thirty-step run at 23 tok/s is minutes of decoding; the same run on a dense 70B at 7 tok/s is a coffee break. The model that scores better on a benchmark can still be the wrong model for the loop.

What actually fits

NVFP4 weights are roughly half a byte per parameter. After the model, you need room for the KV cache, the container runtime and the OS — vLLM's own recipe leaves ~15% headroom.

Nemotron-3-Super-120B-A12B, NVFP4 ~66 GB weights · 128 GB total
weights ~66 GB KV cache headroom
Qwen3.5-122B-A10B, NVFP4 ~76 GB weights · 128 GB total
weights ~76 GB KV cache headroom
A dense 70B at 8-bit ~70 GB weights — fits, but reads all of it every token
weights ~70 GB KV cache headroom
Nemotron-3-Super-120B-A12B plus an 8B critic ~66 GB + ~9 GB weights · 128 GB total
worker ~66 GB KV critic ~13 headroom
model weights KV cache at 128K context a second, small model OS, runtime, growth

Note that the dense 70B fits perfectly well. Fitting was never the problem.

The last row is the one that surprises people, and it is worth reading carefully: a second model does not come out of the first model's weights. It comes out of the KV cache, which is the only elastic line in the budget — and which the single-model configuration over-provisions anyway. Section 4 does that arithmetic properly.

Picking the model

Named models age fast — treat the table below as a snapshot taken in July 2026 and the criteria under it as the part that lasts.

ModelTotal / activeFit on one SparkWhy

The criteria that outlive the table

  1. Tool-call fidelity first. GlassCoder is a tool-calling harness; a model that writes beautiful code but emits malformed tool calls is worthless to it. Check that vLLM has a --tool-call-parser matching the model's chat template before you download 70 GB.
  2. Sparse, not dense. 10–15B active parameters is the target. Below that you lose capability; above it you lose the wall-clock.
  3. NVFP4 checkpoints where they exist. Blackwell has native FP4 kernels. Prefer a pre-quantised NVFP4 release over quantising a BF16 checkpoint yourself.
  4. Long context, but do not pay for it twice. 128K served is plenty; GlassCoder budgets ~48K and compacts, so you are not sizing the KV cache for the worst case.
03

Standing up vLLM

Check this before anything else

The Spark is arm64 with sm_121, and upstream stable vLLM has not always built for it. Use NVIDIA's container or the CUDA-13 track, not the default vllm/vllm-openai:latest. This is the single most common way to lose an afternoon here.

  1. Confirm the box

    nvidia-smi                       # GB10, driver, CUDA 13
uname -m                         # aarch64
free -g                          # ~128 GB unified
docker info | grep -i runtime    # nvidia runtime present

  2. Pull a container that knows about GB10

    Either NVIDIA's NGC build or vLLM's CUDA-13 track. Pin the tag — "nightly" is a compatibility track, not a reproducible one, and you want the ability to say which build produced a given metrics row. 

    # NVIDIA's build (recommended starting point)
docker pull nvcr.io/nvidia/vllm:26.02-py3

# or vLLM's CUDA-13 track
docker pull vllm/vllm-openai:cu130-nightly

    NVIDIA also publishes step-by-step recipes for this hardware in the dgx-spark-playbooks repository, including a vLLM playbook. Start from there if the container route fights you.

  3. Serve the worker

    Every flag below is load-bearing on this hardware. The two that matter most to GlassCoder are the served name and the tool-call parser. 

    docker run -d --name vllm-worker --restart unless-stopped \
  --gpus all --ipc=host -p 8001:8000 \
  -e HF_TOKEN="$HF_TOKEN" \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  nvcr.io/nvidia/vllm:26.02-py3 \
  vllm serve nvidia/NVIDIA-Nemotron-3-Super-120B-A12B-NVFP4 \
    --served-model-name worker \
    --max-model-len 131072 \
    --gpu-memory-utilization 0.85 \
    --max-num-seqs 4 \
    --enable-auto-tool-choice \
    --tool-call-parser qwen3_coder \
    --guided-decoding-backend xgrammar \
    --trust-remote-code

  4. Wait, then warm it

    First load reads tens of gigabytes from disk — expect 10–15 minutes. The first request after that triggers kernel compilation, around 25 seconds. Fire a throwaway request so a real one never pays for it. 

    curl -s localhost:8001/v1/chat/completions \
  -H 'content-type: application/json' \
  -d '{"model":"worker","messages":[{"role":"user","content":"hi"}],"max_tokens":3}'

What each flag is doing

--served-model-name
The alias clients address. GlassCoder requires an alias and rejects anything that looks like a checkpoint path at startup, so name it worker and keep serving topology out of your configuration.
--gpu-memory-utilization
0.85 on a unified pool. This memory is also the operating system's — take it all and you will meet the OOM killer rather than a clean error.
--max-num-seqs
4. Above roughly four concurrent decode streams the per-token bandwidth tax outweighs what continuous batching gives back. This is a bandwidth limit, not a compute one.
--enable-auto-tool-choice
Without this, tool calls come back as prose in the message body and every one of them is an invalid call.
--tool-call-parser
Must match the model's chat template — qwen3_coder, hermes, llama3_json and others. Wrong parser looks exactly like a stupid model.
--guided-decoding-backend
The grammar engine behind constrained decoding. GlassCoder leans on this hard: it is what makes a malformed tool call structurally impossible rather than merely unlikely.
--reasoning-parser
Only for models that emit reasoning blocks, and only the parser that model documents. Omit it otherwise.
04

Serving the roles

GlassCoder ships two served aliases you host yourself: worker drives the loop and critic runs the refutation pass. You do not need two models to start.

A third alias exists in the source, and is not configured

drafter is declared in ModelRoles for a larger model on hard sub-problems, but nothing in the harness calls it. Its entry in appsettings.json is commented out for that reason, so it no longer appears in the settings dialog and no longer fails the connection check. Uncomment it when there is a call site to serve — see section 9.

There is a fourth role, and it is not served here

critic-remote is the second opinion the desktop app offers per run, and it ships pointed at api.anthropic.com over the Anthropic transport rather than at this box. Nothing on the Spark serves it, and nothing on this page changes because it exists — it is listed here only so a fourth entry under Models:Roles is not mistaken for an alias you forgot to serve. Point it at a local endpoint instead if you would rather keep everything on your own hardware; it is a transport switch and an endpoint.

One Spark, one model

Point both roles at the same endpoint and alias. Phases 0 and 1 only ever use worker, so this costs you nothing until Phase 2.

The caveat to write down

When the critic is the same model as the worker, its blind spots are the worker's blind spots — it will happily approve the reasoning it just produced. That is not a fatal problem, but it means recovery rate from a same-model critic is an optimistic number. Note it next to the metric, or the Phase 2 result will read better than it is.

One Spark, two models

A better arrangement once you reach Phase 2: keep the big MoE as the worker, and put a small dense model from a different family on a second port as the critic. Refutation is a much easier job than authoring, so a 7–14B model does it well and costs little memory.

It looks like it should not fit. It does, and the reason is worth understanding rather than taking on trust.

So the critic costs about 13 GB, and it is paid for out of KV cache the worker was not using. The headroom line even goes up, because dropping the worker to 0.72 hands back more than the critic takes.

The flag that does not do what its name suggests

Lowering --max-model-len does not free memory. vLLM claims --gpu-memory-utilization of the pool and turns whatever is left after weights into KV blocks, regardless of the per-request cap; --max-model-len only bounds how long a single sequence may get. To actually make room for a second model you must lower the utilisation — the context length is how you work out how low you can safely go.

Read the real number off the worker's startup log rather than trusting the table: 

docker logs vllm-worker 2>&1 | grep -i "KV cache size"
# INFO ... GPU KV cache size: 1,234,567 tokens

That figure must exceed Context:MaxContextTokens × --max-num-seqs — 48,000 × 4 ≈ 192K tokens on the settings this guide recommends. If it does, the worker has all the cache it will ever use and the rest was slack. If it does not, raise the worker back towards 0.78 and shrink the critic instead.

In flags, that is one number changed on the worker and one new container. Which model goes in it, and the order to do this in, are both below — the order matters more than it looks. 

# worker: exactly as in section 3, but yielding the slack
    --gpu-memory-utilization 0.72 \
    --max-num-seqs 4

# critic: a second container, a second port, ~13 GB
    --gpu-memory-utilization 0.10 \
    --max-num-seqs 3

Choosing the second model

The criteria are not the worker's criteria, and one of them is much weaker than you would expect — which widens the field considerably.

  1. It never sees a tool, so tool-call fidelity does not apply. The critic panel sends a plain chat request — a system prompt, the change, the evidence — and asks for a verdict. No tools array is ever attached. That means no --enable-auto-tool-choice and no --tool-call-parser on this server, and it means the first and hardest criterion in section 2 is simply not binding here. Models you had to reject as workers because vLLM has no parser for their template are all candidates again.
  2. It must emit JSON, and the failure mode here is quiet. The panel asks for {"refuted": bool, "confidence": number, "reason": string} and reads everything from the first { to the last } — so a markdown fence or a sentence of preamble is tolerated. What is not tolerated is a reply that will not parse, or has no braces at all: the panel then falls back to scanning the raw text for the literal refuted": true. A model that refuses in prose — "I would reject this change" — matches nothing and is recorded as a non-refuting vote carrying a fabricated 0.3 confidence. It does not fail loudly. It silently becomes an approving vote, which is the one outcome a refutation pass must never invent. Only a completely empty reply is counted as unavailable. Keep ConstrainedDecoding.Enabled true for the role, and test this before you trust a recovery-rate number.
  3. A different family, not a different checkpoint of the same lineage. This is the entire reason to spend the 13 GB. If the worker is a Nemotron, a Qwen or Mistral critic decorrelates the blind spots; a second NVIDIA checkpoint of similar ancestry mostly does not, and you would be better off with the one-model setup and an honest caveat.
  4. 7–14B dense, at 8-bit rather than 4-bit. Sparsity buys nothing at this size, and 4-bit saves ~4 GB while landing its damage precisely on calibrated judgement — the confidence number and the refuse/accept boundary are the first things to degrade, and they are the whole output.
  5. Three votes arrive at once. Critique:CriticCount defaults to 3 and the panel fans out in parallel, each critic taking a different lens — correctness, regression, evidence. Match --max-num-seqs to that number.

Do not put a reasoning model in this slot

A critic that thinks before it answers spends the one resource this box is short of — decode tokens — on text nobody reads, and then hands the parser a reply with braces in the scratchpad ahead of the verdict, which is exactly the shape the first-brace-to-last-brace rule mis-reads. All three picks above are plain instruct models for that reason. If you use a reasoning model anyway, suppress thinking at the server rather than hoping it stays quiet, and re-run the calibration check below.

Installing it

  1. Confirm the repo exists, and is not gated

    Cheaper than discovering either fact 15 GB into a download. gated=false means no licence click is needed. 

    M=Qwen/Qwen2.5-7B-Instruct

curl -s "https://huggingface.co/api/models/$M" \
  | jq -r '"\(.id)  gated=\(.gated)  downloads=\(.downloads)"'

# and to see whether a newer generation has landed since May 2026
curl -s "https://huggingface.co/api/models?author=Qwen&sort=downloads&direction=-1&limit=25" \
  | jq -r '.[].id'

  2. Pre-fetch into the cache the container already mounts

    You are downloading the BF16 checkpoint — about 15 GB for a 7B — and quantising at load in the next step. Doing it here rather than inside docker run means a failed download looks like a failed download rather than a container that never becomes ready. 

    huggingface-cli download "$M"        # newer clients: hf download "$M"
du -sh ~/.cache/huggingface/hub/models--Qwen--Qwen2.5-7B-Instruct

  3. Give the worker back its slack first

    This step is the one that bites. The worker is holding 0.85 of a pool the critic is about to want 10% of; start the critic against that and you meet the OOM killer rather than a clean error. Restart the worker at 0.72 before the critic exists — and budget the 10–15 minute reload, because this re-reads every one of those 66 GB. 

    docker stop vllm-worker && docker rm vllm-worker
# then re-run the section 3 command with --gpu-memory-utilization 0.72

  4. Serve the critic

    --quantization fp8 quantises the BF16 weights as they load, so you do not have to find a pre-quantised checkpoint — Blackwell has native FP8 and this is the path with fewest moving parts. Note what is absent: no --enable-auto-tool-choice and no --tool-call-parser, because this role is never sent a tool. 

    docker run -d --name vllm-critic --restart unless-stopped \
  --gpus all --ipc=host -p 8003:8000 \
  -e HF_TOKEN="$HF_TOKEN" \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  nvcr.io/nvidia/vllm:26.02-py3 \
  vllm serve Qwen/Qwen2.5-7B-Instruct \
    --served-model-name critic \
    --quantization fp8 \
    --max-model-len 32768 \
    --gpu-memory-utilization 0.10 \
    --max-num-seqs 3 \
    --guided-decoding-backend xgrammar

  5. Confirm both models are up and the box is not full

    curl -s localhost:8001/v1/models | jq -r '.data[].id'   # → "worker"
curl -s localhost:8003/v1/models | jq -r '.data[].id'   # → "critic"
free -g                                                 # used should leave ~20 GB

    Then run the calibration check below. A critic that serves and answers is not yet a critic that judges.

What the second model actually buys, and what it does not

It buys independence, not speed. An 8B dense at 8-bit reads ~8 GB per decode step, so on this box it runs at roughly the same tokens per second as the 120B MoE reading ~6 GB of active experts. The critic is not the fast one; it is the uncorrelated one.

What makes co-residency affordable is the shape of the work. Critique is a rung of the verification ladder and the loop awaits it, so the worker is not decoding while the panel votes — the two models are almost never hot at the same time. And a verdict is a long diff in and perhaps eighty tokens out: prefill-heavy, decode-light, which is exactly the shape this hardware is good at (~1,884 tok/s prefill against ~23 tok/s decode).

Do not serve a drafter tonight

The second container you start should be the critic, which is wired. drafter is a seam held open for later, not a model you are missing, and its config entry is commented out — serving one would spend memory that nothing requests.

Check it is calibrated, not merely running

The system prompt tells the critic to default to refuted: true whenever the evidence does not establish correctness. A model too small for the job discovers that refusing everything is always defensible, which reads as diligence and is noise. Give it a change whose evidence is visibly inadequate and confirm it says so in JSON: 

curl -s localhost:8003/v1/chat/completions \
  -H 'content-type: application/json' -d '{
  "model": "critic", "temperature": 0,
  "messages": [
    {"role":"system","content":"You are a reviewer whose job is to REFUTE a proposed code change. Judge it through this lens - correctness: does the change actually do what the goal asked, in every case the goal implies. Default to refuted:true when the evidence does not establish that the change is correct. Reply with JSON only: {\"refuted\": bool, \"confidence\": number between 0 and 1, \"reason\": string}."},
    {"role":"user","content":"Goal:\nMake Divide throw on a zero divisor.\n\nProposed change:\nreturn b == 0 ? 0 : a / b;\n\nEvidence offered:\nThe project compiles.\n\nCan you refute this change?"}
  ]}' | jq -r '.choices[0].message.content'

Two things must hold. The reply must contain a brace-delimited object that parses — check it with | jq rather than by eye, because the fallback path above will happily turn a prose refusal into an approving vote and never tell you. And refuted must be true: the change returns a value where the goal asked for a throw, and "it compiles" does not establish otherwise. A critic that accepts this will accept anything, and its recovery-rate contribution is worthless.

Then run the opposite case — a change that is plainly correct, with a passing test as its evidence — and confirm it does not refute. A model that refutes both is not being careful, it is being useless in the direction that looks like rigour. That second check matters most if you ever set Critique:Gates, which lets a refutation block the change rather than merely be reported alongside it.

05

Why a small model can judge a large one

A 7B critic reviewing a 120B worker looks like the wrong way round, and the objection deserves an answer rather than a reassurance: the small model knows less about code, it deliberates less, and it cannot look anything up. The answer is not that it is secretly good enough. It is that it is asked a different question, and the harness is built on the assumption that its answer is noisy.

It is not asked to be a better coder

The panel never asks the critic to write, fix or improve anything. It asks it to refute, through one of three lenses that rotate across the votes:

  1. correctness — does the change do what the goal asked, in every case the goal implies
  2. regression — does the change break behaviour that other code depends on
  3. evidence — does the evidence given actually prove the change works, or only that it compiles

The third is barely a coding question. It is reading comprehension over three texts: the goal says one thing, the diff does another, the evidence claims a third. Noticing that the goal asked for a throw, the diff returns a value, and the evidence offered is "it compiles" takes no deep knowledge of the system. A 7B is genuinely capable at that class of mismatch.

Underneath it is an asymmetry of output spaces. The worker must produce exactly-right code from an unbounded set of candidates. The critic produces one bit and a sentence of justification. That is what makes the verification side affordable at a smaller size.

The limit of that argument, stated plainly

The asymmetry holds for shallow mismatches and collapses for deep ones. A race condition is harder to spot than to write. A small critic will miss that entire class and report no refutation with every appearance of having looked. Verification is easier than generation for the checks this panel actually runs — not in general.

What "no reasoning, no web" actually costs

A non-reasoning model still computes; it just does not deliberate at length in visible tokens. For "does this diff match this goal" a single pass is usually enough, because the judgement is closer to perceptual than to multi-step. The advice in section 4 to avoid reasoning models is nonetheless a trade rather than a free win: a reasoning critic would likely be more accurate, and that accuracy was traded for decode tokens — the scarce resource on this box — and for a reply the brace parser can survive.

The missing web access costs nothing here, because the critique is closed-book by design. The goal, the change and the evidence are all in the prompt. The critic is never asked whether a library was the right choice, only whether this diff matches this goal. Nothing it needs sits outside the window.

What you are buying is independence, not capability

Section 4 notes that a same-model critic is optimistic, because its blind spots are the worker's blind spots. Run that observation backwards and it is the whole answer:

The principle

A weaker but independent critic can contribute more information than a stronger but correlated one. Independence is a property of the ensemble, not of any member of it. That is why the family of the second model matters more than its size, and why the budget is spent on decorrelation rather than on the largest critic that would fit.

A smoke detector is not smarter than a firefighter. It is cheap, independent and never gets bored — and nobody asks it to put out the fire.

The harness already assumes the sensor is noisy

Which is what makes a mediocre critic worth having rather than dangerous:

Three votes, three lenses
Independent calls that never see each other's verdicts, so there is no groupthink to amplify one bad read.
Refute, not review
Deliberately fighting sycophancy. "Is this good?" invites agreement from a model that has just been shown a plausible diff; "find what is wrong with this" is a job it can fail at honestly.
Gates defaults to false
A refutation is reported beside the run rather than allowed to block it. A wrong critic costs you a noisy metric, not blocked work.
Unavailable is not approval
A critic that did not answer is excluded from the tally and counts against quorum. Below quorum the panel is inconclusive, which is a different fact from having accepted the change.
It is rung 6, not rung 1
Compilation, tests and lint run first and are deterministic. The critic is left the residue — "this builds, it passes, and it still is not what was asked" — which is exactly the class no compiler can catch.

Where it will fail

FailureWhat it looks like
Subtle defects Concurrency, numerics, security. Confident silence — the most expensive shape a wrong answer can take.
Missing project context Conventions and invariants that are real but nowhere in the prompt. It cannot refute what it was never shown.
Confidence is decorative A 7B is poorly calibrated, and the parser's fallback path hardcodes 0.3. Read the verdict; do not weight by the number.
False negatives are silent The dangerous direction. An approving vote leaves no artefact to inspect, and the brace-parser fallback in section 4 can manufacture one out of a prose refusal.

The critic raises the floor. It does not raise the ceiling, and it is not a substitute for the deterministic rungs beneath it.

So do not be confident — measure

The honest position is that a 7B critic is a cheap, noisy sensor, and whether it earns its 13 GB is an empirical question rather than an architectural one. Seed a handful of changes you know are broken and a handful you know are sound, then measure the two rates separately: what fraction of the broken ones it catches, and what fraction of the sound ones it refutes anyway. A critic that refutes everything looks like rigour and is noise.

The tier above it already exists

This is the cheap tier of a two-tier oracle, which is what critic-remote is for. The local model votes on every run because it costs nothing to leave switched on; the hosted frontier model is spent on the runs that warrant it, per run, from the desktop app. The 7B is the floor rather than the ceiling — and the point of a floor is that it is always there.

06

Wiring GlassCoder to it

In config/appsettings.json, the roles point at the ports you just opened. Nothing else in the harness needs to know what hardware this is. The desktop app's settings dialog edits the same roles if you would rather not hand-edit JSON — and can check each one against the box before you trust it. 

"Models": {
  "DefaultRole": "worker",
  "Roles": {
    "worker": {
      "Endpoint": "http://spark.local:8001/v1",
      "ModelAlias": "worker",
      "TimeoutSeconds": 900,
      "Temperature": 0.2,
      "ConstrainedDecoding": {
        "Enabled": true,
        "StrictToolSchemas": true,
        "SingleToolCallPerStep": true,
        "GuidedDecodingBackend": "xgrammar"
      }
    },
    "critic": {
      "Endpoint": "http://spark.local:8003/v1",
      "ModelAlias": "critic",
      "Temperature": 0.0
    }
  }
}

Raise to 900. A long prefill plus a slow decode can legitimately exceed the 600 default on a large prompt.
Agent:MaxWallClockSeconds
At ~23 tok/s, a thirty-step run is genuinely minutes. Budget 1800 rather than 900, or you will record time-limit stops that are really just honest slowness.

MaxDegreeOfParallelism

07

Verifying it properly

"The endpoint returns text" is a much weaker claim than "the endpoint calls tools correctly". Check the second one, because that is what the harness needs.

  1. The endpoint answers

    curl -s localhost:8001/v1/models | jq '.data[].id'   # → "worker"

    From the desktop app, Settings… → Test connection does this and the completion below it in one press, per role, against the endpoint and key the harness will actually use — and reports which of the four stages failed rather than a single verdict. See the settings guide. The curl above stays the right tool when you are on the box itself and the app is not.

  2. It emits a real tool call

    The response must contain a tool_calls array. If the function name and arguments appear as text inside content instead, your parser flag is wrong — fix that now, not after a confusing run. 

    curl -s localhost:8001/v1/chat/completions \
  -H 'content-type: application/json' -d '{
  "model": "worker",
  "messages": [{"role":"user","content":"Read the file src/Program.cs"}],
  "tools": [{"type":"function","function":{
    "name":"read_file",
    "description":"Read a text file from the workspace.",
    "parameters":{"type":"object","properties":{
      "path":{"type":"string","description":"Repo-relative path."}},
      "required":["path"]}}}],
  "tool_choice": "auto"
}' | jq '.choices[0].message.tool_calls'

  3. GlassCoder resolves against it

    glasscoder tools                     # config binds, services resolve
glasscoder run --repo /path/to/repo \
  --goal "Find where retries are implemented and explain the backoff."

  4. Read the number that decides everything

    Tool-call validity rate is the acceptance test for this whole setup. Near 1.0 means the seam is healthy and you can start measuring the harness. Anything much lower is a server or parser problem, not a model problem — go back to step 2. 

    jq -r '"\(.taskId)  validity=\(.toolCallValidityRate)  steps=\(.steps)"' \
  metrics/metrics.jsonl | tail -5

  5. Take the Phase 0 baseline

    Read-only, so nothing can be damaged, and it gives you the number every later change is measured against. 

    glasscoder suite --config config/phase0.json
08

Budgets that now make sense

Published figures for a 120B/12B NVFP4 model on a single Spark, to calibrate what "slow" and "broken" look like:

MeasureObservedWhat it implies
Decode ~23 tok/s A 500-token step takes ~22s. Ten steps is about four minutes of pure decoding.
Prefill, short prompt ~140 tok/s Small prompts are dominated by fixed overhead.
Prefill, long prompt ~1,884 tok/s Prefill parallelises well — it is decode that is bandwidth-bound.
Time to first token 0.4 – 3.9 s Scales with prompt length. This is why context compaction pays on every step.
The measurement this hardware makes interesting

Because prefill is fast and decode is slow, anything that shortens the output is worth more here than anything that shortens the input. That is a real, testable hypothesis — and it is exactly what the ablation runner exists for. Run no-context against baseline and see whether the context you are loading actually buys enough to justify itself.

09

If one Spark isn't enough

Two Sparks connect directly over their 200GbE ConnectX-7 ports, giving a combined 256 GB pool; larger clusters go through a switch. People report running 300B-class MoE models across four units, and current flagship open-weight coding models need roughly that.

Before you buy a second box, be honest about which problem you have:

Model too big
More Sparks genuinely help — you are buying memory capacity.
Runs feel slow
More Sparks help far less than you would hope. Aggregate bandwidth rises but so does interconnect latency, and decode stays the bottleneck. Try a smaller active parameter count first.
Want a real critic
A second small model on the same box is usually the better spend than a second box.

Whatever you choose, keep the aliases stable. Moving a role GlassCoder already calls onto a second machine is one line of configuration and no code change — that is the point of addressing aliases rather than checkpoint paths.

The drafter is the exception, and it is worth being exact about why

Standing drafter up on a second machine is not config-only today. Uncommenting its entry in appsettings.json and pointing it at that machine gets you a role the factory will happily build a client for — and nothing that ever asks for one. There is no call site. The seam is open at the configuration layer and not yet at the call layer, so the work is a harness change (decide what a drafter is handed, and when), not an endpoint change.

10

Known rough edges

SymptomCause and fix
Container exits immediately, CUDA arch error Stable upstream vLLM built without sm_121. Use NVIDIA's NGC image or the CUDA-13 track, or follow the DGX Spark playbook to build with sm_120 forward compatibility.
Tool-call validity near zero Almost always --enable-auto-tool-choice missing, or a --tool-call-parser that does not match the chat template. Verify with the raw curl above before suspecting the model.
First GlassCoder run times out Model load is 10–15 minutes and first-request JIT is ~25s. Warm the server before pointing the harness at it.
OOM killer, or the desktop stalls --gpu-memory-utilization too high. This pool is shared with the operating system. Back off to 0.80 and re-measure.
Throughput collapses under load Too many concurrent sequences for the bandwidth. Lower --max-num-seqs, and keep GlassCoder's fan-out below it.
Startup takes forever every time Default safetensors loading. Look at faster loaders, and keep the HuggingFace cache on the internal NVMe rather than a network mount.
Quality drops after long runs If you enabled --kv-cache-dtype fp8 to save memory, turn it back off — it trades predictability for space. Prefer compaction, which GlassCoder already does.
