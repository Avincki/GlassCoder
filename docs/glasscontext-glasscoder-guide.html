Producer and consumer

GlassContext documents the code your project will call, and plans the code your project still needs. GlassCoder then writes that code and reports what an oracle said about it. This is how to configure both, what the loop looks like on one small C# application, and exactly which files change hands — including the one field that, if it is wrong, makes every number the pair produces quietly meaningless.

The seam

GlassContext is a Windows desktop preprocessor. It reads source it will never write to and produces the context a coding agent needs before it can write anything: a root CLAUDE.md for Claude Code, a budgeted CLAUDE.agent.md for a local worker, a docs/llms/ documentation tree, and a WORKPLAN.md of dependency-ordered tasks carrying stable slugs and per-task test oracles. Every step is human-gated: Claude drafts, a second-provider reviewer scores against a rubric, the developer accepts, and only then does GlassContext write the file.

GlassCoder is a local AI coding-agent harness. It runs a worker model against a repository through a sandboxed tool set and a verification ladder — syntax, compile, analyzers, tests, critique — and records what happened to metrics.jsonl. It has a WPF front end and a console host (glasscoder run | suite | ablate | workplan | fixtures | tools).

read this before the diagram

docs/llms/ is not documentation of the code GlassCoder is about to write. It cannot be: that code does not exist when the plan is generated. It is documentation of the code the new project will consume — a sibling library whose source you have but whose binary you link, an archived legacy tree, an internal framework. It is an API reference for the dependency surface, produced so the worker can look a signature up instead of inventing one.

The project’s own source is what comes out of the other end of the pipeline, and it is GlassCoder that writes it.

The contract, artifact by artifact

the one rule

AgentRunRequest.TaskId must be the task’s slug, never its position. GlassContext joins run outcomes onto plan tasks by that key and by nothing else, because a plan is renumbered whenever it is reordered. A runner that passes "workplan-3" produces metrics that silently attach to whatever is third next week — and neither application will tell you.

There is a second coupling, running the other way: GlassContext can call GlassCoder as the worker behind its own IIntentAgentRunner seam, so its documentation passes run on the local box instead of on a metered API. See §5.3.

01

Configuring GlassContext

GlassContext keeps three kinds of state, in three places, and the distinction matters the first time you move a machine or share a project with a colleague.

WhatWhereTravels with the project?
Active configuration %APPDATA%\GlassContext\settings.json No — one active project per machine
Saved project bundle <anywhere>\<Name>.glassproj Yes — commit it beside the repo it describes
API keys Windows Credential Manager
GlassContext:Claude · :OpenAI · :Grok		 Never — no key is written to any file or log

1.1 Four kinds of input, and what each one becomes

This is the part of Module A that decides what docs/llms/ ends up containing, and it is worth being deliberate about. The four source roots are not interchangeable — they travel by different routes and end up in different places.

SettingWhat you point it atWhat GlassContext does with it
RepoRoot the project being built Reads the solution graph and any existing rules; writes the managed CLAUDE.* files, WORKPLAN.md and the docs tree. Never writes into its source tree — PathGuard enforces that at every write point.
SiblingRepoRoots the library your project links against, whose source you have Walks its src/ and writes one documentation page per file. This is the dependency reference, and where it lands decides whether GlassCoder can read it — see §2.2. An ordinary local clone is writable, so the pages go into the sibling’s own docs/llms/; only a genuinely read-only sibling falls back to CLAUDEDOCS_<name>/ inside your repository.
LegacySourceFolders archived reference source you must not edit Copies it to legacy/ in your repository and documents it into docs/llms/legacy/, so it shows up in the catalogue.
ExamplesFolders small projects showing how the library is meant to be used Not documented at all. Inlined verbatim into the drafting prompt as <example_project> blocks, and offered as read-only roots to the intent-enrichment agent. They shape the generated context; they do not become pages.

Module B exposes the first three as independent switches — main repo, sibling DLL, legacy — plus examples for the prompt. On a project whose source GlassCoder has not written yet, main repo produces nothing useful and can be left off; the passes that matter are the sibling and the legacy trees.

1.2 The rest of Module A

SrcSubFolder
Usually src. Defines what counts as a module, and sets the mirror root for every documentation tree — the sibling’s included.
FileExtensions
Default [".h", ".cs"]. If the dependency is a C# library, trim it to [".cs"]; a header walker on a repository with no headers is cost with no output.
GitUsername
From git config user.name, lowercased, spaces to hyphens. It must never normalise to agent: CLAUDE.agent.md is regenerated on every run and would silently eat CLAUDE.<username>.md. ProjectConfigService.Validate rejects that configuration rather than letting it happen.
ClaudeModel · ReviewerProvider · ReviewerModel
Drafting is Claude; reviewing is a different provider (OpenAI or Grok) on purpose, so the reviewer is not scoring its own prose. ScoreThreshold (default 7.0) is advisory — it never blocks an accept.
UniversalRules
Up to eight bullets that constrain every edit in this repository. They live in the configuration rather than only in the generated CLAUDE.md, because that file is regenerated on every run — and they are what FILE 8 carries to GlassCoder’s worker as “rules that constrain an edit”.

1.3 The knobs with no UI

The agent block and the per-file intent block are set by hand in settings.json. They survive Apply Settings — Project Setup clones the loaded configuration and assigns only its own fields, so properties it does not know about round-trip untouched.

two CLI paths, on purpose

agentCliPath names a Claude Code install; glassCoderCliPath names GlassCoder’s console host. One shared path would launch the wrong binary the moment agentProvider changed.

Source files reach an API only when you tick the per-session consent box, and the boxes reset every session — no silent opt-in carried over from last time. Prompts, drafts and reviewer responses are never logged; LogRedaction is applied at the single logging choke point and to every HTTP error body.

02

Configuring GlassCoder

No endpoint, alias, budget or limit is hardcoded anywhere in GlassCoder. Everything comes from configuration, layered in a fixed order — and the order is the part people get wrong, because a saved setting that outranked an ablation arm would make an arm mean something different on every machine.

#LayerWhereScope
1Shipped defaults config/appsettings.json lowest — the documented baseline
2Per-user settings %APPDATA%\GlassCoder\settings.json
(the WPF Settings dialog)		 this machine, every project
3Per-project settings <RepoRoot>\.glasscoder.json this repository — commit it
4Environment GlassCoder__Agent__MaxSteps=50 this shell
5Arm file --config config/arm-*.json highest — this run only

Generated data — logs, metrics, transcripts — anchors to %LOCALAPPDATA%\GlassCoder, not to the working directory, so a dotnet clean cannot erase run history. Override with GLASSCODER_DATA_DIR; an absolute path in configuration is honoured as-is. That detail matters in §5, where GlassContext goes looking for the metrics file.

2.1 The six settings this pairing turns on

Out of the box, GlassCoder is configured as a self-contained ablation harness: nothing is writable, no root context is loaded, and the only readable root is the repository itself. Consuming a GlassContext-managed project means changing six things.

SettingDefaultSet it toWhy
Context:RootContextFiles [] ["CLAUDE.agent.md"] Without it the worker has no product identity unless the goal string carries one. This is the whole GlassContext value proposition, expressed as one array — and a file that cannot be found is skipped, not fatal. See below.
Context:MaxRootContextTokens 6000 leave it FILE 8 is budgeted to sit far below this. A document that needs the ceiling raised is the wrong document — fix the profile, not the budget.
Workspace:RepoRoot "." the target repo Or pass --repo. Resolved against the process working directory.
Workspace:WritablePaths [] ["src", "tests"] Empty means nothing is writable. A workplan run against the default produces no code at all — the most common first-run surprise.
Workspace:ReadablePaths [] = the repo root see below The dependency documentation has to be inside a readable root, or the worker cannot retrieve the page the profile just told it to read.
VerificationLadder:TestFilter null leave it null The workplan runner overrides it per task from the Oracle: line. A global filter here would fight the plan.

2.2 Getting the dependency docs inside the workspace

This is the step that most often goes wrong, and it goes wrong quietly. GlassCoder’s workspace is one repository: with ReadablePaths empty, the only readable root is RepoRoot. GlassContext, meanwhile, decides where a sibling’s documentation lands by probing whether the sibling is writable — it writes a temporary file and deletes it. An ordinary local clone passes that probe, so the default outcome is that the pages are written into the sibling repository, outside the workspace GlassCoder will run in.

Neither application is wrong; they simply have different ideas of where the boundary is. Pick one of these two layouts on purpose.

LayoutHow you get itTrade-off
Default. Docs stay in C:\repos\Acme.Billing\docs\llms\ happens on its own; then add the root to GlassCoder:
"ReadablePaths": [ ".", "C:\\repos\\Acme.Billing\\docs" ]		 one copy shared by every consumer of the library and regenerated where it belongs — but the . must be listed too, because a non-empty list replaces the default root rather than adding to it, and the absolute path is machine-specific
Docs land in CLAUDEDOCS_Acme.Billing/ inside the target repo only when the sibling is genuinely read-only — a checked-out tag, a network share, ACLs must be forced everything is inside one workspace and .glasscoder.json stays portable, but you cannot ask for this layout: it is a consequence of the sibling’s permissions

The worked example below takes the first. Whichever you choose, check it after the first Module B run rather than assuming — the log line says which one happened (Writing docs into sibling repo or falling back to CLAUDEDOCS_…).

The absolute path is needed only in the configuration. What the worker passes to read_file is resolved against the repository root before the readable-root check, so a plan can say ../Acme.Billing/docs/llms/Billing/VatCalculator.md and stay portable across machines that check the two repositories out side by side. 

// C:\repos\InvoiceKit\.glasscoder.json — committed, no secrets.
// The file's own location is the repository root; nothing inside it names a path
// that would go stale the moment the repo is cloned somewhere else — except
// ReadablePaths, which has to, because the dependency lives outside this tree.
{
  "GlassCoder": {
    "Context": {
      "RootContextFiles": [ "CLAUDE.agent.md" ]
    },
    "Workspace": {
      "WritablePaths": [ "src", "tests" ],
      // "." first: a non-empty list REPLACES the default root, it does not extend it.
      // Drop the second entry and every retrieval of a dependency page is denied.
      "ReadablePaths": [ ".", "C:\\repos\\Acme.Billing\\docs" ]
    },
    "VerificationLadder": {
      "VerifyAppliedChanges": true,
      "ProjectPath": null        // null works it out from the edited files
    },
    "Agent": {
      "MaxSteps": 30,
      "MaxWallClockSeconds": 900
    }
  }
}
both failure modes are silent

A root context file that cannot be resolved is skipped with a log warning, not treated as an error. Misspell the name, forget to regenerate it, or point --repo somewhere else, and the run proceeds happily with no product identity at all — which is to say, as an unlabelled no-context arm whose numbers will be compared against everything else as though it were not.

A denied documentation path fails the same way: the read_file call is refused, the model moves on, and the run looks like one where the documentation simply did not help. Before trusting a first comparison, check the log for Root context file … was skipped and confirm the transcript shows at least one dependency page actually being read.

2.3 The rest, briefly

The WPF Settings dialog covers the same surface in ten tabs — Models, Workspace, Agent, Verification, Retrospective, Sandbox, Retrieval, Git, Logging, Telemetry — and writes to layer 2. Four are worth a deliberate decision before the first workplan run:

  • Models — one entry per served role. worker at :8002 and critic at :8003 are local; critic-remote speaks the Anthropic transport and is offered only when its key is present, so a configured-but-unreachable critic does not become a button that fails on press.
  • Sandbox — Mode: "Docker" with AllowUnsandboxedExecution: true. Leave both. The alternative to a host fallback is not a safer build, it is no build at all: with Docker absent every build refuses in milliseconds and the agent writes code with zero compiler feedback, then reports a success it could not have verified.
  • Retrieval — off by default, and it can stay off here. The point of the documentation tree is that the dependency API is already in the workspace; reaching Microsoft Learn is a different question, and worth measuring separately.
  • Approval — RequireApprovalForWrites: false for the console host, which cannot ask a human and fails closed if told to. Push approval stays on: a write can be reverted from the change log, a push has left the machine.
check before the first run

glasscoder tools prints the tool surface the model will see, and glasscoder help is the cheapest launchable verb — GlassContext uses exactly that to decide whether the host is on PATH. If WritablePaths is still empty, the run will complete, report progress, and change nothing.

03

The workflow, end to end

A worked example, small enough to hold in one head.

RepositoryRoleState at the start
C:\repos\InvoiceKit the project to be built — WPF app + Core library + xUnit tests solution, three empty projects, a handful of tests written by hand
C:\repos\Acme.Billing in-house billing library — ships to InvoiceKit as a DLL finished, read-only, ~200 source files the agent will never see compiled
C:\repos\Acme.Samples\* two sample apps showing how the library is meant to be used finished; prompt material, not documentation input

The job: build InvoiceKit’s invoicing core on top of Acme.Billing, without reimplementing arithmetic the library already provides. That last clause is the whole reason the documentation pass exists — a worker that cannot see Acme.Billing.VatCalculator will cheerfully write its own, and it will be subtly wrong about rounding.

  1. Point GlassContext at all of it — Module A

    RepoRoot = C:\repos\InvoiceKit, SiblingRepoRoots = [C:\repos\Acme.Billing], ExamplesFolders = [QuickInvoice, BatchExport], FileExtensions = [".cs"]. Enter the Claude and OpenAI keys once; they go to Credential Manager. Project → Save As → InvoiceKit.glassproj.

  2. Document the dependency — Module B

    Tick sibling DLL; leave main repo off, because InvoiceKit’s src/ is what GlassCoder is about to write and there is nothing there to document. DocGen walks Acme.Billing/src/ and writes one page per file, path-mirrored, with a machine-readable .intent.json beside each. Acme.Billing is an ordinary writable clone, so the pages land in C:\repos\Acme.Billing\docs\llms\ — outside the repository GlassCoder will run in. That is what §2.2’s ReadablePaths entry is for; without it every retrieval of one of these pages is denied, and the run looks like one where the documentation did not help.

    With intentEnrichmentEnabled, each page also gets an agent-written purpose, behaviour and gotcha section — the things a signature does not say. This is the expensive pass; it runs once per dependency release, not once per task.

  3. Draft, review, accept the context — Modules C and E

    Module C runs the human-gated loop: Claude drafts from the project description, the solution graph and the inlined <example_project> blocks; the reviewer scores it on six criteria and returns remarks; you tick the remarks worth incorporating and press Go again. On Accept, GlassContext writes CLAUDE.md (FILE 1) and regenerates CLAUDE.agent.md (FILE 8). FILE 8 is what GlassCoder loads, so review it on its own rubric — conciseness and actionability are the criteria that matter, and the token count is reported beside the score.

  4. Generate the plan — Module D

    Claude proposes dependency-ordered tasks from the accepted context. Edit them until each is a single agent’s worth of work, then make sure of the two v2 fields that matter: a stable <!-- task:slug -->, and an **Oracle:** line naming the test class that decides completion. Save → WORKPLAN.md at the repository root.

    the generator cannot see the dependency

    Module D’s prompt is given one input: the accepted Module C draft. The documentation tree you just spent Module B generating, the .intent.json sidecars and the example projects are all absent from it. Whatever the plan knows about Acme.Billing is whatever survived into CLAUDE.md as prose.

    In practice that means editing the generated tasks to name the pages the worker should read, as the task in §4.2 does. The plan is the only place that pointer can currently come from.

    who writes the tests — decide this explicitly

    The shipped prompt tells Claude the oracle may name “a real test class from the context, or one the task itself creates”. On a project being built from near-nothing the second branch is the common one — and it means the agent writes both the implementation and the test that grades it. The checkbox then records that the model agreed with itself.

    The harness cannot detect this: a passing filter is a passing filter. So it is a decision you make when reviewing the plan. Where a task’s correctness actually matters, the test has to come from somewhere the agent is not — written by hand before the run, generated by Module F from a finished reference project, or carried in from the sample apps — and tests/ should come out of WritablePaths for that run so it stays ground truth.

    A task with no oracle at all is still allowed: the harness runs it and refuses to tick it, because the checkbox records oracle outcomes and not the model’s opinion. An unticked box you have to judge yourself is more honest than a ticked one that means nothing.

  5. Wire the harness

    Drop the .glasscoder.json from §2.1 into InvoiceKit and commit it. That is the entire integration: no plugin, no build step, no shared assembly. Both applications talk through files.

  6. Run the plan

    > cd C:\repos\InvoiceKit
> glasscoder workplan --plan WORKPLAN.md

  workplan  4 unticked of 5
  [1/4] invoice-line-model              attempt 1
        ladder: syntax ok · compile ok · analyzers clean · tests 6/6
        oracle: InvoiceLineTests              PASSED   ticked
        11 steps · 23,400 tokens · 2.6m
  [2/4] totals-via-acme-billing         attempt 1
        read C:\repos\Acme.Billing\docs\llms\Billing\VatCalculator.md  (step 4)
        ladder: compile ok · tests 8/9
        oracle: InvoiceTotalsTests            FAILED   not ticked
        InvoiceTotalsTests.UsesLibraryRounding — expected 12.35, got 12.34
        22 steps · 58,900 tokens · 6.1m
  stopped at totals-via-acme-billing (task 2 of 4)
> echo %ERRORLEVEL%
1

    The runner stops at the first failure, and that is arithmetic rather than caution: the tasks are dependency-ordered, so everything after a failed prerequisite measures the prerequisite rather than itself. Re-invoking resumes at the first unticked task — the file on disk is the state — with the attempt number incremented in the metrics.

  7. Read the failure — it is usually about the dependency

    Task 2 rounded the total itself instead of letting Acme.Billing.Money do it. The agent did read the page, so the failure is not that the documentation was missing — it is that the page did not say “never round a Money; it rounds on construction”. That is a gotcha, and gotchas are what the intent-enrichment pass exists to capture. Fix it in the source of truth — re-run Module B for that one file, or add the constraint to the task description — and re-run: 

    > glasscoder workplan --plan WORKPLAN.md
  workplan  3 unticked of 5
  [1/3] totals-via-acme-billing         attempt 2
        oracle: InvoiceTotalsTests            PASSED   ticked

  8. Import the outcomes — back to Module D

    Import metrics reads metrics.jsonl and annotates the plan by slug: attempts, last stop reason, whether the oracle passed on attempt 1. Two attempts on one task is a signal about how that task — or that documentation page — was written. See §5.

4.1 CLAUDE.agent.md — the profile the worker carries

The same facts as CLAUDE.md, written for a model on a token budget rather than for a session with a human in it. # InvoiceKit

## What this is

InvoiceKit is a .NET 8 WPF desktop application for issuing customer invoices. It is a
front end over Acme.Billing, which owns every monetary calculation. InvoiceKit models
the document, the workflow and the print layout; it does not do arithmetic.

## Build and test

- Build: `dotnet build InvoiceKit.sln`
- Test: `dotnet test InvoiceKit.sln`
- One class: `dotnet test InvoiceKit.sln --filter <TestClassName>` — prefer this while iterating.

## Solution

| Project | Kind | Framework | References | Tested by |
|---|---|---|---|---|
| `InvoiceKit.App`   | WPF app | net8.0-windows | InvoiceKit.Core  | InvoiceKit.Tests |
| `InvoiceKit.Core`  | library | net8.0         | Acme.Billing.dll | InvoiceKit.Tests |
| `InvoiceKit.Tests` | tests   | net8.0-windows | App, Core        | — |

## Rules that constrain an edit

- Core has no UI dependency. WPF types stay in InvoiceKit.App.
- Money is `decimal`, never `double`. Use `Acme.Billing.Money` where it fits.
- Never reimplement arithmetic Acme.Billing already provides.
- Every monetary path is covered by a test in InvoiceKit.Tests.

## Finding out about a file

Per-file documentation mirrors the source tree: `src/foo/Bar.cs` → `docs/llms/foo/Bar.md`.
Read that page when you touch a file — it carries purpose, gotchas and test-mined
examples that the signatures do not. A `.intent.json` sidecar beside it holds the same
content in machine-readable form.

Do not read the documentation tree up front. Retrieve one page when you open the file
it describes.

## Outside this repository

- `Acme.Billing` — sibling repository, documented at `../Acme.Billing/docs/llms/`:
  `foo/Bar.cs` under its source root → `../Acme.Billing/docs/llms/foo/Bar.md`.

That is roughly 470 tokens against a 6,000-token ceiling. The headroom is deliberate: the goal, the workspace map and the tool schemas all have to fit beside it.

the sibling line is resolved, not assumed

That last section is derived from where the documentation actually went. AgentProfileEmitter.Emit takes the resolved siblingLocations — the same list RootClaudeEmitter already received — and renders each sibling’s real documentation root plus the mirror rule for it, computed from the directory DocGen wrote to. Both layouts of §2.2 therefore come out right, and a sibling the run produced no pages for is named without a path rather than pointed at an empty directory: 

- `Acme.Billing` — sibling repository. No documentation generated for it.

One fixed string remains above it: the “Finding out about a file” rule always names this repository’s docs/llms/, whether or not the main-repo documentation pass ever ran. On a project whose source GlassCoder is writing, that pass is usually off (§3, step 2) and the line points at nothing. It costs a worker at most one failed retrieval, and the profile is otherwise silent about a tree that does not exist — but it is the one claim in the file still made without evidence. See §6.2.

# VatCalculator

Applies VAT to invoice lines. Stateless; safe to call from any thread.

## `Money GrossOf(Money net, VatRate rate)`

**Intent** — the single place VAT is applied in the Acme stack.
**Behaviour** — multiplies by `1 + rate.Fraction` and returns a new `Money`.
**Gotchas** — `Money` rounds on construction, to the currency's minor unit, away from
zero. Do **not** round the result again: a second rounding of an already-rounded value
is where the classic one-cent drift comes from. Callers that need per-line VAT should
call this per line rather than once on the sum — see `GrossOfLines`.

using Acme.Billing;

namespace InvoiceKit.Core;

/// <summary>Totals for one invoice. Arithmetic belongs to Acme.Billing.</summary>
public static class InvoiceTotals
{
    public static InvoiceTotal Of(Invoice invoice)
    {
        var net   = invoice.Lines.Aggregate(Money.Zero(invoice.Currency),
                        (sum, line) => sum + line.Net);
        var gross = invoice.Lines.Aggregate(Money.Zero(invoice.Currency),
                        (sum, line) => sum + VatCalculator.GrossOf(line.Net, line.VatRate));

        // No rounding here: Money rounds on construction.
        return new InvoiceTotal(net, gross - net, gross);
    }
}

5.1 Importing the outcomes

Module D’s Import metrics reads the harness’s metrics.jsonl, reduces it per slug and annotates the loaded plan. It is strictly read-only and strictly advisory: it never rewrites the plan, because deciding that a task was too big is a judgement and the human gate exists so a machine does not make it.

the one path to set

The importer looks first at <RepoRoot>\telemetry\metrics\metrics.jsonl and falls back to a file picker. GlassCoder writes to %LOCALAPPDATA%\GlassCoder\metrics\metrics.jsonl. Those are not the same place. Either point the picker at the real file each time, set Metrics:Directory to an absolute path under the repository’s telemetry/metrics, or snapshot it the way this repository does with scripts/publish-logs.ps1.

5.2 What the numbers are for

A reviewer score is an opinion about a document; an oracle outcome is a fact about it. Until the two meet, neither side knows whether the context was good enough. Three readings are worth acting on:

  • Two or more attempts, and the transcript shows the page was read — the documentation was thin, not absent. That is a Module B finding: re-enrich that file, or add the missing gotcha. It is the most valuable signal the pairing produces, because it is the only one that says which page to improve.
  • Two or more attempts, and the page was never opened — the pointer failed, not the prose. Check that the docs are inside a readable root and that the profile names the path they are actually at (see §4.1).
  • StepLimit or TimeLimit — the task is more than one agent’s worth of work. Split it in Module D; the slugs of the halves become new join keys and the original’s history stays attached to the original.

5.3 The other direction — GlassCoder as GlassContext’s worker

Set agentProvider: "GlassCoder" and GlassContext’s own agent work — per-file intent enrichment, principally, which is the expensive pass in step 2 — runs on the local box through glasscoder instead of through metered Claude Code. Same seam, same contract, different tokens. On a two-hundred-file dependency that is the difference between a documentation pass you run per release and one you run once.

The contract is the interesting part: the runner never writes files. It returns text, and GlassContext performs every write through SafeFileWriter. That is enforced rather than trusted — each run is handed a generated arm configuration with an empty WritablePaths, which the host reads as “nothing is writable”, so the agent physically cannot edit the repository it is reading. The two applications exchange a command line and stdout rather than an assembly reference, because both Core libraries define a type called AgentRunRequest and putting two meanings of that name into one compilation is a problem neither needs.

6.1 Two pending tasks need their scope adjusted

task 81, rescoped

Task 81 hashes the concatenated RootContextFiles, so that two runs carrying identical context share a hash whatever their timestamps say. That is the right idea and the wrong set of files for this workflow: the root context here is one small profile that changes rarely, while the thing that actually varies between runs is the documentation tree — and that is retrieved on demand, so it never appears in RootContextFiles at all.

A re-run of Module B can change every page the worker reads and leave the hash identical. To make a fresh-versus-stale ablation mean anything here, the stamp needs to cover what was retrieved as well as what was resident: hash the pages the run actually opened, or the docs tree as a whole, alongside the root.

task 82, restated

As written, task 82 fires its hint on first touch of a workspace source file, mapping src/foo/Bar.cs to docs/llms/foo/Bar.md. That mapping is for a repository whose own source is documented. In this pairing the documented tree is the dependency’s, and the files the agent touches most are ones it is creating — for which no page exists and none should. Implemented literally, the hint would append a dead path to most observations.

The version worth building points the other way: when the agent references a type it did not declare, name that type’s page. Same one line, same budget, aimed at the retrieval that actually pays — and still worth deleting rather than keeping out of politeness if it does not move tokens-to-solve.
